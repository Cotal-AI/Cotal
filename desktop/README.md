# Cotal desktop

The Tauri app controls the stock `cotal daemon`. It bundles that CLI and Node 24, so end users do not need a terminal, Node or npm. The app and CLI use the same daemon, sign-in and space registry. Closing the window hides it in the tray; quitting the app leaves the installed daemon running.

## Use

Open Cotal and choose **Continue with Cotal Cloud**, or **Use another Cotal host** to enter your installation's sign-in URL. The welcome explains who can launch applications as your user. Continuing prepares the background service if needed and opens browser approval, with a code and a button to reopen that page. Your login stays in the background service, never in this app.

On account-computer hosts, successful sign-in opens **This computer is connected to your account** with **Open dashboard** to turn on spaces. The header reads **Ready** with no enabled spaces, **Connected** when a space answers, and **Sign in required** after account sign-in expires. When no space is connected and a space refuses, it shows **Needs attention** and **Connection needs attention** with a red warning icon. Removing all spaces keeps **Ready** and shows **No space is using this computer**. Ready and Connected dots are green, starting or waiting dots gold, and actionable refusal or sign-in dots red.

On hosts without account computers, the four steps are Welcome, Sign in, Connect and Ready. After approval the app selects the space named by an onboarding link, otherwise the personal space, otherwise the account's only space. Several team spaces without a personal one show a compact choice on Connect. The confirmation names the space before **Connect this computer** runs setup with five named progress steps. Nothing connects before that click. Original diagnostics and exact refusals stay under a closed **Details** disclosure.

On Connect and in Settings after connecting, choose **Edit** in the computer-name pill to rename it. **Save** or Enter saves, and **Cancel** or Escape leaves the name unchanged. Names use 1 to 128 trimmed characters without control characters or line breaks. Long names truncate with the full name available on hover. The daemon saves the name and immediately sends it to the account host, so the dashboard shows the same name after registration. The default is the operating system's computer name, not a network-supplied macOS hostname. The computer owns its name; a future dashboard rename must ask the computer to adopt a desired name.

With several saved logins, the app follows the provider just signed in to, then the selected space's provider, then the only supported account. A failed refresh at another provider shows a notice naming its host without blocking sign-in or Refresh spaces. Failure at the active provider remains an error. Older daemons without provider failure details retain their existing error behavior.

While waiting for the browser, copy the approval code with **Copy** and watch its countdown. An expired code offers **Get a new code**. A replacement waits for the old native sign-in to settle, so two sign-ins never overlap. Approval advances the app automatically. Missing applications, declined sign-in, an unreachable host, empty accounts, pending owner approval, active sessions and version mismatch each show a recovery action. Details keeps the original diagnosis.

Step changes fade in with a small movement. Progress markers show waiting, running and completion, and the running row says what is being checked. Details and notices expand in height. Reduced motion removes movement and continuous animation. Enter invokes the current primary action, Escape closes Details, and one polite live region announces state changes. Background refresh preserves focus, typed fields and unchanged progress nodes.

Later opens show **Spaces using this computer**, the same list as Ready. Each row names a space and its kind, with **Remove** to disconnect it. **Add a space** when the list is empty, or **Add to another space** when a space is listed, shows the account's other spaces and a separate confirmation before connecting. Pending owner approval stays in the space's row. When every per-space connection is waiting, **Check approval** refreshes its status. Removing the last space leaves one heading and **Add a space**, without an empty list gap. If every space is waiting, the gold clock view names the owner approval and hides the empty application list. Account-computer hosts keep Open dashboard available while approval is pending. Open dashboard, Open at login and the version remain available. The window defaults to 880×660, with a 560×660 minimum. At increased zoom, the app scrolls internally so the top of the card and its final actions remain reachable. The paper theme and local icons are unchanged. The background service runs as the operating-system user after the window closes. Removing a space stops its Manager and machine-service connection without revoking remote grants. On hosts with account computers, Connect and Remove update the same desired space list as the dashboard. Ready reads daemon account status and shows connected, starting, waiting for approval, locally removed and refused spaces. Sign-in expiry stays on Ready with a primary **Sign in** button. Hosts without account computers report per-space mode and keep local connections.

Refresh also reads the hosted Managers' local agent inventory over their parent IPC channels. The connected view lists the agent name, application, space, folder and elapsed running time. The pinned model is available on hover and in the accessible description. A secondary count names the observed inventory. With running agents, a compact header makes room for six rows in the single-space view. The list shrinks when update notices or more space rows need room, and scrolls internally. Empty inventory is hidden when no space is connected. Installed applications appear once, in a secondary summary when inventory is available or as application chips otherwise. Long names and folders are shortened in the middle, with their full values available on hover and to assistive technology. The list scrolls internally without scrolling the window. The CLI's `cotal daemon status` text and JSON expose the same per-space observation. A Manager that cannot answer reports an unreadable space, not an empty inventory. No prompts, credentials, console links or command lines enter this read. The tray reports the running-agent count, or says agents are unavailable when an observation fails.

Refresh reads hosted Manager readiness. Account-computer status refreshes each second while the window is visible, so dashboard changes arrive after the daemon's five-second desired-set poll. Per-space hosts refresh every ten seconds. A connected machine service alone is not launch-ready. While the selected space is launch-ready, Connect this computer is disabled. Delayed status replies cannot replace a newer action or selection. A missing application refusal names the supported applications and offers **Check again**, which runs the same setup again. An error that a background status check raised clears on the next check that succeeds, so a service restart during an update leaves no stale error behind. An error from anything else stays until you act on it. When the background service is not running, **Start service** starts it and returns to the view you were on.

The `setup-progress` frame carries additive `progress` metadata (`step`, `outcome`, `detail`, and application names for the application check) from setup's own records. The renderer does not infer steps from terminal sentences. Terminal report lines are unchanged. Missing service on first open is a neutral setup state, while real refusals retain their exact reason and remedy in Details.

The app runs the stock `cotal daemon setup --space <space> --idp <url>` operation through its closed native boundary. Setup reconciles stock connectors, prepares the hosted Manager's default persona, and hosts that space's Manager. Machine-service registration and owner approval remain separate and do not delay launch-readiness. The daemon restarts hosted Managers after crashes and resumes them after its own restart. Disconnect removes that intent. The terminal's `--no-manager` keeps the connection-only path.

On macOS and Linux the bundled CLI reads PATH from the account's interactive login shell with a bounded native call. It keeps only PATH, validates absolute directories, and adds its bundled Node directory. No shell output or shell credentials enter the renderer. Setup uses the daemon's guarded pinned-PATH refresh when a newly installed application is missing from its service environment. Windows reads the current machine and user PATH through the system PowerShell without loading a profile; its scheduled task reads those values on each native start. No renderer PATH is accepted. A shell that fails or a relative PATH refuses instead of guessing. Installation preserves the refusal message and next step before any service change.

Long connected-space lists scroll inside a named region. Tab to the list and use the arrow keys, Home or End to reach its rows while the header stays available.

On account-computer hosts, Open dashboard opens the signed-in provider's `/machines` page even before a space is launch-ready. Per-space hosts target `/machines?space=<canonical catalog id>&machine=<Manager instance id>` only with a launch-ready Manager. The canonical ID comes from the daemon's discovered catalog, not a space slug. Changing spaces or disconnecting discards the old per-space target.

The app does not replace existing daemon identities, change grants, or claim remote vitals that the registered service does not expose. Sign-out, identity-contract migration, remote management and signed automatic updates remain separate from these controls.

A dashboard can open `cotal://connect?idp=<encoded-provider-url>&space=<space>`. The installer registers this scheme. It only fills public provider/space fields; it does not start sign-in, approve a grant or connect. The route must be `connect` with no path or a single `/`. User information, explicit ports, fragments, unknown fields, secrets and duplicate parameters are refused before URL normalization. Provider URLs cannot contain a query or fragment. Parsing does not require the WebView to support custom-scheme URL objects. Development runs do not register a protocol handler on the host.

The equivalent terminal controls are `cotal daemon install`, `cotal daemon start`, `cotal daemon login --idp <url>`, `cotal daemon spaces --refresh`, and `cotal daemon setup --space <space> --idp <url>`. The app does not maintain a second configuration or login store. The lower-level `register` and `service-connect` adapter requests remain available for machine-service connections.

Registration requires the space owner's approval and the space operator's binding for `ai.cotal.machine`. No shipped command or page provides those approval controls. Once both are complete, rerun `cotal daemon register --space <space>` until it reports `registered`, then run `cotal daemon service-connect --space <space>`. See the [daemon registration prerequisites](../docs/cli-processes.mdx#daemon) for the approval states and refusals.

Space rows say Connected only after that space's Manager reports launch readiness. A space that is still coming up says Starting, including one that was just turned on and whose Manager is booting. A refused, ended, conflicting, expired, unreachable, or disconnected space names that state on its row, and a saved refusal shows its own sentence there. The window title and tray say Needs attention for either. The space heading includes the total count. Long lists keep natural row heights and size their scroll region to whole rows while reserving room for the actions. Short names share a line with their pill and status. Connected content scrolls inside the card's padding. The footer stays outside the card's scroll region. Edit in the Connected header opens the computer-name editor in Settings. During Connect, the editor expands in the header rather than staying inside the name pill.

## Design

The cotal.ai site design system is the visual source: cream paper, navy ink, hard offset shadows and the three-ring mark. The app uses one paper theme in either OS appearance. Bricolage Grotesque, Geist and Geist Mono are bundled as latin WOFF2 files with their SIL Open Font License texts in `dist/licenses/`. No font host is contacted. The existing same-origin CSP covers fonts through `default-src 'self'`.

## Settings

Open **Settings** in the window or **Settings…** from the tray or menu bar after setup. It uses the same window and shows this computer's name, update preferences, Open at login, the selected account and its spaces, and app and background service versions. **Edit name** opens the computer-name editor in its Settings row. Account spaces use their catalog display names when available, including account-action outcomes and connections that remain after sign-out. At the default window size, all five Settings sections remain visible. Enlarged text can scroll inside Settings. Open at login stays above taskbar pin guidance. **Sign out** names the selected host and asks for confirmation. It revokes that login session and clears its cached sign-in and discovered spaces. Existing computer connections keep running on their own service proofs. Disconnect first if you also want to stop those connections.

**Disconnect this computer** shows the spaces it will stop before confirmation. It stops their hosted Managers and machine-service connections and removes their resume intent. Account hosts also update the desired space list. The background service stays installed. This action does not remove the computer from the dashboard or revoke remote authority. Disconnect erases local service credentials and identity. Connecting again requires registration and approval. A refused or unknown result is shown rather than reported as a completed disconnect.

## Updates

A newer desktop version appears in a gold notice and in the tray menu after setup. **Later** hides that version until another version is available. Opening the installer checks that version's GitHub release assets for this platform and architecture. If no matching installer exists, Cotal opens the release page and explains why. Installer feedback appears in Settings under Updates and is announced to assistive technology. Install the downloaded version and reopen Cotal. The app does not replace itself, and no automatic-update feed is configured.

**Check now** runs the background service's existing update check. Its registry cache lasts a day after success and an hour after an attempt, so this does not promise a fresh network request. Desktop installations offer **Notify me about updates**, because their app and bundled service update through the platform installer. Linux npm installations can offer **Install updates automatically** for the background service. These preferences are the same ones used by `cotal update --auto` and `cotal update --notify`.

## Develop

Install the [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/) for your OS and use Node 24 with the repository's pnpm version.

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm --filter cotal-ai seeded-connectors
pnpm --dir desktop prepare:runtime
pnpm --dir desktop check:runtime
pnpm --dir desktop app:dev
```

The runtime staging command uses lockfile-based `pnpm deploy` with a hoisted dependency layout to package the built stock workspace. It removes build-only source maps, TypeScript declarations, test trees, duplicate non-runtime package outputs and the local `nats-server` binary before sealing `desktop-runtime.json`, and strips local debug symbols from the bundled Node binary on Linux and macOS. It refuses an existing staged runtime rather than overwriting files a daemon could still be using. Use a clean build checkout for another version. No install or service start happens during staging.

On Windows, the bundled executable keeps the name `node.exe`. The runtime check relocates it with that installed name. Linux and macOS continue to use `cotal-node`. The app selects the bundled executable from its own installation, never from PATH.

```sh
pnpm --dir desktop test
pnpm --dir desktop build
cargo test --manifest-path desktop/src-tauri/Cargo.toml --no-default-features --lib
pnpm --dir desktop app:build
```

The Rust tests without default features check request, URL and environment boundaries, not the native webview or tray. A browser preview displays a native-controls-unavailable message rather than simulated daemon state.

`pnpm --dir desktop test:render` builds the real front end and serves it to headless Chromium with only the native bridge stubbed. Install its browser with `pnpm --dir desktop exec playwright-core install chromium`. The suite checks every state in the paper theme at 880×660 and 560×660: browser errors, page scroll, text clipping, target overlap, Tab order, axe accessibility including contrast, and reduced motion. Screenshots go to `desktop/test/render/artifacts/`, or `SHOTS=<directory>`. `CHROMIUM_PATH` selects an installed Chromium executable. `MOTION=1` also records 0, 80, 160 and 240 ms frames in normal and reduced motion, plus a JSON record of captured animations. Progress completion, success, notice expansion and Details opening must capture their expected finite animation. The server uses the app's shipped CSP. `CASES=<comma-separated-names>` narrows a local iteration. CI uploads the renders without comparing font-sensitive golden images.

## Real-window checks

The Desktop apps workflow installs the release deb or NSIS package, or mounts the DMG and copies its app to Applications. Each launch uses private home, XDG, application-data and runtime directories. It requires a live process, real OS and memory metadata through native accessibility, and a nonblank window-sized PNG. Linux uses an owned D-Bus session, Xvfb and ImageMagick. Windows captures the app's native window with PowerShell. Both macOS 15 architectures and the Apple Silicon macOS 26 job launch the mounted app by its canonical executable path, then the Applications copy through LaunchServices, capturing each in light and dark appearance. Linux OCR and macOS Vision require the captured welcome screen. Only the Applications validation copy has its quarantine removed. It keeps the shipped signature, which must verify strictly, without re-signing the copy or disabling Gatekeeper. Before its window launches, the harness reads the installed `cotal-node` signature and requires the `com.apple.security.cs.allow-jit` key, independent of the macOS entitlement display format, then runs the installed bundled CLI's `daemon status --json` through that Node. The private home has no daemon: the answer must be the stock `TARGET_UNAVAILABLE` refusal with cause `NOT_RUNNING` and exit 2, rather than a crash or an unparsed process exit. `applications-daemon-status.json` retains the answer and installed Node/CLI hashes. This proves the installed client executes, not that a service is running. The macOS 26 job exercises the hardened-runtime behavior absent on macOS 15. Its artifacts end in `-macos26` to separate the two ARM64 jobs. `desktop-launch-<OS>-<arch>` artifacts hold the screenshots and logs, with `mounted-dmg-` and `applications-` prefixes for macOS. macOS retains every attempted region and whole-display capture, with capture and accessibility-inspection timestamps and the paired accessibility tree. The region must still pass the welcome-screen check. The later native presence check reuses the stopped Applications copy only when the successful launch record and installed executable hash still match. An unrelated existing installation refuses. Before the first executable launch on each platform, a persistent native sampler waits for the window to become visible and captures its header until the coloured mark appears. `*-first-paint` directories retain the first visible and painted header images, monotonic sample times and capture durations. These are sampled visible-to-header intervals, not compositor presentation timestamps. Process-start-to-visible latency is recorded separately from the sampler clock, using Linux process start ticks, macOS kernel process start time or Windows process start time. Header samples also record paper coverage and whether a sampled frame was neither paper nor content. The Windows header check requires all three mark colours against paper, not arbitrary coloured desktop pixels. Sampler errors are retained separately and do not replace or block the connected lifecycle verdict.

The Windows job also runs a diagnostic-only launch with one fixed public synthetic `cotal://connect` URL in fresh private state. It does not sign in or install a service. `desktop-windows-deep-link` retains the native argv classification, the plugin's current URLs, a read-only renderer snapshot and a screenshot after launch. Unknown arguments remain redacted. A diagnostic result does not replace or relax the per-space or account journey assertions.

Debug E2E builds retain `login-preference-receipts.jsonl` for the Open at login input. It records the app's DOM change handler, trusted-input and busy flags, native preference handler entry/return, and the existing login-item API calls' success or failure and enabled readback. Each record pins the app PID and time. Connection observations are named separately from preference changes. No extra native read, toggle, wait or retry is added. A later finally-cleanup input remains separate from the failed acceptance input. Missing receipts do not prove the OS lost a click.

Linux and Windows also drive the built webview through `tauri-driver`, using WebKitWebDriver or an Edge WebDriver matching the app's installed WebView2 runtime version. They reuse the daemon desktop setup smoke's local signed provider, real broker, auth service and hosted Manager. The test follows Welcome, Sign in, Connect and Ready, using an inline space chooser only when the account has no default. It covers a custom host, pending browser approval, missing-application refusal and Check again, dashboard targeting, quit/reopen, removing a Ready-list connection, a `cotal://connect` link and denied/expired approval. Both window state and `cotal daemon status` must agree. The fixture host returns 404 for account-computer routes and exercises the supported per-space compatibility path. Its connector proves application discovery and Manager readiness, not a real agent's sign-in or launch. Selectors use stable element IDs only. ## Platforms

### App presence and login

After setup, close the window and use Cotal in the macOS menu bar or the Windows/Linux system tray. Its menu shows **Ready** for a registered account with no space turned on, **Connected** when a space is connected, **Starting** while spaces start or wait, and **Sign in required** when signed out or expired. A space that failed, or that has a saved refusal, shows **Needs attention**. Its actions are **Settings…**, **Open dashboard**, and **Quit app (computer stays connected)**. Settings reopens the Ready list after setup, or keeps onboarding available before setup. Open dashboard uses the same verified canonical space and Manager target as the window. If that target is unavailable, the window explains what needs attention. Quitting stops only the app, not the background daemon. Status refresh continues while the window is hidden. Menu item IDs are `status`, `settings`, `dashboard`, and `quit`, on tray `machine`.

On macOS, install **Cotal.app** in Applications. The DMG places Cotal on the left and the Applications alias on the right. When opened from a mounted disk image or Downloads, Cotal offers to copy itself to `/Applications/Cotal.app` and reopen there. It never replaces an existing installation. **Not now** is remembered. Open at login is unavailable from these temporary locations. Cotal appears in the Dock while its window is open. Closing the window leaves only its menu bar item. Opening it from the menu bar, Applications, Spotlight or a `cotal://` link restores the window and Dock icon. Dock Quit and Cmd+Q quit the app without stopping the daemon.

To keep the macOS icon after quitting, use the Dock's **Options > Keep in Dock**. Cotal does not edit Dock preferences or restart the Dock. Apple provides user controls and managed Dock profiles, but no supported ordinary-app self-pinning API was found.

On Windows, both installers create a Cotal Start menu entry and desktop shortcut with the same `ai.cotal.desktop` application identity as the running app. A visible window has its Cotal taskbar button. A second launch focuses the existing window. Closing hides to the system tray, with a one-time explanation before the first hide. On supported Windows versions, the connected screen offers **Pin Cotal to the taskbar** once. Only clicking it requests Windows consent. Already pinned apps are not offered again. Older versions that require Microsoft's limited-access token, unsupported versions and administrator restrictions display their reason instead. Cotal has no pinning token and does not use undocumented pinning commands.

Once the computer is registered to its account, **Open at login** defaults on, even with no assigned spaces. It opens Cotal in the background at login, without showing or focusing its window. On macOS the app stays in the menu bar without a Dock icon, and on Windows/Linux it stays in the system tray until opened. Turn the switch off to remember that choice across reconnects. On hosts without account computers, startup follows the verified space inventory and disconnecting the last space removes the login entry. On account-capable hosts, removing a space does not disconnect the computer from the account. The app's login entry and the daemon's background service are separate.

Windows NSIS and MSI uninstall remove their shortcuts and the current user's app login entry. A macOS DMG has no executable uninstaller: dragging the app to Trash cannot run cleanup code. Turn off Open at login before deleting the app. Linux deb/rpm packages install the desktop entry and icons for the launcher. Package removal does not remove the independently installed daemon. Disconnect spaces and use the matching CLI's daemon uninstall operation before removing a service installation you no longer need.

The bundled Node 24 requires macOS 13.5 or later and Windows 10 / Server 2016 or later. Linux installers are built on Ubuntu 24.04 and require the platform WebKitGTK 4.1 libraries; older distributions have not been verified.

Native builds run on the target OS. AppImage is not a daemon distribution: its temporary mount is not a durable service executable path. Headless LaunchDaemon, Windows SCM and Linux system-service profiles are not provided by the desktop installer.

Without a certificate, macOS packages are signed ad hoc over the whole bundle, and the build verifies that signature. macOS then asks the person to allow a downloaded copy once under Privacy & Security, where an unsealed bundle is reported as damaged. The bundled Node runs under the hardened runtime, so every macOS signature carries `src-tauri/entitlements.plist`: V8's executable memory and the ad hoc signed native addons need it, and without it Node stops before it runs a line. The build runs the bundled Node, the bundled CLI and each native addon from the signed app. Other validation builds are unsigned. Version-tag builds sign and notarize macOS packages when `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY` and one complete Apple ID or App Store Connect notarization set exist. Configuring both sets refuses the build. Windows uses `WINDOWS_CERTIFICATE`, `WINDOWS_CERTIFICATE_PASSWORD` and `WINDOWS_TIMESTAMP_URL`, importing the owner's PFX and passing Tauri its thumbprint, SHA-256 and timestamp configuration. Missing Windows secrets keep validation packaging unsigned, and missing macOS secrets keep the ad hoc signature; partial secrets or a signing failure stop the build. Linux signing is not configured. Version-tag installers are attached to the GitHub release, creating a draft if needed. No automatic-update feed is configured.

After replacing the app in the same installation directory, reopen it, choose a saved space and click Connect this computer. Read-only saved-space listing works across compatible daemon versions. Stock setup can restart the recorded owned service under its existing Manager seat fence to load the new bundled runtime. Other mismatched-version mutations remain refused. If the old service pins another installation directory or an incompatible protocol, setup refuses with its next step. That relocation needs the old installation's service removal before setup from the new app. Native installer replacement and active-seat acceptance still need testing on macOS and Windows.

## Local boundary

The main window reports a decoded mark and prepared header layout through the no-argument, idempotent `first_paint` command without waiting for a hidden-page frame clock; native show requests wait for that report, with a two-second limit, while background starts stay hidden. A tiny same-origin `paper.css` loads before the bundle to keep the initial background paper under the unchanged CSP, matching the native window and supported webview backgrounds.

The OS user is the trust principal. A hostile process running as that same user is not isolated by the tray. Native peer authentication and lifetime custody protect the daemon from other users and foreign listeners. The renderer has no shell, filesystem or remote IPC capability. Login startup is reconciled from successful native daemon replies, not a renderer-supplied connected flag. Its preference control accepts only a Boolean. Relocation uses this executable's bundle and the fixed Applications destination, and pinning accepts no app identity or command. Neither command accepts a renderer path. Rust launches only the bundled Node and stock CLI, admits a closed request schema, removes inherited provider/agent authority from its child environment, and bounds input/output and time. Browser opening permits HTTPS and literal loopback HTTP only. Login proofs and tokens never cross into the webview.

On macOS, starting or removing a loaded LaunchAgent requires its recorded source digest and native evidence matching its label, executable and full argument vector. New installs carry the working directory in those arguments: a small Node entry validates it and changes directory before loading the CLI. They do not depend on launchd exporting its WorkingDirectory property. Legacy plists that carry that property still require the matching native field; an omitted field refuses without stopping the job. No legacy receipt is migrated or adopted through the new path. An unavailable lookup or missing executable/arguments also refuses. `launchctl` display text is not parsed as authority.
