`@cotal-ai/pi` loads Cotal into the operator's pi process.
The connector does not include a pi runtime.
[Connect pi](connect-pi.mdx) contains installation and launch procedures.

## Host integration

This release targets `@earendil-works/pi-coding-agent@0.79.10`.
Cotal requires Node 22 or later; that pi host requires Node 22.19 or later.
The installed `pi` binary is required for managed spawning.

The standalone extension supports managed spawning, interactive pi extension discovery, and SDK hosts using pi's default resource loader.
The copied artifact has no repository-local or sibling-file imports.
SDK hosts must bind extension lifecycle events if Cotal is expected to drive an idle session proactively.
The extension requires pi's custom-message lifecycle API and refuses an incompatible host.

Without a Cotal mesh identity, the extension is inactive.
`COTAL_HOME` or `COTAL_DEFAULT_AGENT` alone does not activate it.
A partial managed control endpoint is refused.
Cooperative stop uses connector-core's authenticated control server and the active pi context's `shutdown()`.

Peer traffic uses custom messages with `triggerTurn: true` and `deliverAs: "steer"`.
That path can steer a streaming turn and avoids an idle-to-streaming race during dispatch.
The structured batch details remain attached to the custom message.
Human `input` transformations are bypassed because the message is peer context.
Provider, tool, permission, and sandbox hooks remain active.
A text response in pi is not automatically a peer reply.
Peer replies are explicit `cotal_dm`, `cotal_send`, or `cotal_anycast` calls.

## Delivery confirmation

Delivery uses separate observations of one batch:

1. A matching custom `message_start` proves pi dequeued the batch locally.
2. A provider `context` containing the same batch proves it entered that request.
3. A successful `after_provider_response` confirms provider acceptance when the transport exposes that hook.

Some transports, including the Codex subscription, omit `after_provider_response`.
For those transports, a clean terminal assistant boundary following the matching context confirms acceptance.
Local dequeue alone does not acknowledge the message.

Only provider-confirmed IDs can be acknowledged, and acknowledgement waits for a terminal agent boundary.
The pi-local ledger commits those IDs through `MeshAgent.drainInboxIds()`.
It removes exact IDs even when older quiet traffic is interleaved or some IDs were already evicted by inbox overflow.
Missing confirmed IDs are marked handled and tombstoned so later copies do not reappear.
A crash or quit before the terminal boundary leaves durable traffic available for redelivery.

Quiet ambient never enters automatic or continuation batches.
Quiet mentions remain automatic.
`cotal_inbox` explicitly returns and clears quiet ambient while the driver owns automatic traffic.
Focus recall displayed alongside the inbox is read-only.

### Run turns

A run turn is carried by its inbox batch.
It becomes shown when the provider takes that request.
`after_provider_response` proves this on transports that expose it.
Without that hook, a tool execution from the answer or a clean terminal boundary proves it for the matching context.
The seat can then call `cotal_yield` during the same pi turn.
A batch the provider never accepts leaves the run turn unshown for later delivery.

### Continuation rules

Pi's `agent_end` does not state whether another attempt will follow.
The driver uses the active `AbortSignal`, the last assistant stop reason, and output count to decide whether work is terminal.

| Stop outcome | Delivery behavior |
| --- | --- |
| Non-aborted `stop` or `toolUse` | Confirmed IDs can commit. |
| Non-aborted `length` with positive output | Confirmed IDs can commit. |
| Error, unknown reason, or `length` without positive output | The association is retained and automatic continuation is bounded. |
| User abort | The association is retained without automatic retry. |

A nonterminal outcome with pending delivery starts at most two automatic continuation attempts, separated by a fixed 50 ms backoff.
Each attempt re-dispatches the retained batch through the same send path.
Its `agent_start` and subsequent provider evidence must prove the continuation.
A clean terminal boundary commits confirmed work.
After the attempts are exhausted, presence names the need for intervention and the attempt count.
The remedies are a new turn in that session or replacement of the seat.
The person who aborted a turn controls its continuation, so abort remains a plain hold.

`session_before_compact` with `reason: "overflow"` and `willRetry: true` identifies overflow but does not itself prove a terminal outcome.
An abort or dispatch watchdog blocks automatic replay.
In managed headless use, restart ends a possibly live provider call before durable redelivery.

## Session lifecycle

`reload`, `new`, `resume`, and `fork` tear down the extension runtime.
A process-global map retains the mesh connection, control listener, delivery association, and ordered presence updates for the same identity.
The next `session_start` binds the replacement runtime and atomically records the new pi session ID.
Only `session_shutdown` with reason `quit` stops the mesh.

### Managed recovery

`--resume <id>` uses `pi --fork <id>` to create a new meshed session without changing the source transcript.
A fresh managed seat receives a session UUID before its first turn, so an idle seat still has a recoverable identity.
After readiness, the manager obtains the current native session ID through the token-authenticated control socket.

An unexpected managed pi process exit reopens that session with the same Cotal identity, lifecycle UID, credentials, and durable inbox.
Three restarts are allowed in a rolling two-minute window.
A fourth crash retires the seat as a crash loop.
Deliberate stop, despawn, or maintenance does not trigger restart.

A manifest with `continuity: exact` uses `pi --session <id>`.
A missing session is refused rather than replaced by an empty transcript with the same ID.
Forking, same-session continuation, and reopening are mutually exclusive launch requests.

## Event plane

Managed pi publishes AG-UI events on `events.<owner>.<actor>` using pi's native session ID as the thread ID.
The durable source is the native session JSONL file.
Extension hooks wake the reader after persistence; they are not the event record.

Published records include runs, completed assistant text, and tool start and end boundaries.
Live text deltas cannot be recovered after a crash and are not published.
Tool arguments and results, reasoning, usage, branch records, and compaction records are excluded.
User text is excluded because native user records cannot distinguish human-authored text from peer-authored context.

Events are enabled by default.
`--no-events` can disable them only on an unrestricted space.
An event-required registration arms the plane independently of an ambient flag.
The seat still needs the channel's publish grant and a stable workspace root for its write-ahead log.

A stopped emitter leaves the seat running on every space.
The pi log records `AG-UI emitter stopped` with the reason and re-establishment delay.
Re-establishment starts the same session from its durable event state.
It settles any pending frame and restores the run and tool calls opened by that frame, so a later persisted result can close its tool call.

Reload keeps the same native session and event frontier.
A new, resumed, or forked session gets its own thread and log on the same principal channel.
Existing transcript history is excluded when a newly adopted session starts publishing.
An acknowledged event cursor takes precedence during process restart.

## Launch restrictions

Model variants, MCP tool sharing, and arbitrary launch options are not implemented and are refused.
Persona text is passed through a private file as pi's appended system prompt.
`--model` overrides the persona model and is passed to pi unchanged.
Provider variables come from the connector's declared keys plus the explicit `spawn.env` allowance.
The connector does not pass the whole shell environment.

An initial prompt is pi's final positional argument after every option.
An empty prompt or a prompt beginning with `-` or `@` is refused before persona material is written.
Those prefixes would be parsed as a flag or a file reference.
Cotal credentials and the control token are carried in private launch material.
The extension removes the material pointer after reading it, so shell commands do not accidentally inherit that pointer.
