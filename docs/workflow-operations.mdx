## Keyed submission [#keyed-submission]

`run-start-keyed` binds an envelope submission ID to one host-minted run. `run-submission-status` reads that binding for the
authenticated caller incarnation. Both require fresh issued reach and digest-verified contracts pinned to one manager instance and
epoch. Legacy `run-start` remains unchanged. Unsupported keyed commands never fall back to it.

The scheduler must persist the submission ID, semantic fingerprint, caller incarnation, contract digests and instance/epoch before
dispatch. The client helpers prepare that snapshot and send one attempt at a time. They pass on only `signal` and `deadlineMs`,
which a keyed request keeps at or below 30000. They refuse a reply that names another submission, instance, epoch or fingerprint,
and that outcome stays unknown. They do not schedule retries, replace unknown work or re-pin it to another manager.

Their prepared handle is process-local and WeakMap-bound: serialized JSON cannot be rehydrated through these helpers. Persisted
scheduler recovery needs separate reviewed integration, not a cast or an automatic fresh Describe. Keep the original work
reservation while reconciling any unknown outcome.

The binding winner may make at most three admission-create attempts in its original callback deadline, with the same admission
bytes and authority. Initial authorization precedes binding, but fresh authority rechecks before each admission attempt can fail
after binding and retain binding-only debt. The manager refuses a start while it is stopping or already at its launch limit before
it reads or writes a binding, so that refusal writes nothing. It says nothing about an earlier attempt under the same key, which
may already be bound or running.

`run-submission-status` takes no launch slot, so read the outcome there. A launch that fails after admission leaves `admitted`
with no run, and no later call launches it. Later duplicates only read. A `binding-only` result is a visible reconciliation hold,
not a queue or permission to repair. An absent admission is an observation at read time, not proof that the original callback
cannot still write. A changed caller generation or manager epoch refuses rather than adopting the run.

The receiving manager or issuing host measures the request budget on its own monotonic clock, and checks the caller's authority
expiry on the wall clock. Wall-clock changes do not extend or spend the monotonic request budget. Authority expiry remains a
wall-clock check. The callback deadline a status read returns is a wall-clock record of that window, not something a caller or
host enforces.

The original callback timer bounds waiting and starting more attempts. It does not cancel an already-issued broker publish, which
may land later with the same frozen admission bytes. No new admission attempt starts after the request budget or authority window
ends. Once an admission exists, the activation check uses only the manager's remaining monotonic request budget; it does not
recheck the caller's wall-clock expiry. Keep the reservation even if an earlier read observed no admission.

Submission state `activated` reports evidence of activation, including completed and failed runs. It is not a running-state or
active-lane signal. Use native `run-status` for lifecycle state. Terminal submission bindings remain permanent, and duplicate
starts never relaunch them.

This implementation is under validation. Static native and signerless issuer paths require separate acceptance evidence before
release or integration.

## Agent session requests [#from-an-agent-session]

Fresh `cotal setup` defaults declare `capabilities: [spawn, run]`. On an authenticated mesh, `run` exposes `cotal_run`. The
selected manager must support execution. The release-matched offline documentation is available through `cotal_docs` pages
`lang-card` and `workflows`.

A minimal start request has this form:

```json
{
  "verb": "start",
  "source": "await sleep(\"1s\", { name: \"first-run\" });",
  "file": "first-run.cotal.js"
}
```

`source` contains the program. `file` labels diagnostics and reads nothing from disk. The reply returns a run ID before execution
finishes. A subsequent `cotal_run` request with `verb: "status"` and that `runId` reports state and the step journal. A completed
timer records the sleep step as `ok`.

## Tool availability [#if-cotal_run-is-missing]

`cotal_orientation` reports the connector version, capabilities, and tool list. Older installations use the [upgrade
guide](https://github.com/Cotal-AI/Cotal/blob/main/docs/UPGRADING.md).

A persona needs `run` in its existing capability list, such as `capabilities: [spawn, run]`. `spawn` alone does not expose
`cotal_run`. Setup preserves existing personas except for its [byte-exact legacy migration](getting-started.mdx). Peer
persona-definition tools cannot grant capabilities.

A relaunch through the manager issues a new credential and connector configuration from the updated persona. Editing the file or
reconnecting with the old credential grants nothing. `COTAL_CAPABILITIES`, when present at launch, overrides the file. Successful
readiness checks show the tool in a fresh `cotal_orientation` result and permit `cotal_run` with `verb: "ps"`.

Tool visibility alone does not establish execution support. Hosted runs require issued caller authority. Static-auth credentials
receive issuance. On a user-auth mesh, a registered participant manager hosts authorized runs. Managed agents use their
launcher-provided bearer command and immutable manager selection. Both the current managed grant and its direct parent's current
grant must carry `run`. Removed grants, stale lifecycles, or a wrong manager refuse without borrowing a signed-in user's
authority.

Open meshes may expose the tool but refuse hosted runs. A local user-mode host without remote run authority and an `execution:
"none"` control manager also refuse. Legacy credentials without issued authority require replacement through the current issuance
path.

## Run commands [#operating-a-run]

The manager hosts runs. `cotal run start` hands the program to the manager of the resolved mesh (the usual `--space` / `--server`
/ `--creds` flags), which validates it, mints the run id, drives it in its own process, and answers with the id once the run is
recorded. The terminal is free the moment the id prints; the run continues on the manager through every pause, and a manager
restart takes back every run it had recorded running, from the journal, under the next epoch.

`resume` names a run the manager recorded and is refused while the manager is already driving it. `ps` and `journal` read;
`answer` resolves an open checkpoint, or an open `ask` attempt, from any terminal or agent that holds the `run` capability.

`journal` prints an open pause's question under its step. Once a checkpoint or `ask` settles with an accepted answer, it instead
prints the answer value as JSON, who answered, the artifact when one was cited, the recorded time, and the accepted answer id.
Expired pauses and ordinary steps print no answer line.

A settled step is never answered twice, so a participant who changes their mind uses `amend`. It files a new answer beside the
accepted one, naming the answer it supersedes, and `journal` prints each amendment under the step as an `amended` line, in the
order the store committed them. The last line is the current position, whatever clock each amender's `at` came from. The pause
stays settled and the run keeps the answer it acted on. A step that is still open, or that settled with no answer, refuses an
amend.

The manager records the amender from the credential, as for an answer, and a spawned seat may amend only an answer recorded under
its own name.

```bash
cotal run start --file build.cotal.js                   # the manager starts it; the minted id is printed
cotal run ps                                            # list run records: state, holder, lineage
cotal run journal run-3f2a90c41b7e0d5a6c884e19b02df4a1                      # print the durable step journal
cotal run resume run-3f2a90c41b7e0d5a6c884e19b02df4a1                      # the manager takes the run back
cotal run answer run-3f2a90c41b7e0d5a6c884e19b02df4a1 "/checkpoint:approve#0" --value '"yes"'
cotal run amend run-3f2a90c41b7e0d5a6c884e19b02df4a1 "/checkpoint:approve#0" --value '"no"'   # record a changed position
cotal run migrate run-3f2a90c41b7e0d5a6c884e19b02df4a1 --local --file build-v2.cotal.js   # check an edited program against the journal
```

A program that does not validate is refused before anything is recorded, with every problem in the answer as the validator would
print it. The driver records the program beside the run, so `resume` takes the run id alone and the manager reads the source back;
an edited program is a `migrate` or a `fork`, never a resume.

`cotal run migrate <runId> --local --file <program>` is that check: it replays the run's journal and walks the edited program over
it, prints whether the migration is admissible, how many journal rows the walk accounted for, every orphaned step with its verdict
and code, and exits 0 on admissible and non-zero on not. It reads only, under the same credential `journal` reads on, and the
commit side is not reachable yet: the report itself says what a commit would file and that this invocation filed nothing.

An answer is recorded under the answerer the manager knows from the caller's credential: a managed agent by its name, anyone else
by their principal. The request carries no name. An agent with `capabilities: [run]` has the same five verbs as the `cotal_run`
tool ([MCP tools](mcp-tools.mdx)), so a program can be written and started from inside a session.

A `start` or `resume` answers once the run's record is written, within a bounded wait; a manager that is still taking back a
predecessor's runs at boot refuses both with `unavailable`, and a retry a moment later is the whole remedy.

## Local execution [#local-execution]

`--local` drives the run in this process instead: `start`, `resume` and `answer` exit when the drive settles, `--by <who>` names
the answerer, and `cotal run resume <runId> --local --file <program>` is how a run with no recorded program is continued. On a
static mesh the local drive mints the run's own credential from the folder's trust material, so it runs from the mesh's project
folder.

A local start also names the run's channel ceiling itself: `--admit-read <channels> --admit-publish <channels>`, comma-separated
patterns or `none`, both required. The record it writes says an operator admitted the run and why, and the host checks it the same
way it checks a hosted admission. A registered remote user-auth manager can host a run through its issuing host.

The host resolves a versioned caller against live issuance, admits the run, and signs only the run's fixed driver, mediator and
one-shot operator credentials for manager-held nkeys. Renewal checks the activated attempt; the manager holds no signer. Local
user-auth runs remain unavailable because a user bearer holds no run rows. An open mesh hosts none either, since it issues no
caller authority to admit a run under.

## Remote user-auth hosting [#remote-user-auth-hosting]

A logged-in user starts runs on that remote manager with `cotal run start`. The auth callout issues the user's manager connection
against the user's actor-ledger row, the CLI reads the generation back from the connection's accepted row, and every `run` verb
rides the versioned rail. The issuing host admits a run only for the owner who registered the manager, and on every resume and
answer it checks that owner and that the caller's issuance is still live.

It also watches the start, resume and answer requests on the broker itself, and admits or issues for one the manager forwards only
if it saw that request, and only once. A resume or answer gets issuance only for the run, step, endpoint and amendment that
request named. An answer's credential reaches one pause, and the host reads which one off the run's own journal, for a run
admitted on that manager's instance.

A request bound to another manager instance or epoch gets nothing, and so does one whose class or pinned contract is not the one
the manager registered. Another user's start, answer or resume is refused, and so is a revoked actor's. Such a run spawns, turns
and despawns agents owned by that user. A spawn has the reach of the user who started the run, as their actor-ledger row reads at
that moment, and the host enrolls each agent through its managed-agent enrollment.

A spawn may be placed on the manager that hosts the run and on no other instance. [User-auth run
start](design/user-auth-run-start.md) records the path.

Run admission accepts canonical space names such as `cotal_cloud` and `u_example-name` without rewriting them. Endpoint names keep
their separate DNS-label grammar.

## Run admission [#run-admission]

A hosted run is admitted under the caller that started it. The caller's credential is an issuance ([identity and
auth](identity-and-auth.mdx#issued-authority)): its requests ride a versioned rail that carries the credential's generation, and
the manager resolves that generation's recorded permission ceiling and writes it beside the run before the driver starts. That
ceiling, the caller's own channel scope as it was issued, is what the run may read and post in channels; the manager's own reach
never stands in for it.

A request from a credential minted without an issuance is refused with `permission-denied` and a detail naming the caller. A run
whose caller had no channels can still sleep, checkpoint and turn agents; its `wait` on a channel is refused at the effect.

## Revocation [#revocation]

`cotal run revoke <runId> --local --by <who> --reason <text>` writes the run's revocation marker from the project folder. An empty
`--by` or `--reason` is refused before anything is written. The admission itself is never rewritten. Every host reads the marker
before its next channel effect, so an open `wait` refuses at its next poll, and no resume, takeover or manager restart continues
the run. Revoking twice is not an error, and the first reason stands.

A run whose admission is missing or revoked is left parked by the manager's boot reconcile, named in its log.

`run ps`, hosted or `--local`, reads the marker beside each run record and prints `revoked` for a run that carries one, whatever
state the record itself holds, with the revoker and the reason under the table. The record is display only here: a revoke writes
no terminal state, because no host drove the run to one and the journal owns the facts. A marker the listing cannot read, whether
the store is unreachable or the marker has a version or shape it does not know, prints `unchecked` in the `STATE` column.

The reason and the state the record carries go to stderr, and the command exits 1 once every row is printed. The hosted `run-ps`
rows carry the marker as `revoked` (`by` and `reason`) or a failed read as `revocationUnreadable`, beside the record's own
`state`.

## Refused steps [#refused-steps-and-timer-expiry]

A run whose step was refused (L5016) stays held; a resume on a host that can perform the step performs it live and continues from
there. `journal` prints what an open pause asks beneath its step key, which is the address `answer` takes back. Checkpoint expiry
rides the mediated timer writer, which the delivery daemon pumps on a live mesh; on a bare broker a pause still resolves, it just
cannot expire.

## Diagnostic inventory [#diagnostic-inventory]

A large inventory can exceed the broker's reply limit. A host that supports page mode can return one bounded JSON page. Page mode
is not in release 0.88.0 or earlier: the calling CLI or connector and the manager both need a later version.

```bash
cotal run ps --page --on <instance> --limit 8
cotal run ps --page --on <instance> --cursor <cursor>
```

For the MCP surface, use `cotal_run` with `verb: "ps"`, `instance` and `page: { limit: 8 }`. Pass a returned `nextCursor` as
`page.cursor` to continue. A managed session can use its existing manager binding. Keep the same space, endpoint filter, instance
and process epoch throughout a scan. The CLI requires `--on`; page mode is not available with `--local` or other verbs. An older
host refuses page mode rather than returning a truncated legacy list.

Each page has at most 16 rows (default 8), and the complete reply fits 65536 bytes and the broker's payload limit. The reader
issues at most 64 storage calls and stops issuing them after 2 seconds or the smaller request duration. These are application
limits, not bounds on broker CPU, disk work, client-library retries or total elapsed time. One row that cannot fit is refused,
never split.

The response carries `semantics: "diagnostic"`, the observed sequence cut, responder, storage-read count and `stopReason`. Rows
contain spec/status revisions and whether a revocation marker was observed. Programs, journal contents and revocation reasons are
omitted. Legacy requests without page mode retain their existing array output.

`endObserved` means the walk reached its cut or received a no-match response. It does not prove an atomic snapshot, absence,
ownership, terminal work or worker inactivity. Cursors are unsigned continuation data. Deleted history and restores can be
invisible. Keep partial results incomplete, and retain uncertain-start reservations and ownership holds. A continuation that makes
no progress is reported as incomplete; do not retry it in a loop or use it to release work.
