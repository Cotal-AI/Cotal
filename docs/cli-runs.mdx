Workflow commands operate recorded runs and durable step journals. A run receipt records acceptance; it does not establish live agent progress or task completion.


## run [#run]

Operate durable workflow runs (cotal-lang programs) from the terminal.

```bash
cotal run start --file <program> [--timeout <dur>] [--local --admit-read <channels> --admit-publish <channels>] [--on <instance>]
cotal run resume <runId> [--local --file <program>] [--on <instance>]
cotal run [--endpoint <ep>] [--json] [--on <instance>]
cotal run --page --on <instance> [--limit <n>] [--cursor <cursor>] [--endpoint <ep>]
cotal run show <runId> [--endpoint <ep>] [--json | [--plain] [--limit <n>]] [--on <instance>]
cotal run answer <runId> <stepKey> [--value <json>] [--artifact <ref>] [--endpoint <ep>] [--local --by <who>] [--on <instance>]
cotal run amend <runId> <stepKey> [--value <json>] [--artifact <ref>] [--endpoint <ep>] [--local --by <who>] [--on <instance>]
cotal run revoke <runId> --local --by <who> --reason <text> [--endpoint <ep>]
cotal run check <runId> (<program> | --file <program>) [--local] [--endpoint <ep>]
```

`ps` (or `list`), `journal` and `migrate` still work as compatibility aliases of bare `run`, `show`
and `check`.

Operator run commands use `--space <s>` and `--server <url>` to pick the mesh and
`--creds <path>` to select a credential where supported. Offline commands take no mesh or caller
selection. The seat-only `turns` and `yield` forms do not take `--creds`.
A hosted verb refuses a raw `--creds` file `UNSUPPORTED`, exit 2, because the file
carries no endpoint-caller triple for the manager call and that route cannot mint one. Its next step
is to run the verb again without `--creds`, in the mesh's project folder or with `--space`, where
the CLI mints the one-shot caller itself.


### Manager selection

Hosted run verbs accept `--on <manager-instance>` to choose one full manager id
as `cotal ps` prints it. A managed seat defaults to the manager that launched
it; an unbound user-auth caller with several managers must choose one. Without
`--on` its call is refused with exit 2 before any request, and the refusal names
each live manager.
`--on` does not apply to local, offline or seat-only run commands, and a failed
pin never falls back to another manager. Rich run reports label an explicit pin
as the requested manager, and the JSON target carries `requestedManagerInstance`.
Follow-up commands printed by the CLI retain the same explicit pin and fill
in the run ID the command named or the manager returned, only when it matches the native
run-token shape. Keep the pin on later status, answer and resume calls.

A run ID that is not 1 to 64 letters, digits, `_` or `-` is refused as `USAGE_INVALID`, exit 1,
on every verb that takes one, before anything is contacted. When `run show` needs a valid ID,
its list and journal commands keep the space, broker, manager or local endpoint you requested.
If the manager has no record for that ID, the suggested lookup also keeps those selectors and your output format.
For a malformed ID in `run check` or `run revoke --local`, use the suggested `cotal run list --local`
with the same target selectors, then replace only the ID in the original command.
A journal row limit applies only to the text journal. If you give both `--limit` and `--json`,
choose a limited text view or the full JSON journal before looking up a missing run ID.
A hosted verb the manager refuses reports the outcome and code as other commands do, and with
`--json` as one refusal envelope on stdout. A refusal the manager makes before acting is refused: a
denied credential or a step in the wrong state exits 2, and a program that does not validate is
`SCHEMA_INVALID`, exit 1, like other invalid input. A run or step it holds no record of is `TARGET_NOT_FOUND`, with `cotal run` or
`cotal run show <runId>` as the next step. A manager activates at most 8 runs at once, counting
each `start` or `resume` until its run is recorded. One more is refused `LIFECYCLE_BLOCKED`, exit 2,
before anything is written; the refusal names the runs still activating, and the next step is to
wait until one has activated and run it again. Any other refusal of `start`, `resume`, `answer` or
`amend` may follow a recorded change, so it is unknown, exit 3, and is not retried.

Hosted `start` on a known open mesh refuses `UNSUPPORTED` (exit 2) before looking for a manager.
Use `cotal r simulate <file>` to test the program offline. Use a static-auth mesh to host the run.

Otherwise, an unpinned hosted verb run by the operator reads the space's service registry first. On a
known open mesh with no live manager, `show` reads the journal directly from the broker. A verb that
needs a manager, including `show` with `--on`, refuses `TARGET_UNAVAILABLE` (exit 2) when the registry
lists no live manager. If this machine started the stack at the requested broker, the next step
names its project folder. A machine that only registered the space points you to the host where its
stack runs.

A mesh a run verb cannot resolve or connect to is refused before any request under the refusal's
own code, hosted or `--local`, as `ps` refuses it. With no mesh running that is `TARGET_NOT_FOUND`,
exit 2, and with `--json` one refusal envelope on stdout.

`start` hands the program to the mesh's manager, which validates it, mints the run id (the record
never takes a caller-supplied one), drives it in its own process, and answers with the id once the
run is recorded. If the program does not validate, `start` lists every problem and shows each
control character as its `\uXXXX` escape. With `--json`, the refusal carries the problems in
`error.cause.detail`. Each has a `code`, `title`, `where` with the file, line and column, `cause`,
and `fix`. Every verb
that takes a program file refuses a missing one with `TARGET_NOT_FOUND` and one this account cannot
read with `PERMISSION_DENIED`, exit 2. A directory, device, FIFO or socket is refused with
`USAGE_INVALID`, exit 1, naming its kind. Use a regular file, or a symlink to one, for the source.
A `start` interrupted with Ctrl-C or `SIGTERM` after its request went out reports outcome `unknown`,
because the manager may already have recorded the run, and exits 130 or 143. List the runs with
`cotal run` before starting it again.
A `start`, `resume`, `answer` or `amend` whose request went out and drew no reply before the
deadline is also unknown, exit 3, and is not retried, because the manager may have recorded it. Read
the run with `cotal run show` or list the runs with `cotal run` before running it again. A list or
`show` whose request drew no reply fails with `OPERATION_FAILED`, exit 5: the manager answered on the
same rail just before, so it runs, and a read is safe to run again. When no manager answered before
the request went out, or none was subscribed to receive it, the verb refuses `TARGET_UNAVAILABLE`,
exit 2.
`resume` asks the manager to take an existing run back and continue it from its step journal; the
source is the recorded program, so no `--file` is taken. Supplying it refuses `USAGE_INVALID`
(exit 1) before mesh preparation, with a JSON refusal under `--json`; omit `--file` to resume the
recorded program. A run recorded `completed` or `failed` is
refused `LIFECYCLE_BLOCKED` (exit 2) and gets no new activation, because nothing is left to continue;
the next step is `cotal run show <runId>`. Neither takes `--endpoint`: the manager records
its runs under its own endpoint, and naming another is refused. Bare `run` lists the run records and
`show` renders one run's durable records; both only inspect. When it reads through a manager,
`show` reads the journal in pages, each one reply, so a journal larger than the broker's payload
limit stays readable. A record or a journal row too large for one reply refuses `UNSUPPORTED`,
exit 2, and names `cotal run show <run-id> --local`, which reads the run's stream from its
project folder with no reply. A manager from release 0.99.3 or earlier reads no journal page, so
through it both refuse `UNSUPPORTED` and name the same local read. An open pause prints its question
under `Needs an answer`, along with its recorded checkpoint schema as JSON when present, and only
then does Next offer `answer`. The schema is guidance; checkpoint answers are not checked against it.
A checkpoint with a `to` prints
beside its question whom it escalates to, and once it has escalated, until when that attempt is open. A pause counts as open while its
last journal row is pending, so a settled or expired one is not listed there.
A pause settled with an accepted answer prints its value as JSON plus the recorded answerer,
artifact when present, time, and answer id, then one `amended` line per later amendment, in the
order the store committed them, so the last is the current position. A value longer than 120
characters is cut there, with a line that says so; `--json` carries it whole.
Expired pauses and ordinary steps print no answer line.
A step whose last journal row recorded an error prints its outcome and the recorded message under
`Step errors`, a caught failure included, with each control character shown as its `\uXXXX`
escape. A run that failed records its cause on its status. Its recorded state reads
`failed (<code>)` in the run list and the run view when the error carries a language code, and the run
view prints the message under `Failure`. When a step's error is the run's failure, `Failure` names
that step and the message stays under `Step errors`. A run that failed before its status recorded a
cause shows only `failed`. A failure raised by program code outside any step is recorded in no
journal row. When the status recorded no cause either, the view says so under `Failure`. The hosted
view names `cotal service logs stack-manager --space <space>`. With `--local`, the view points to
the driving process's output if the run was driven locally.
The failure records no line or column in the program: a source position belongs to a problem
`run validate` reports before the program runs.

If an attempt activated and stopped before its first `running` status note, a later resume still
advances past that journal activation. Hosted resume, manager restart and local resume choose the
next epoch and fencing token above both the recorded status and the latest journal activation.
An equal token never admits a different holder.

If a broker outage prevents a hosted run's final status write, the manager retries that write
while the attempt's connection remains open, including when NATS returns before JetStream
can answer. The program does not advance during this repair.
Once JetStream answers, `run` and `run show` report the recorded state. If the outage also
interrupted a journal append, the same manager tries to resume the run after recording the release.
It retries temporary failures for at least 30 minutes after recording the release. After the
first minute it waits at least a minute between attempts. The manager logs the first failure it
will retry and any failure that ends retries. It replays the journal under a new attempt instead
of retrying the interrupted append. A revoked run or a run that another attempt already holds ends
retries immediately. A rate-limit answer is temporary. The manager waits for the `Retry-After` it
carries, and at most one minute when that wait is missing or longer. The wait also ends when the
30 minutes do. An answer that says the request is not implemented ends recovery at once, including
one that arrives while the manager is reading the run. If the manager stops while a retry is still due, its next boot
continues that recovery for the rest of the 30 minutes. Its next boot also takes back runs still
recorded `running`.
The manager scans run records in batches. It checks programs, admissions and journals only for
runs recorded `running`, so finished runs do not each require a separate broker round trip.

A run recorded `released` has no recorded reason. Its `Released` section points to the executing
manager's log for a hosted run or the driving process's output for a locally driven run. A journal
read does not establish that execution host or log location, so the view does not guess one.
A journal entry larger than the broker's configured `max_payload`, such as a large checkpoint
question, can release a run with `L5010 Journal append rejected`. Repeating `resume` while the
cause remains can release it again; this view does not change that state or prevent the retry.

A program's `log(...)` lines are not journalled, so `show` does not print them. A hosted
run writes each line to its manager's log as `run <run-id>: log <text>`, which
`cotal service logs stack-manager --space <space>` reads, and a resumed run writes the lines before
its resume point again. `--local` prints them in the terminal that drives the run.
`--json` on the run list or `show` writes one envelope on stdout, as other commands do, and nothing on
stderr, whether the manager answers or `--local` reads. The list puts its rows under `result.items`.
`show` puts the run under `result.view`: its `runId`, `endpoint`, recorded `spec` and `status`,
its `programHash` as the list row carries it, and its rows under `result.view.journal`. A program
record that cannot be read gives `programUnreadable` with its reason, and no `programHash`. A list row carries `runId`, `endpoint`, `state`, `holder`, `epoch`,
`journalHigh`, `forkedFrom`, `startedAt` and `programHash` (the values the program's `run()`
reports; `programHash` is absent for a run with no recorded program), `failure` on a failed run
with its `code` and `message`, and `revoked` or `revocationUnreadable` when the marker says so. A journal row is an `activation` or a `step`. A
step row carries its `step` key, the `effect` kind and its `name`, `state`, `outcome`, the recorded
`status` and `errorCode` once settled, the recorded `errorMessage` of a failed or refused step,
and `startedAt` and `endedAt` in epoch milliseconds. An open
pause adds its `asks`, its `deadlineAt`, and for a checkpoint its recorded `schema`, the `onExpiry` it was armed with and
the `addressee` its `to` names. A checkpoint's escalation is armed with `proceed`, so it never
escalates again. A settled pause adds its `answer` and its `amendments`, as the text view prints
them. A field the
journal does not record is absent: a checkpoint opened before `onExpiry` was recorded carries none.
An unreadable revocation marker makes the result partial, exit 4, with a `REVOCATION_NOT_CHECKED`
warning naming the run. A `run --endpoint <endpoint>` that matches no run lists nothing and says so,
naming the endpoints runs are recorded under, with an `ENDPOINT_HAS_NO_RUNS` warning. The text view is presentation and is not a stable parsing target. With
`--local`, only the list, `show`, `answer` and `amend` take `--json` or `--plain`. Any other local form
refuses either flag with `USAGE_INVALID`, exit 1. For `start --local` and `resume --local`, remove
the output flag to drive the run locally, or use the suggested manager command, which keeps your
explicit target and output flag. `revoke` and `check` have no other form. For `check`, the retry
keeps the candidate file and explicit target and omits the output flag. If the broker URL cannot
be displayed safely, the refusal asks you to remove the output flag from your original command.
`run --page`, which is not in release 0.88.0 or earlier, asks one manager for a single bounded
diagnostic JSON page instead of the full list:
`--limit` takes 1 to 16 rows (default 8), and `--cursor` continues a scan from a returned
`nextCursor`. It requires `--on` and refuses `--local`, and a page proves neither absence nor
ownership ([Diagnostic inventory](workflows.mdx#diagnostic-inventory)). If the Manager ID is missing or malformed, look it up in the roster for the same space and broker, then retry the original page request with that ID. Keep any cursor and limit unchanged.
`revoke` writes the run's revocation marker from the project folder; `--by` and `--reason` are
required ([workflows](workflows.mdx)).
`answer` resolves an open
checkpoint through the manager, presenting as the holder that armed it; the manager records the
answerer from your credential, so no `--by` is taken there. A settled step refuses a second
`answer` with `TARGET_NOT_FOUND`, also when it is sent before the run records the first, and a
revoked run refuses every answer with `LIFECYCLE_BLOCKED` and files nothing. A step the run holds no
open request at is also `TARGET_NOT_FOUND`; when an open checkpoint or `ask` has the name you typed,
as `frage` names `/checkpoint:frage#0`, the retry uses the full key and keeps your answer, artifact,
target, and output flags. If the broker URL cannot be displayed safely, the refusal asks you to
replace the key in your original command. Several matches are listed for you to pick from.
A run ID that no run is recorded under is `TARGET_NOT_FOUND` too, with or without `--local`.
The refusal says no run is recorded under that ID. Its next step lists
runs with `cotal run`, rather than showing the missing record. For local `answer` and `amend`, the
list command keeps the selected space and any explicit `--server`, `--creds`, `--endpoint`, `--json`,
or `--plain`. If the broker URL cannot be displayed safely, the refusal asks you to reuse the original
target options. Missing-step refusals instead name `cotal run show <runId>`. Hosted follow-ups keep
the selected space and any explicit manager pin. An
answer without `--value` carries no value: the step settles as answered, and the
program's checkpoint result has no `value`. `--value` is refused with `SCHEMA_INVALID` before
anything is sent when the record would not hold what you typed: an object that names a key twice,
a number outside the range JSON carries (such as `1e999`), or a value nested more than 1000 levels
deep. An empty or blank `--artifact` is refused with `USAGE_INVALID`. The text receipts for `answer`
and `amend` show the step, the submitted value or that none was given, any artifact and the answer
ID. They shorten values longer than 120 characters and say when they do.

With `--json`, `result.answer` contains `step`, the full `value` and `artifact` if supplied, and
`valueGiven`, which is false when `value` is absent. The returned answer ID is in
`result.result.answerId`. An amendment also reports the ID of the accepted answer in
`result.result.supersedes`.

`amend` records a changed position on a settled checkpoint or `ask`: it files a new answer beside
the accepted one, and the journal lists it under the step. The pause stays
settled and the run keeps the answer it acted on. A step that is still open or settled without an
answer refuses an amend. So does a run ID that no run is recorded under, and that refusal says no
run is recorded under that ID. With `--local` these refusals are `TARGET_NOT_FOUND`, exit 2, as the
hosted ones are, since nothing was written. The run records an accepted answer a moment after `answer` returns, and an
amend sent in between is refused with a message saying the answer is not recorded yet; amend again
once `run show` lists it. A spawned seat may amend only an answer recorded under its own name.
`check` replays a run's journal against an edited program, from this terminal under a read
credential (`--local` only; the manager serves no run-migrate command). It prints whether the
migration is admissible, every orphaned step with its verdict and code, and exits 0 on admissible
and non-zero on not. An edited program that does not validate is refused before the replay, with
each problem's code, position, cause and fix. It writes nothing: the commit that would file the
migration is not reachable yet, and the report says so. A run ID with no record on the endpoint is refused
`TARGET_NOT_FOUND`, exit 2, as `run show` refuses it. Its next step is `run list --local` on the same
space, broker, credential and endpoint. The list reads the records without a manager.
`check` refuses `--adopt`, `--release` and `--discard-approvals` as `USAGE_INVALID` (exit 1)
before mesh preparation or connection, since they decide what a commit does and the check files nothing.
If you pass `--adopt` or `--release` without a handle, the refusal tells you to remove the flag.
`--timeout` sets the default
limit of a checkpoint, `ask` or turn that sets none of its own (default 1h). A checkpoint that
expires under `onExpiry: "fail"` says in its L4007 whether the deadline came from its own `timeout`
or from this default. It takes a duration
longer than zero, such as `30m`, and refuses anything else with `USAGE_INVALID` before the run starts. `--on <instance>` sends a hosted verb to one manager
instance. It takes the full instance id `ps` prints, not a manager name or host. On a mesh whose managers this terminal can
list, an `--on` that names none of the running ones is refused `TARGET_NOT_FOUND` at once, naming
them, and nothing is sent. On a user-auth mesh where you run more than one
live manager, an unpinned hosted verb is refused and `--on` picks one. `--local` takes no `--on`. `--local` drives in this process instead, over one
connection per invocation under the run's own credential minted from the project folder's trust
material, and is the path on a bare broker with no manager or for a run with no recorded program
(`cotal run resume <runId> --local --file <program>`). If the supplied file differs from the
recorded program, local resume refuses with `CONFLICT` (exit 2) before taking over the run.
Omit `--file` and its value to resume the recorded program. If the run record itself is missing,
`resume --local` refuses with `TARGET_NOT_FOUND`, exits 2 and points to `cotal run list --local`
for the same space and any explicit broker, credential or endpoint. If a local `resume`, `answer` or `amend` has a
malformed run ID, use `cotal run list --local` with the same target options. Then replace only the run
ID in the original command. A hosted `resume` with a missing or malformed ID points to the run list
with the original target options and output format. Add or replace the ID in the original command
without changing its options. For a local `resume` with no run ID, use the local list and add the ID.
`answer --local` and `amend --local` take
`--by <who>` and print the same receipt as the hosted path, and `start --local` requires
`--admit-read` and `--admit-publish` (comma-separated
patterns or `none`), the run's channel ceiling. An omitted option or a list containing only commas
and whitespace is refused as `USAGE_INVALID` before contacting the broker. An entry that is not a
channel or a pattern, such as `a b`, is refused `USAGE_INVALID` naming it. When the run's status
records that its program failed under this drive, `start --local` and `resume --local` fail
`OPERATION_FAILED`, exit 5, naming the run and its language code with that code's title. A failure
whose code has no title shows the first line of its recorded message instead, with control
characters escaped. Their Next is
`cotal run show <runId> --local`, which prints the whole message. Any other error the drive ends on
stays `unknown`, exit 3. On a
user-auth mesh the host's own manager refuses the family by name, and `--local` has no credential
there. A participant's manager started with `cotal supervise` hosts a logged-in user's runs through
its issuing host: the auth callout issues the user's manager connection, and every `run` verb rides
the versioned rail under that issuance.
[User-auth run start](design/user-auth-run-start.md)
records the path. The guide is [workflows](workflows.mdx).


## Workflow command forms [#workflow-command-forms]

`cotal run` (or `cotal r`) lists the authorized workflow records. On an open mesh, both the hosted
and local text lists point to offline simulation because that mesh cannot host runs. If no manager
is running, the hosted text list also points to `cotal run list --local` to read records directly from
the broker. The hosted JSON list exits 0 with `completeness: "not-checked"` and a `TARGET_UNAVAILABLE`
warning that tells you to add `--local`. Its empty `result.items` does not establish that there are no
records. `run show <run-id>` reads
recorded state, open requests, each step's recorded error and the last 20 journal rows. `--limit <n>`
prints the last `n` rows instead, from 1 to 1000, and is refused with `--json`. A settled
`race` row names the branch it took, and a cancelled row in a branch that lost a race names the
branch that won and the race. An answer whose step was in a branch that lost a race, or
whose pause was cancelled after accepting it, is listed as `not acted on`. Its JSON result contains
the full returned status and journal. The JSON and answer commands under `Next` keep `--local` and
any explicit target selectors. The JSON command omits `--limit`, and a local answer requires
`--by <who>`. Answer and amendment receipts keep the same route in their `show` command.
If `run show --local` finds no record for the ID, it points to `cotal run list --local` on the same
target. The local list does not need a manager. The list's `show` command keeps `--local` and any
explicit target selectors so it reads from the same place.
Revoked admission and unreadable revocation markers remain distinct from the record's state.
Neither a record nor a receipt is a live agent-progress report.

```bash
cotal r
cotal r start ./workflow.cotal.js
cotal r show <run-id> --json
cotal r resume <run-id>
cotal r answer <run-id> '<step-key>' --value '<json>'
cotal r amend <run-id> '<step-key>' --value '<json>'
cotal r check <run-id> ./edited.cotal.js
cotal r revoke <run-id> --local --by <actor> --reason '<text>'
```

Start takes a positional source file. A source file a `run` verb cannot read is refused naming
its path and the cause: `TARGET_NOT_FOUND` for a missing file or a link whose target does not exist,
`USAGE_INVALID` for a directory, device, FIFO or socket and `PERMISSION_DENIED` for a file it may not read.
The source must be a regular file or a symlink to one. Pipes are refused even when a writer has
supplied data, including process substitution paths. Save that output in a regular file first.
`-` is a file name there, since `run` does not read a program from standard input. A run verb that reads a source
file refuses an empty one or one that is not valid UTF-8 with `SCHEMA_INVALID`, before it checks or
sends anything, because a run's source must not be empty and its text is never replaced. A file
whose text is only comments or whitespace is not empty as bytes, and validation refuses it with
L1031 because the program has no statements. A lone `;` is an empty statement and is still a program. A hosted
start sends the program to the manager in one message, so a program over the broker's message limit
(`max_payload`) is refused `UNSUPPORTED` with its size and the limit, and nothing is sent. Resume uses the host's recorded program. Hosted answers
and amendments are attributed to the authenticated caller, never a supplied name. On a static-auth mesh that caller is one actor derived from the OS login and host, so hosted run commands from that login and host record the same actor. Each command still mints a fresh short-lived credential and lifecycle. A signed-in user keeps that user's `cli` actor, and a managed seat keeps the seat's name. Local answers and
amendments require `--by <who>`. If the value is missing, empty or whitespace-only, the CLI refuses it with
`USAGE_INVALID` before contacting the broker, with a JSON refusal under `--json`. `check <run-id> <file>`
replays the run's recorded journal
against the edited program and prints whether the migration is admissible, and it files no migration. Revocation keeps
the existing local trust and explicit actor/reason requirements and does not cancel a task.
Hosted start, resume, answer and amend have JSON and plain receipts. The local drive and local
check retain their native output rather than claiming an unsupported structured format.


### Offline commands

```bash
cotal r validate ./workflow.cotal.js
cotal r plan ./workflow.cotal.js
cotal r simulate ./workflow.cotal.js --handler ./results.json
```

These three forms are offline and reject mesh or caller selection. Validation checks the
language and nothing a broker decides, so a valid program over the broker's message limit is still
refused by a hosted `start`. A program that does not validate is refused by all three with every problem listed: its
code, position, cause and fix, as a hosted `start` lists them. `--json` carries them under
`result.problems`. If the JSON cannot be written, the CLI prints the problems on stderr unless the
reader closed the pipe. For a JavaScript syntax error, use the reported position. Its line and column
both start at 1, and the cause describes the error without repeating the position.
A warning leaves the program valid. Text output prints it on stderr with its code, position, cause
and fix. JSON output puts it in the envelope's `warnings` and leaves stderr empty. The warning stays
in the output if the CLI refuses the results script or the simulator fails after validation.
`validate --json` also lists it under `result.warnings`. One is
L3021, a `fanOut` over a list written in the call whose items carry no
`id` and that passes no `key`, which the run refuses when it reaches it. A list held in a variable
gets no warning, because it can change before the call; the run refuses it the same way.
Plan lists validated static call sites in source order with their one-based line numbers. It counts
JavaScript line breaks, including bare CR, the same way validation does. It labels calls through
computed properties `derived call` without evaluating the property. It does not evaluate branches,
loop counts or an execution schedule. Simulation uses the native simulator with a JSON
results script. It executes no JavaScript handler and invents no unscripted outcome. A scripted
checkpoint result needs a `status` of `resolved` or `expired` and may carry `value`, `by` and
`artifact`. An invalid checkpoint result is refused with `SCHEMA_INVALID`. The refusal names the
results file and the entry to correct before rerunning. The simulator stamps `at` from virtual
time, so you cannot script it. A scripted turn result needs a `status` of `done`, `blocked` or
`handoff` and may carry a string `note`. Only `handoff` requires and accepts `to`. Use an agent
handle such as `{ "agent": "sim.reviewer", "persona": "reviewer" }` instead of an agent name.
Invalid turn results are refused before simulation with `SCHEMA_INVALID`. This includes an invalid
status, a non-string note, an unknown field, a scripted `at`, and a missing, malformed or
unexpected destination. The refusal names the results file and the field or result to correct
before rerunning. For a list entry the path includes the array index.

A missing script entry or an exhausted list raises L6001. If it goes uncaught, the error names the
table and step, suggests what to add, and prints a retry command with shell-quoted paths where needed.
The retry command keeps `--json` or `--plain` when you pass either flag.
For an exhausted list it names the needed result, counted
from 1, while the step key counts occurrences from 0. JSON includes `target.step` if a failed
journal entry matches the error code. That can be a different step from the one in the message,
for example when parallel branches both raise L6001.

If L6001 or a statement such as `throw "boom"` goes uncaught, the simulator produces no report.
The CLI exits 5 with `OPERATION_FAILED`. Its JSON envelope has `outcome: "failed"` and
`result: null`.

A simulation that returns a report exits 0 with envelope `outcome: "ok"`. This includes reports of
program faults with language error codes L3xxx or L4xxx, such as L4007 when a checkpoint expires
under the default `onExpiry: "fail"`. Those reports have `result.outcome: "failed"`.
A simulation does not establish live authority, installed applications or readiness. All three
offline commands support JSON and plain output and contact no broker.

The `--handler` file is one JSON object in UTF-8, with an optional leading byte-order mark.
It must be a regular file or a symlink to one, as the program file must be.
A missing file or dangling link is refused with `TARGET_NOT_FOUND`, and an unreadable file with
`PERMISSION_DENIED`, exit 2. A directory, device, FIFO or socket is refused with `USAGE_INVALID`,
exit 1. An empty file, invalid JSON, or a top-level value other than an object is refused with `SCHEMA_INVALID`, exit 1.
These refusals name the path, the cause and a next step. An unknown top-level key is also refused
with `SCHEMA_INVALID`, exit 1. The refusal names the file and suggests a replacement, such as
`turns` for `turn`, or lists the supported keys. A file that is not valid UTF-8 is refused
with `SCHEMA_INVALID`, exit 1, before simulation, naming the path and how to save it as UTF-8.
No invalid bytes are replaced. A repeated key is refused with `SCHEMA_INVALID`, exit 1. Use an array
under one key to give that step multiple sequential results. Each results table is an object keyed
by step name, with one value for every occurrence or an array used in order. If a table is not an
object, the refusal names the results file and the expected shape. A step with no name is keyed by its effect, such as
`ask`. `spawn`, `sleep`, `notify`, `monitor`, `observe` and conclaves need no entry, and a sleep
moves the virtual clock forward.

Use this results file with the [example program](workflows.mdx#a-first-program). The blocked builder
prompts an `unblock` turn, and the unnamed wait reads the `wait` entry.

```json
{
  "checkpoints": { "approve-plan": { "status": "resolved", "value": true, "by": "ana" } },
  "asks": { "plan": { "steps": ["design", "build"] } },
  "turns": { "build": { "status": "blocked", "note": "needs a key" }, "unblock": { "status": "done" } },
  "events": { "wait": null }
}
```

| Field | Meaning |
|---|---|
| `turns` | `turn` results: `{status, to, note}`, where `status` is `done`, `blocked` or `handoff`. Only `handoff` requires and accepts `to`. |
| `asks` | `ask` replies, each checked against the step's `schema` |
| `checkpoints` | `checkpoint` results: `{status, value, by, artifact}`, where `status` is `resolved` or `expired` |
| `events` | `wait` results. `null` is a timeout |
| `clock` | `{start, turn, ask, checkpoint, wait}`: `start` is a safe integer in milliseconds, between -9007199254740991 and 9007199254740991, so the virtual clock can advance by whole milliseconds. Effect durations take values such as `"5m"`. A turn takes 5 minutes and the others 1 minute unless set |
| `faults` | `[{at, kind, code, message}]`: the step at `at`, a step key such as `turn:build#1`, fails with that error |

An invalid clock value is refused with `SCHEMA_INVALID`, exit 1. The refusal names the field and
results file and tells you how to correct the value before rerunning the simulation.

To fail a race or a parallel step before any branch runs in `run simulate`, target its own step key,
such as `/race:first#0` or `/parallel:batch#0`. To fail an effect inside a branch, use that effect's
step key instead.

An invalid clock duration is refused before simulation with `SCHEMA_INVALID`, exit 1, even if the
program does not reach that effect. The refusal names the results file and the field to correct.

If the `clock.wait` delay is longer than the step's `timeout`, the simulated wait returns `null`
and advances virtual time only to that timeout.

A simulated `turn` or `ask` rejects a reply that arrives at or after the step's `deadline`.
All `ask` attempts share one deadline, and `clock.ask` is the delay for each attempt. When the
deadline expires, virtual time advances only to that deadline. The step fails with `L4003` for
`turn` or `L4006` for `ask`.

A checkpoint scripted as `expired` expires at the step's `timeout`, as a live deadline does. A
resolved checkpoint, or an expired one without a `timeout`, takes the `clock.checkpoint` delay.

When the simulation returns a report, `cotal run simulate <file> --json` puts these fields in the
`result` object:

| Field | Meaning |
|---|---|
| `result.kind` | `workflow-simulation`. |
| `result.outcome` | The program's outcome, `completed` or `failed`, inside the CLI's `ok` envelope. |
| `result.failure` | `null` when the program succeeds. Otherwise contains `code`, `title`, `cause`, `fix` and the journal diagnostics `step`, `stepOutcome` and `after`. Unavailable details are `null`. |
| `result.steps` | The number of interpreter steps charged against the step budget, including work that does not call an effect. `null` if the program fails. |
| `result.elapsedMs` | Milliseconds advanced on the virtual clock since `clock.start` (default `0`). |
| `result.effects` | Simulation journal entries with `step` (the step key), `kind`, `name` (empty if unnamed) and `status` (the journal state if no status was recorded). An effect inside `once` can also carry `atMostOnce: true`. |
| `result.agents` | Simulated `spawn` requests with `persona` and channel names in `joins`, plus `worktree`, `role` and `permits` if supplied. No agents were launched. |
| `result.waits` | One entry per reached `waitUntil` that starts polling, with `step`, `name`, polling interval `every` and duration `deadline`. Channel `wait` calls appear in `result.effects`. |
| `result.checkpoints` | One row per checkpoint request sent to the simulator, with `step`, `name`, `prompt` and any `timeout`, `onExpiry` and `to` from the request. An escalation adds a second row with the same step key and `onExpiry: "proceed"`. |
| `result.unusedScript` | Keys from `turns`, `asks`, `checkpoints` and `events` that were never selected during result lookup, in `table.name` form (for example, `checkpoints.approve-plan`). A matching list counts as used even when empty or exhausted. A fault injected before lookup does not use the key. A fault that was never injected is listed as `faults.<at>` (for example, `faults./sleep:typo#0`); the simulation still completes, since the fault may target a branch this run did not take. |
| `result.log` | `log(...)` calls in order, each with `scope` and `values`. In plain output these appear under `Log`. |

In `result.failure`, `step` and `stepOutcome` describe the last failed entry in journal order with
the same error code. If there is no match and the code is L4007, they describe the last settled entry
if it is an expired checkpoint. These are journal matches, so they may not identify the source of
the uncaught error. When no step matches, `after` names the last settled entry in journal order, if
there is one.

`result.elapsedMs` does not measure how long the CLI process ran. For example, `await sleep("1h")`
advances virtual time by `3600000` milliseconds without waiting an hour in real time.


### Seat turns

Inside a manager-launched static or open seat, `run turns` reads that seat's assigned turns and
`run yield <turn-id> --status <done|blocked|handoff>` reports an outcome. Handoff also requires
`--to <agent>`; `--note <text>` carries context. If the turn ID is missing, the refusal points to
`cotal run turns` and shows the status and handoff flags. The native launcher supplies the caller context.
These forms use the launcher's seat identity and manager and reject `--creds` with `USAGE_INVALID`
(exit 1). They refuse user-auth self impersonation and skip operator catalog and installation repair.
Yielding one turn does not complete the entire workflow.
