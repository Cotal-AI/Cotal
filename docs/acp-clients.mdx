An [Agent Client Protocol](https://agentclientprotocol.com) (ACP) client can spawn and drive Cotal agents.
T3 Code, Zed, JetBrains IDEs and Neovim are ACP clients.
In the client, each thread is one Cotal agent. Its first prompt spawns the agent through your space's manager, in the thread's folder.
The agent belongs to the manager, so it keeps running on the mesh when the client closes.

## Install the extension [#install]

The `cotal acp` command comes from the optional `@cotal-ai/acp` extension.
`cotal setup` adds it when it finds T3 Code or Zed on this computer.
To add it yourself, run this on the machine where the client runs its agents:

```bash
cotal ext add @cotal-ai/acp
```

The agent needs a [running mesh](run-a-mesh.mdx).
It finds the space the way other commands do, from the folder the client starts it in.
A client may start it anywhere, so pin the space with `--space`.
When none of the managers a new thread may use runs on this machine, as when none may start its agent or only another computer's is live, `cotal acp` starts this machine's manager for the space with `cotal manager start --idle-exit 600` before the thread offers anything, and the thread says so in one line.
Threads that open at the same time share one start, and the later ones say the manager is running.
That manager stops itself once it has held no agents for 10 minutes, so nothing runs while you use no agents.
It runs on its own, so closing the thread, or the app that runs `cotal acp`, does not stop it ([background services](cli-processes.mdx#direct-process-lifecycle)).
Its seats get a provider key or harness folder from the environment `cotal acp` runs in only when [`spawn.env`](config.mdx#launcher-variables) lists it.
Until then, a bare `cotal down` for the space refuses and names the command that stops that manager first.
A thread's first prompt checks again when its Machine is this machine's, so a thread left open past that time starts the manager again.
When no manager is registered for the space, as after that manager stopped itself, listing threads, loading or deleting one, and `/open` fail with a message that says so and that a new thread starts this machine's manager. None of them starts a manager.
If the start fails, the new thread fails with the start's reason. It also fails when the start succeeds but the space does not list a manager on this machine yet; open the thread again.
A manager runs on this machine when it names this machine's id, the `machine` field of its status and presence (see [Control discovery](control-discovery.mdx#status-metadata-and-launch-availability)). The host name decides nothing, because macOS changes it when the network changes. A manager that names no machine, such as one from a release before this field, counts as another computer's. When `cotal acp` cannot read this machine's own id, as in a container with no `/etc/machine-id`, no manager counts as this machine's, so a thread neither defaults to one nor starts one. A new thread offers the listed managers in the Machine option, a prompt with none chosen fails and says why, and a manager the thread names runs its agent as before. With none listed, the new thread fails and says why.

## Add Cotal to the client [#add-to-a-client]

`cotal setup` adds Cotal to T3 Code and Zed when it finds them on this computer, one entry per space.
It finds T3 Code from a `t3` command or its `~/.t3` folder (`T3CODE_HOME` when set), and Zed from a `zed` or `zeditor` command or its settings folder.
Run setup once for each space you want in the client.

Each entry runs this computer's `cotal acp --space <name>` by absolute path, because an app started from the desktop often does not see the folders your shell adds to `PATH`.
The paths are ones that survive an upgrade: under the get.cotal.ai launcher the entry runs the launcher's own Node link, not the folder of one Node version such as Homebrew's `Cellar/node/<version>`, and it runs the install's entry, not one update's copy.
When `COTAL_HOME` or `XDG_CONFIG_HOME` is set, the entry passes it on.
A new entry is named `Cotal (<name>)`.
An entry that already runs `cotal acp` for the space, such as one you added by hand, is updated in place.
In T3 Code, setup uses a different provider ID if another provider already has the ID Cotal would use.
Setup keeps your other settings, and in Zed it keeps your comments.
Before it changes a settings file, it copies it next to the original as `settings.json.cotal-backup-<time>`.
Both apps load the change without a restart.
When a settings file cannot be read or written, setup says which one and why, saves the rest, and reports the run as partial.

`cotal update` points every Cotal entry at the Cotal it installed, for example after Cotal moved to another folder.
`cotal status` lists the spaces each client reaches, and shows an entry whose command is gone.

To add an entry by hand, give the absolute path of `cotal` (`command -v cotal` prints it) and `acp --space <name>` as its arguments.
In T3 Code, add a provider instance with a local ACP command to T3's `settings.json`.
Its settings page shows the command but not its arguments:

```json
{
  "providerInstances": {
    "cotal-<name>": {
      "driver": "acpRegistry",
      "displayName": "Cotal (<name>)",
      "enabled": true,
      "config": { "source": "local", "commandPath": "/home/you/.local/bin/cotal", "commandArgs": ["acp", "--space", "<name>"] }
    }
  }
}
```

In Zed, add it under `agent_servers` in your settings:

```json
{
  "agent_servers": {
    "Cotal (<name>)": { "type": "custom", "command": "/home/you/.local/bin/cotal", "args": ["acp", "--space", "<name>"] }
  }
}
```

## Start it with npx [#npx]

A client that installs agents as npm packages starts Cotal with `npx @cotal-ai/acp`.
That command keeps nothing of its own. It finds the `cotal` installed on this computer, on `PATH`, in `~/.local/bin` or in npm's global folder, and runs its `cotal acp` with the same arguments.
Your spaces, sign-in and agents stay the ones that `cotal` already uses.

When this computer has no Cotal, or a Cotal without the ACP extension, the agent offers only **Sign in to Cotal**.
That sign-in runs in a terminal. It installs Cotal with `curl -fsSL https://get.cotal.ai | sh` (`npm install -g cotal-ai` on Windows) or adds the extension, then signs in to a space or sets one up.

## How threads map to agents [#threads]

| In the client | On the mesh |
| --- | --- |
| A new thread | Nothing yet. A thread that is opened and dropped leaves no agent. |
| The thread's first prompt | Spawns an agent in the thread's folder, with that prompt as its first task. The agent's name is the thread's id, or the name you gave it with `/name`. The turn ends when that first task's run ends. |
| A later prompt | Reaches the agent as your own words: through the agent's `turn` where its presence says it takes one now, else typed into its terminal through its manager. The thread picks the path from the agent's presence before it sends the prompt, and a path that fails is reported, not retried another way. The turn ends once the agent has started working and stopped again. |
| Listing sessions | The managed agents in that folder, including ones you spawned elsewhere. An agent a thread spawned or opened is listed as that thread. |
| Importing a session | Shows what the agent's event channel still holds, then follows it live. |
| Deleting a session | Hides that agent run from the list. The agent keeps running. |

A later prompt sent as a `turn` joins the agent's queue, as one of the agent's own commands does. While the agent finishes earlier work, the prompt waits there and its turn stays open, however long that takes. The turn shows only the agent's run for that prompt.
If the agent does not start working on a later prompt within 30 seconds of taking it, or of having it typed in, the turn ends with a note saying so.
The agent still has the prompt, and answers it when it gets to it.

A turn shows the agent's messages, its reasoning when the application publishes it, and its tool calls.
A tool call shows its arguments and its result, and a file edit shows as a diff.
They come from the agent's payload rail ([SPEC 13.19](../SPEC.md#1319-private-tool-results)), so a call shows by name and status until its payload arrives, and a result over the rail's size limit is replaced by a note.
Importing a session and `/open` replay the rail's history too. When it cannot be read, they fail and say that the agent's earlier tool inputs and results cannot be read, and why.
A to-do list the agent keeps, such as Claude Code's tasks, Codex's plan, or the to-do lists of OpenCode, Jcode and Hermes, shows as the thread's plan.
On current models Claude Code keeps tasks only when the operator opts in ([Claude connector](claude-connector-reference.mdx#event-plane)).
The thread knows the file and shell tools of Claude Code, Pi, Codex, OpenCode, Jcode and Hermes. Any other tool shows by name, with its arguments and result as the agent sent them.

The thread also uses the agent's `agent` endpoint ([SPEC 13.22](../SPEC.md#1322-the-agent-endpoint)), on every space.
On a static space the bridge calls it through a connection that holds only the calls an owner makes to their agents, minted from the space's signing key on this machine.
On an open mesh nothing checks who calls, so any program that reaches the broker can answer an agent's questions or run its commands.

- A question the agent stops to ask, such as a tool permission, shows as a permission request in the client, which may answer it from the thread's mode. A question with a form is shown as a form when the client takes forms. The answer goes back to the agent. An option that needs a written note is not offered; answer it at the agent's terminal. A client takes a question only during a prompt, so one the agent asks while the thread runs none, as when it works on a message from another agent, shows when you next send a prompt in the thread. Answer it there or at the agent's terminal. A prompt stays open while a question it shows is unanswered.
- An agent the thread spawns asks before it uses a tool where its application can, so those permission requests reach the thread. It also publishes its reasoning where its application can. The thread asks for both only where the manager reports that the application takes them, and a manager that refuses fails the first prompt with its reason.
- The agent's own commands and skills join the command list. A skill is listed with a leading `$`. Sending one runs it through the agent's `command`.
- A prompt can carry images (PNG, JPEG, GIF or WebP) when the agent's presence says it takes them with a turn. Otherwise the prompt fails before anything is sent. A first prompt with images starts the agent with no task, waits up to 20 seconds until it takes a turn, and then gives it the prompt.
- After each turn, the client's context meter shows how full the agent's context window is, when the agent's presence says it reports its usage. The usage arrives before the prompt answers, unless the agent takes more than 3 seconds to report it.

## Choose the agent [#options]

A new thread offers these options next to the model list. They apply when the first prompt spawns the agent.

| Option | What it sets |
| --- | --- |
| Model | The application and model, as `<application>/<model>`. Each name starts with its application, so the list picks the application in clients that do not show groups, such as T3 Code. `<application>/default` leaves the model to the application. A model id the list does not show is passed to the manager as given. |
| Harness | The application the agent runs, when more than one can. Choosing a model moves it to that model's application, and choosing another harness starts that application on its default model. |
| Reasoning | The model's variant. Offered while any listed model has variants; for a model without them it holds only the model default. |
| Persona | A persona from the manager's catalog. A catalog of 64 or more personas offers a short list: the default, the current choice, and up to 16 personas you own. `/persona` picks any other. |
| Channel | One channel the new agent joins. A space with 64 or more channels offers a short list: no channel, the current choice, and up to 16 channels, those the space describes first, each group with the most retained messages first. `/join` picks any other. |
| Machine | Which manager spawns the agent. The default is your live manager on this machine. Another computer's manager is never the default, because it cannot use this machine's folder. A listed manager whose rail the broker reports empty, as when its computer is gone or it died without deregistering, is not offered. With none of yours live on this machine, a new thread starts this machine's manager first, as above, so another computer is used only when you choose it here. The list is offered when there is more than one manager, or when none of them runs on this machine. On a space where people sign in, the list comes from the space's auth service: the space's own manager while you have registered none, and each of your registered managers it lists as a candidate once you have. A candidate can be one whose computer is gone. With none of yours live, a new thread starts this machine's manager, which registers it on its first start, as a manual `cotal manager start` does. Every call a thread makes names its manager, so a space host that sends unnamed calls to its own manager (`local-primary`, see [Embedding a manager](embedding-manager.mdx)) does not change the list. A thread keeps the manager it started on. When a thread you load offers this list, its agent's manager is in it and is the current choice, so a new agent the thread starts after `/despawn` starts there unless you choose another. |

Only applications that publish an event plane are offered, because the thread is built from it (see [Connectors](connectors.mdx)).
Any other select that would hold 64 or more choices is not offered.
The session's model list also gives each model its reasoning choices, so a client that reads them, such as T3 Code, shows a model's reasoning choices before any thread has run it.

## Slash commands [#slash-commands]

| Command | What it does |
| --- | --- |
| `/name <new name>` | Before the first prompt, sets the name the agent starts with. On a running agent, changes the name it shows on the mesh. Its manager still lists it by the name it started with. |
| `/open <name>` | In a thread with no agent, drives an agent that is already running, found by its name or the name it shows. The thread shows what the agent's event channel still holds, then follows it live. When you load the thread again, it opens that agent. |
| `/despawn` | Send it by itself to stop the thread's agent. The thread stays, and its next prompt spawns a new agent when your grant may spawn agents (see [Sign in](#sign-in)). |
| `/roster` | Lists who is on the mesh and what each is doing. |
| `/channels` | Lists the space's channels. |
| `/persona <name>` | Sets the Persona option to any persona in the manager's catalog, by its exact name. Offered when the Persona option shows a short list. |
| `/join <channel>` | Sets the Channel option to any channel of the space, by its exact name. Offered when the Channel option shows a short list. |

`/persona` and `/join` are offered only while the thread has no agent, because the choices apply when the agent starts. While an agent runs, the thread does not take them, so the agent's own command of that name reaches it. A name the list does not hold fails with one line, and the choice stays.

## Sign in [#sign-in]

For a space that authenticates users, a client that can run a terminal offers **Sign in to Cotal**. Open and static-auth spaces do not offer it.
It runs `cotal acp --auth`, which signs in to a space that authenticates users with `cotal login`.
When no space is recorded, the client offers the same action to run `cotal setup` instead.

On a space where people sign in, your own sign-in is enough. Whatever your scope, it lists and
loads your agents, types into them, stops their turns, reads their event channels and despawns them.
Starting a thread also needs a grant that may spawn agents. Without one, a thread you load offers
only the agent's own model, and once you despawn that agent the thread cannot start another. You need no `admin` scope, because a
person controls every agent under their own owner (see
[Delegation](identity-user-auth.mdx#delegation)).

## Limits [#limits]

- Stopping a turn takes one path, picked from the agent's presence when you stop it: the agent's own `interrupt` where its presence says it serves it now, else the interrupt key through its manager, which Claude Code and Pi agents support. A Claude Code agent serves `interrupt` only while its command mod runs. When that path fails, the thread says the agent could not be stopped, the turn ends as cancelled, and the agent keeps working on the mesh. A prompt still waiting in the agent's queue is taken out of the queue instead, so it never runs, and the agent's earlier work goes on.
- When you stop a Claude Code turn before the agent answered, Claude puts that prompt back in its input box. Your next prompt is typed after it, so the agent gets both.
- A later prompt that is typed into the agent's terminal is typed as if you typed it into the application, so the application's input shortcuts apply. In Claude Code, a prompt that starts with `!` runs as a shell command and its turn does not show in the thread.
- A later prompt typed through the manager ends when the agent stops working. When the agent was already busy as the prompt arrived, the turn can end when that earlier work does.
- A later prompt typed through the manager needs an agent on the built-in `pty` runtime. An agent on tmux, cmux, Orca or Herdr refuses it, and so does a Claude Code agent showing a selection menu. The turn then fails with the manager's reason. An agent that takes a `turn` has no such limit.
- Images need the `agent` endpoint and a harness that takes them. Otherwise the prompt fails and says why.
- Work an agent does between your prompts, such as answering a peer, does not show live in T3 Code.
- An agent on another machine's manager shows its conversation and tool calls, but T3 Code shows no diffs or checkpoints for it.
- An agent on another machine's manager starts in the thread's folder, so that folder must exist on that machine. Otherwise the spawn is refused.
- On a space where people sign in, the thread list shows your agents on every live manager the space's auth service lists for you, the space's own included. You can load them even while none of your managers may start a new thread.
- A manager that does not answer leaves its agents out of the list until it answers again. While it does not answer, loading or deleting any thread the list does not show fails, because its agent may run there. On a space where people do not sign in, a registered manager whose host is gone is not waited for. Where they do, it is waited for like one that does not answer, until you remove it with `cotal endpoint deregister manager <id> --space <space> --yes`, which needs the `supervise` scope. The error names that command when one of your own registrations does not answer a read. The space's own manager is not yours to remove; ask the space's operator. A manager that died less than a minute ago can still look current, and then a new thread fails reading its lists. Try again once its presence lapses, or remove the registration. A sleeping laptop's manager is not gone, so it holds those loads up until the laptop wakes.
- Every manager read and command opens its own connection. A list opens one for each manager it reads, a new or loaded thread opens about three more, and each prompt, cancel or `/despawn` opens one. A space limits how many connections one sign-in opens a minute (60 by default), and your other `cotal` commands count too. Opening many threads at once can be refused, and the refusal names the limit. The allowance refills through the minute, so a retry a few seconds later can pass.
- When your sign-in is granted again, or this machine signs in as another account, while `cotal acp` runs, it stops and says why. It sends nothing as the new sign-in. Start the agent again in your client.
- `/open` finds the agents the thread list would show. If another thread in the same client drives that agent, the agent moves to the new thread.
- A rollback in T3 Code starts a fresh session, which spawns a new agent.
- An agent whose credential holds no rows for the `agent` endpoint, such as one an older release started on a static space, answers none of its calls: its questions stay at its terminal, its commands are not listed, and `/name` fails. Despawn it and start it again.
- The client's own MCP servers are not passed to the agent.

## cotal acp [#acp]

```
cotal acp [--space <name>] [--server <url>]
cotal acp --auth [--space <name>]
```

Serves the ACP agent on standard input and output. Standard output carries the protocol only.
Logs go to standard error.

| Flag | Meaning |
| --- | --- |
| `--space <name>` | The space the agent works in. |
| `--server <url>` | The broker address. An explicit address overrides the address recorded for the space. |
| `--auth` | Sign in to the space, or set one up, then exit. |

Deleted sessions are kept as agent runs in `acp/hidden-runs` under the Cotal home, one per line.
The link from each thread to the agent run it spawned or opened is kept in `acp/threads`, one per line.
