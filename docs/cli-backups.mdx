Backup artifacts transfer message and registry state from a stopped, preserved space.
Restore requires the same space and existing trust. It does not create replacement authentication.


## Commands [#backups]

```bash
cotal down --preserve-state [--store-dir <dir>]
cotal backup create <dir> [--only full|registry] [--store-dir <dir>] [--json|--plain]
cotal backup inspect <dir> [--json|--plain]
cotal backup verify <dir> [--json|--plain]
cotal backup recover <full-attempt-id> [--yes|--dry-run] [--json|--plain]
cotal backup cleanup-fallback <full-attempt-id> [--yes|--dry-run] [--discard-history] [--json|--plain]
cotal backup restore <dir> [--only registry] [--store-dir <dir>] [--accept-missing-source] [--json|--plain]
cotal up --restore <dir> [--restore-only registry] [--accept-missing-source]
```

When you name a backup subcommand, its JSON `command` field identifies that operation, such as
`backup inspect` or `backup verify`, on success and on refusal.

On a controller root, one with a stack journal, `backup create`, `backup restore` and
`up --restore` refuse `UNSUPPORTED` (exit 2) in this release. Each needs a preserved cut, and
`down --preserve-state` cannot make one there. They refuse while validating their arguments,
before the connector seed or any write. Plain `down` and `up` keep a controller stack's store,
channels and history. On a full store `down` refuses first, and [down](cli-shutdown.mdx#down) says how to stop the
stack there with or without purging that history. Backup and restore of a controller-owned stack
return in a later release. The
rest of this section applies to a root without a stack journal.

Backup is offline-only. It requires the stable `ready` record from `down --preserve-state`, an exact
store match (`--store-dir` defaults to the cut's recorded source store), no recorded process that may still be running (the same test `clean` uses), and an
unreachable exact endpoint from the recorded cut. That endpoint is probed immediately before cloning, so a live broker with a missing or stale pidfile
is still refused. `backup restore`, `up --restore` and a bare `up` that resumes the cut probe the
broker address they will bind before they move or start anything. While another process listens
there they refuse `CONFLICT` (exit 2), name the address and leave the cut unchanged. It claims the cut, reflink/copies the stopped source to a
private attempt clone, and opens only that clone on a random loopback bootstrap broker with an
independent parent/deadline watchdog. A bootstrap broker that does not accept connections within
15 seconds fails the command. Each maintenance-login reload waits for the broker's acknowledgement
for up to 15 seconds, bounded by the operation deadline. On Windows, the CLI requests the reload
through a dedicated login on the isolated broker that cannot access the backup data. A rejection,
broker exit or missing acknowledgement fails the command before the next phase receives its login.
Creation returns one JSON/plain receipt after cleanup.
A published artifact plus incomplete cleanup is partial and retains the artifact and original
attempt; it is not a reason to repeat creation blindly. It validates the canonical stream and pull-consumer inventory,
writes native snapshots with consumers excluded, and stores conservative contiguous ACK-floor
checkpoints separately. The presence bucket is memory-backed, so it does not survive the cut and
the clone may lack it. Every other stream must be present. The original store is never opened by
the backup broker, and the stack is not restarted implicitly. Artifact destinations must not overlap
the preserved source or maintenance attempt tree. A restore target cannot overlap the artifact or
the maintenance attempt tree. It can overlap the preserved source only by replacing it at the same path.

`backup create` checks its preconditions before it claims the cut or creates any maintenance state.
If it receives an option it does not accept, such as `--yes`, it names the option and asks you to remove it.
A root with no preserved cut refuses. If the root is prepared for its first controller start,
the refusal points to `cotal space show` and explains that starting it does not make preservation
or backup available. On a legacy root, a plain `cotal down` records no cut, and `down --preserve-state`
only cuts a running stack. The refusal says to start the stack with `cotal up`, stop it with
`cotal down --preserve-state`, then create the backup. A cut in another state
refuses and names that state and its space. A create during a restore that still runs refuses
`LIFECYCLE_BLOCKED` (exit 2), names that restore attempt, its process and when it started, and says
to wait for it. A create that finds the root's maintenance lock held, such as by another
`backup create`, names the operation that holds it, its pid and since when it has held the lock.
Neither refusal journaled anything, so it names no attempt of its own. A destination that already exists is a `CONFLICT`
refusal, because create writes only a new directory. If an otherwise eligible destination's parent
does not exist, create refuses `TARGET_NOT_FOUND` (exit 2) and names that parent. Create makes only
the artifact's own folder. If a link on the way to that parent has no target, the refusal names the
link. Repair the linked folder or choose a destination in an existing directory.
A destination check that finds a non-directory parent (`ENOTDIR`) or a
symbolic-link loop (`ELOOP`) refuses `USAGE_INVALID` (exit 1), naming the destination and its parent. Choose a destination
with a directory parent; no attempt was started and the preservation journal is unchanged.
A destination that overlaps the maintenance attempt directory refuses `USAGE_INVALID` (exit 1),
even when its parent does not yet exist. Choose a destination outside that directory. The same refusal covers the maintenance journal
directory `.cotal/maintenance/v1`, the lock path `.cotal/maintenance/lock.json`, and the lock
recovery path `.cotal/maintenance/lock-reaper.json`, including a destination that is either lock
path. A backup stored directly under `.cotal/maintenance`, beside those paths, is still accepted.
The refusal does not start a backup or change a ready cut.
A destination inside the preserved store refuses `USAGE_INVALID` (exit 1). So does one
inside a path `clean all` removes, such as `.cotal/auth` or the space's `.cotal/space.<hex>`
folder, because that cleanup would remove the backup with them. For either refusal, choose another
location even if the destination's parent does not exist. If this account cannot write or
search the destination's parent folder, create refuses `PERMISSION_DENIED` (exit 2) and names
that folder without changing the preserved cut. Next suggests `chmod u+w` for missing write
access or `chmod u+x` for missing search access on the parent, with a shell-quoted path when it can
display one unchanged. You can also choose a folder this account can write and search.
A `--store-dir` that is not the cut's preserved store, such as an empty folder,
refuses `CONFLICT` (exit 2) and names both stores. A process that listens at the cut's recorded
address refuses `CONFLICT` (exit 2), as `backup restore` and a resuming `up` refuse it, and its Next
says to stop the process that listens there and run the same `backup create` again. Retry commands
quote the destination and any `--store-dir` path for POSIX shells, or for PowerShell and `cmd.exe`
on Windows, when both paths can be displayed and copied unchanged. Otherwise, Next asks you to
rerun your original command. Run either from the same project folder. Any other refusal or failure
shows the check's own sentence as its native detail.
A failure that removed what it wrote leaves the preserved cut ready, and its Next names the same
`backup create` to run again once that cause is fixed.
A create that runs out of disk space (`ENOSPC`) or quota (`EDQUOT`) after it claims the cut removes
what it wrote and fails `OPERATION_FAILED` (exit 5). Its message names the error and where it was
writing: the store copy under `.cotal/maintenance/attempts`, or the backup in its destination. It
also says that no backup was published and that the preserved cut is still ready. Its Next asks
you to free space on the disk named in the error and retry the same `backup create`.

A `backup create` interrupted by SIGINT, SIGTERM or SIGHUP after it claims the cut exits 130, 143
or 129 and names its attempt, the partial artifact it left and `cotal backup recover <attempt> --yes`.
That claim follows the restore claim's rule below: it holds the cut until its backup process and
brokers are proven gone, or for 30 minutes when they cannot be. Until then `up`, another create and
`backup recover` refuse `LIFECYCLE_BLOCKED` and name the backup process and the deadline, and
`cotal status` names the attempt and its next step. While a create or pre-commit restore holds
the cut, its Next section leads with recovery instead of offering a restart that would refuse.
The JSON report leads its hints with the same step. Once it is stale, `backup recover` removes the
partial artifact, the clone and the broker files, each matched by inode, and a create to another
directory does the same before it starts, then backs up the cut's recorded store, a custom
`--store-dir` one included. A create naming the partial artifact refuses `CONFLICT`
and names that recovery. The release's receipt names `cotal backup create <directory>` and
`cotal up` as its next steps.


## Artifact inspection

`backup inspect` reads the bounded manifest and exact declared file-name inventory, and refuses a
declared file that is not a regular file. It does not hash snapshot or checkpoint contents.
`backup verify` additionally reads each named regular file and compares its size and SHA-256. Both
are read-only: no staging directory, broker, restore or secret upload. A path through a linked
folder is read at its real path, as `backup restore` reads it, and the report names that path.
Reports omit snapshot bytes, configuration bodies and trust material. JSON retains
the declared metadata; terminal file lists are bounded and state their omissions.

If the operating system denies opening a declared file for reading, `backup verify`, `backup restore`
and `up --restore` refuse `PERMISSION_DENIED` (exit 2), name the file, and ask you to restore read
access and retry or use a readable copy. Where JSON output is available, its target names the file
in `file` and reports `unreadable` in `fault`. If the operating system denies read access to
`manifest.json` itself, these commands and `backup inspect` refuse `PERMISSION_DENIED` (exit 2)
and name the manifest path.

When a declared file is missing, an undeclared file is present, a declared file is not regular,
or a file does not match its declared size and SHA-256, the refusal names that file and its JSON
target carries `file` and `fault`. A declared name that is not a plain file name in the folder,
such as one with `../` or an absolute path, has the fault `invalid-name` and is not printed.
A `manifest.json` that is not a regular file, is larger than 1 MiB or is not a valid manifest
has the fault `manifest-not-regular`, `manifest-too-large` or
`manifest-invalid`. `backup restore` and `up --restore` refuse these schema and integrity faults
with `SCHEMA_INVALID` and the same file and fault as `backup verify`.
For a ready cut, these permission, schema and integrity refusals do not claim or move the
preserved store. Restore removes any partial stage it made. If restore finds a stale earlier
attempt, it can roll that attempt back before checking the artifact contents. This can move the
preserved store back to its original path and update the journal even if the artifact is refused.
A directory with no `manifest.json` that holds files a `backup create` writes is refused as an
incomplete artifact with the fault `manifest-missing`. The refusal names the real directory even
when the supplied path is a symbolic link. The refusal names `backup recover` only when the current
root's interrupted create still owns the directory at its recorded destination. The recorded path
can pass through a linked parent, but its final component must be that directory. Otherwise, verify
another intact copy or create a new backup from a stopped preserved cut.
A file, or a directory that holds neither a manifest nor such a file, is not a backup artifact and
refuses `TARGET_NOT_FOUND` (exit 2), naming it and saying whether it is a file, an empty folder or
a folder with other files. The folder of a create in this root that was
interrupted before it wrote a file is still an incomplete artifact. A path that names nothing refuses
`TARGET_NOT_FOUND` (exit 2) and says in `missing` whether its folder or the artifact is missing, as
`backup restore` does. If this account cannot search the path to the artifact, these commands refuse
`PERMISSION_DENIED` (exit 2) before reading the artifact or staging a restore. Grant search access on
the folder that blocks traversal, or use an accessible copy. `backup inspect`, `backup verify`,
`backup restore` and `up --restore` need both read and search access on the artifact folder itself.
If either is denied, they report `PERMISSION_DENIED`, name the folder and leave the backup unchanged. A path through a symbolic-link loop
refuses `USAGE_INVALID` (exit 1) before the artifact is read or a restore attempt is staged. Fix the
link or use a path that avoids it.
A full artifact of an authenticated space
restores only into a root that still holds the trust state it was taken under, so it cannot move to
another machine or a fresh root. `backup create`, `backup inspect` and `backup verify` say so in a
`Restores into` row, and their JSON carries `trustBound`. A registry restore does not check the trust
state, so `--only registry` still restores such an artifact's channel settings. When a full restore
refuses `CONFLICT` because the trust state moved, its Next names that `--only registry` restore for an
artifact that holds the registry.

File integrity is not a signature or a restore proof. Matching a manifest does not authenticate
its author, verify snapshot semantics or prove existing trust will accept a restore. `backup
inspect` and `backup verify` do not compare an artifact's trust state with this root's, and their
`Authority continuity` row says `not checked`. A full artifact taken on this root before `clean all`
or `up --rotate-sys` still verifies, and restore refuses it `CONFLICT`. The guarded
read path refuses unsupported file-protection environments rather than using a weaker reader.

`backup recover <full-attempt-id>` uses the original root's pre-commit restore journal, not a
manifest path or selected-space guess. It rolls the attempt back once it is stale: its restore
process and every recorded watchdog and broker are proven dead, and either every broker this root
started is proven gone or the claim's deadline has passed. Commit intent forbids rollback. The
receipt names `cotal up`, which resumes the space from its preserved state, and
`cotal backup restore <directory>`, which tries the restore again, as its next steps.
`backup cleanup-fallback <full-attempt-id>` selects the fallback recorded for that attempt. It does
not take `--store-dir`. It requires the matching healthy active restore and
removes only its unchanged retained old-store identity; it never removes the restored target.
It removes that store by its store entries, as `clean store` does. When the old store also holds
anything else, such as a file you put in a custom store directory or in the fallback folder, its
`--dry-run` names those entries, and the cleanup refuses `CONFLICT` (exit 2), names them and deletes
nothing. Move those entries out before retrying. The retry includes `--discard-history` only if
it was given in the original command. If the store holds the only copy of data the restore left
out, the refusal tells you to keep that store unless you choose to discard the data.
A restore into the preserved store's own path moves that store aside whole, so it refuses
`CONFLICT` (exit 2) the same way before anything moves.
A restore made with `--accept-missing-source` replaced a missing source and retains no old store.
Run `cotal backup cleanup-fallback <attempt> --yes` to retire its journal without removing a store.
A later `down --preserve-state` then
starts a new backup cycle. A registry restore leaves every other stream out, chat and DM history
and workflow runs included. A full restore of an artifact with no workflow runs leaves the runs out,
and a full restore of an older artifact can leave out newer messages, workflow runs, channel
settings, access grants, members, or history limits. A backup holds one account, so any restore also
leaves out the streams of another account in the store it replaced, such as an open mesh's account
beside a static space's after both ran in one folder. When the restore retained an old store, that store holds the
only copy of what it left out. In that case, `--dry-run` warns with
`HISTORY_ONLY_IN_PREVIOUS_STORE` and names what it left out, with those accounts in `otherAccounts`, and the cleanup refuses
`USAGE_INVALID` (exit 1) and deletes nothing unless `--discard-history` is given.
That refusal names the flag and does not print the command help.
The age difference alone does not require consent if restore verifies that the newer cut held no
additional backed-up state.
Both review full paths and default to Cancel. Scripts need `--yes`; `--dry-run` reads the plan
without taking a maintenance lock or writing. Passing both flags refuses `USAGE_INVALID` (exit 1)
before looking up the attempt. Use `--dry-run` to review or `--yes` to apply.
Apply rechecks the reviewed journal revision under
the native lock, preserves unknown outcomes and never retries a deletion. No live-owner override
or process kill is supplied.
A restore's full attempt id has the form `restore-<uuid>`. `backup recover` also takes an
interrupted create's `backup-<uuid>`, as described above. `cotal status` shows the attempt a root
holds under Maintenance, with its state and next step. That step includes `--discard-history` when
describing the consent needed to delete data the restore left out. The command it prints in that
case previews cleanup. For a registry restore with no retained store,
it says that chat and DM history and workflow runs start empty. The legacy `clean restore-fallback` also refuses a
matching pre-commit attempt without deleting anything and points to `backup recover`. A refusal for
the wrong state names the next step for the recorded one. A completed `cleanup-fallback` retires the
journal. If the attempt ID does not match an active restore that retained data, the
`TARGET_NOT_FOUND` remedy previews cleanup for the recorded attempt. It carries an explicitly given
`--discard-history` only on that read-only preview, not on a deletion command for a different
attempt. When the current root holds no restore attempt, cleanup refuses with `TARGET_NOT_FOUND`
and asks you to check that you are in the original project folder. The refusal does not confirm that
cleanup already ran.


## Restore receipts

`backup restore <dir>` is the canonical restore. It runs the same guarded restore as
`up --restore <dir>`, with the same lock, claim, trust and space proofs and the same resume, and
returns one `backup restore` receipt: the restore attempt, space, root, selection, store, broker
process and whether the manager, delivery and auth service started. The restore follows the
artifact's own selection, and `--only registry` narrows a full artifact to the registry. Any other
`--only` value is refused, because the restore could not honor it. The space, broker and runtime
come from the preserved cut, so no selector can rebind them. An artifact of another space refuses
`CONFLICT` (exit 2) and names both spaces, and a full artifact taken under another trust state
refuses `CONFLICT` the same way. An artifact file that is missing, undeclared or not its declared
size and SHA-256 refuses `SCHEMA_INVALID` (exit 1) and names the file, as `backup verify` does. A
manifest whose space is longer than 200 characters is invalid, so restore refuses it with the fault
`manifest-invalid` and does not print that space. In each case the preserved cut is not changed. A
receipt means the
active journal was written. Its `seatResume` field says whether retained seats were handed to the
manager's resume (`requested`) or dropped by a registry restore (`not-requested`). It does not
confirm that any seat joined. Its `restored` and `recreatedEmpty` fields name the streams the
restore brought back and the ones it recreated empty. A restore brings back the history limits the
artifact recorded for channel posts, DMs, the delivery inbox and stored copies: it creates each of
those streams with no age limit and the recorded count, checks the restored state, and only then
applies each recorded age. A registry restore brings back channel settings only, so chat and DM
history and workflow runs start empty. Its receipt says so with a `HISTORY_NOT_RESTORED` warning.
If the restore set aside a store, `previousStore` names it and the receipt says that
`backup cleanup-fallback` deletes it only with `--discard-history`. A full restore of
an artifact made before the state it replaced was preserved, such as a backup taken before a later
`cotal up` and `down --preserve-state`, can omit changes to channel settings, access grants, members,
history limits, message history, or workflow runs. When the full artifact includes the workflow
journal, restore checks the newer cut on an isolated copy. A fresh cut can qualify if its streams
hold no additional state, its history limits match the backup, and any initial channel-default
entry matches the restored copy. A cut with consumers does not qualify. Cuts made in auth mode or
user mode have consumers and do not qualify for cleanup without consent based on this check. If restore verifies that
the cut qualifies, the plain receipt says so, and cleanup does not require `--discard-history` for
the age difference alone. If the check finds additional state or cannot rule it out, the receipt warns with
`NEWER_HISTORY_NOT_RESTORED` and cleanup still requires `--discard-history`.
When the store a restore replaced also held another account's streams, the receipt says they are not
restored and names the accounts in `otherAccounts`. That is an `OTHER_ACCOUNTS_NOT_RESTORED` warning,
or the warning above when the restore also left out history or workflow runs. Deleting the previous
store requires `--discard-history` in either case. `previousStore` names the store a restore set aside whenever
that store holds the only copy of something the restore left out, and is null otherwise. A restore
made by an earlier release recorded no other accounts. For it, `status`, the cleanup preview and
the cleanup read them from the store it set aside while that store is still the one the restore
recorded, and name only the accounts the restore's auth mode rules out: every account but `$G` after
an open restore, and `$G` after a static or user one. Which data account a static or user restore
brought back is not recorded, so another data account in that store is not named. Before such a
cleanup, list the previous store's `jetstream` folder: each folder there is one account.
When that restore brought the workflow runs back, it also names each run it rolled back and each
step that was answered after the artifact and is open again, and says that answer is only in the
store it set aside. A reopened step accepts an answer again. `cotal status` and the
`backup cleanup-fallback` preview name the same runs. Restore checks for additional state and reads
the prior run journals on the same isolated copy of the store it sets aside, so such a restore takes
longer and needs disk space for that copy.

Restore refuses `USAGE_INVALID` (exit 1) before staging if `--store-dir` names a symbolic link or a regular file, or if a regular file blocks the path. The only store path allowed inside `.cotal` is the project's default store. For an alternate store, choose an unused path in an existing writable directory outside `.cotal`. The restore creates the store directory.

`up --restore --restore-only registry` prints the same two lines. Without `--store-dir`, a restore
creates its store at `.cotal/nats`, also when the cut's store is elsewhere, as after
`up --store-dir`; only a controller root restores into its recorded store. The preserved store stays
where it is until `backup cleanup-fallback` deletes it, so to keep the space on another disk, name a
new store there with `--store-dir`. `--store-dir` names a store the restore creates, so a path that
already exists, whose parent does not resolve to an existing directory, or that contains a
symbolic-link loop or exceeds filesystem path limits refuses `USAGE_INVALID` (exit 1) before
anything is staged. A store path that overlaps the backup artifact or sits inside the preserved
store also refuses `USAGE_INVALID` (exit 1) before the restore starts. Choose an absent path outside
both the backup artifact and the preserved store. If access
is denied while checking `--store-dir`, both restore forms refuse `PERMISSION_DENIED` (exit 2), name
the blocking directory when it can be identified and leave the preserved cut unchanged. Restore
search access there or choose a new store path under a parent this account can search and write.
A parent this account can search but cannot write also causes `PERMISSION_DENIED`. Make it
writable or choose a different parent. Leave the new store directory absent so the restore can
create it. Restore needs the stopped preserved cut from `down --preserve-state`. A root with no
maintenance journal refuses before the restore takes its
maintenance lock. Both `backup restore`
and `up --restore` leave the project folder and the connector installation unchanged in that case.
If the root is prepared for its first controller start, the refusal points to `cotal space show`
and explains that starting it does not make preservation or restore available. On a legacy root,
the refusal says to start a stack a plain `cotal down` stopped with `cotal up` first, since that stop
records no cut. An artifact path that names nothing refuses `TARGET_NOT_FOUND` (exit 2) at the same
point. It names the path, and its JSON
target says in `missing` whether the folder that should hold the artifact (`folder`) or only the
artifact (`artifact`) is missing. A path that is not an artifact, or is an incomplete one, refuses
there too, as `backup verify` refuses it. A restore artifact can sit in `.cotal/maintenance`, beside
the attempt and journal directories. It must not overlap the preserved store or any of these paths:
`.cotal/maintenance/attempts`, `.cotal/maintenance/v1`, `.cotal/maintenance/lock.json`, and
`.cotal/maintenance/lock-reaper.json`. If paths overlap, restore refuses `USAGE_INVALID` (exit 1)
and names the protected path. Restore repeats this check under the maintenance lock because a link
may name another folder by then. A restore that fails after it
began names its attempt in the text and in the JSON target, which also carries `journalState`, and
its remedy gives the next step for that state. The listener endpoint must be a bare `nats://` or
`tls://` URL without credentials, a query, a fragment or a path. Its refusal does not repeat the
endpoint value, including when it came from a preserved launch. `up --restore`
remains as the equivalent startup form. It refuses `--no-manager` with `USAGE_INVALID` (exit 1)
before staging. A restore needs the manager to commit its state, so run it without `--no-manager`.
The preserved store and its ready journal stay unchanged. After their startup lines, both foreground and detached
starts name the restore attempt and give the cleanup step. If the retained store holds data the
restore left out, the step previews cleanup and explains that deleting the store requires
`--discard-history`. When `up --restore --root` selects another
project, the cleanup step starts with `cd <project> &&` so you can run it from the folder where you
ran the restore. `backup restore` defers connector reconciliation to startup, as `up --restore` does.

Three commands refuse an active restore. `down --preserve-state`, in each of its forms, refuses
`LIFECYCLE_BLOCKED` (exit 2) and stops nothing: a new cut begins only after the restore journal is
retired, so it names the attempt and `backup cleanup-fallback` as the next step. If the retained
store holds data the restore left out, the command it prints previews cleanup. `team boot`
resumes only a stopped stack whose manager never launched, and a restored stack's manager already
ran, so start it with bare `cotal up` instead. `cotal up -f` boots a fresh mesh, so it starts only
once the restore is retired. While the restored broker runs, it refuses `CONFLICT`, exit 2, naming
the broker's PID, and its Next is `cotal down`, then `backup cleanup-fallback <attempt> --yes`, then
`cotal up -f` again. If the retained store holds data the restore left out, the refusal names
cleanup as a separate choice and explains that deleting the previous store requires `--discard-history`.
Once that stack is stopped, it refuses `LIFECYCLE_BLOCKED`, exit 2, and names
the cleanup. Nothing is started either way. While the restored broker runs, any other `cotal up`,
bare or with `--server`, refuses `CONFLICT` too, naming its PID, and leaves the restore journal as it
was. Its Next is `cotal down`, then `cotal up`. Once the broker stops, `cotal up` checks the store's
identity and reopens the store recorded in the active restore journal. You do not need to repeat
`--store-dir` or retire the journal to restart.


## Artifact contents

Full backups retain tool arguments and results in the EVP payload stream. Restore preserves their
owner and actor subjects without widening payload read permissions. Registry-only restores recreate
EVP empty, as they do the other message streams.
New artifacts use `cotal-space-backup/v3`. Restore also accepts `v2` artifacts without EVP and
`v1` artifacts without EVP or workflow stores, recreating those omitted streams empty.

Stopped client-managed KV ordered consumers are ephemeral read residue, not backup state. Backup
ignores only the pinned client's exact stopped shapes: ordinary last-value watchers, a watcher of one
subtree of its bucket such as the manager's goal index, and the whole-bucket scanner that uses
all-history delivery to collapse concurrent tombstones. A bound consumer or any lookalike with a
filter outside its bucket, another inbox, lifetime, or other config is still refused.

`full` is the default and indivisible: channel registry, CHAT/EVP/DM/TASK/INBOX/DLV, ACL, MEMBERS, on
a static-auth or open mesh the workflow run stores (the WFJ step journal, the records store and the
run admission store), and validated durable checkpoints. `registry` is the sole partial artifact. Presence, derived membership
feed, leases, native ephemeral/history consumers, credentials, keys, tokens, owner secrets, and actor
ledger files are excluded. The other endpoint stores are nonportable control state: endpoint
submissions, facts, events, timer requests and fires, work pools, contract artifacts, and the
auth, session and issued-authority stores. Restore recreates those streams empty with their
canonical configs before exposing the normal listener, so endpoint sessions do not cross a backup.
A full backup includes the checkpoint of an open-space DM inbox that is still present after its
seat disconnects, if the inbox has the standard inactivity threshold or none. A full restore
recreates the inbox at the checkpoint's replay position with the standard inactivity threshold.
The delivery daemon's anycast request records are control state too and come back empty. A full
restore brings back the requests the TASK queue held at the cut and recreates its durables from
checkpoints, so a role request a holder had taken and not yet acked at the cut is on its role's
queue again, even if that holder finished and acked it after the cut. The broker delivers it again
at delivery count 1, as it redelivers any unacked request, and any holder of the role may take it
and do the work again. Until then, on an authenticated mesh, its sender reads it as waiting
([SPEC §8.1](../SPEC.md#81-anycast-request-status)). A
workflow run that waited at a checkpoint or a timer at the cut is back after a full restore, and the
manager takes it over as after a restart. The records store also holds the endpoint authority rows,
such as lifecycle heads, obligations and policy versions, and a full restore rolls them back to the
cut with the runs. A user-mode full backup holds no workflow run store, because the records store's
lifecycle heads name credential rows in the auth store, which a backup does not carry; its restore
recreates the run stores empty and says so. An artifact in the earlier `cotal-space-backup/v1`
format still restores; it holds no workflow run, so the run stores come back empty and the restore
says so. `backup create` says so too when its artifact holds no runs, as a registry or user-mode
artifact does. After a restore that left the runs out, the store it set aside holds their only copy:
its receipt says so with a `RUNS_NOT_RESTORED` warning that names that store, and
`backup cleanup-fallback` deletes it only with `--discard-history`, as for a registry restore. Each
restore lists what it restored and what it recreated empty. Artifacts are exclusively created `0700`;
snapshot/checkpoint files and
the manifest are `0600`; `manifest.json` is written last with exact sizes and SHA-256 values. The
directory is trusted operator input: hashes detect corruption, not malicious rewriting. So
`backup verify`, `backup restore` and `up --restore` apply the
[`space create`](cli-selection.mdx#selecting-a-space) rule for other local writers to the artifact directory, each
file in it and each directory above it. An artifact another account could write refuses
`PERMISSION_DENIED`, exit 2, before a restore stages or changes anything, and the refusal names each
such path and one remedy such as `chmod g-w <paths>`. `backup create` refuses the same way, before it
writes anything, when a folder that would hold the artifact breaks the rule. `backup inspect` does
not check this, and a copy that other accounts can only read is accepted.


## Store staging

Restore validates and stages the exact allowlisted artifact bytes before moving or creating a store.
It requires the same space. A full restore also requires the trust state the artifact was taken
under; a registry restore, `--only registry` of a full artifact included, does not check it. The
whole pre-commit window holds a journaled
liveness claim (coordinator, watchdogs, brokers, and a deadline 30 minutes after the restore
began). While the claim is live, ordinary `up`, a repeated restore, `backup create` and
`backup recover` refuse `LIFECYCLE_BLOCKED` (exit 2) and name the restore process, when it started
and the deadline. A command that finds
the root's maintenance lock held refuses the same way and names the pid that holds it. The attempt
is stale once the restore process and every recorded owner are proven dead on this host, and
either the deadline has passed or every broker the root started is proven gone. A broker's
watchdog stops it when the restore process exits, so a restore stopped by Ctrl-C is stale within
seconds. A retried restore rolls a stale attempt back and continues; an operator can also roll it
back with `cotal backup recover <full-attempt-id> --yes`. Nothing ever rolls back a live attempt.
A restore interrupted by SIGINT, SIGTERM or SIGHUP before it commits exits 130, 143 or 129 and
prints its attempt id and that recovery command. A registry-only artifact restores as registry-only whether or not
`--restore-only registry` is passed; omitted infrastructure is always created and the exact
post-restore stream inventory is asserted before commit intent. Ordinary `up` from a preserved cut
resumes only the exact recorded source store, file store cap, runtime and broker address. A different
`--store-dir`, `--max-file-store`, `--runtime` or `--server` refuses `CONFLICT`, exit 2, before
anything starts, naming the value given and the recorded one. The Next resumes with `cotal up` without that flag, then `cotal down` and
`cotal up` with it.


## Seat checkpoint admission

**Admitting a seat checkpoint.** An ordinary `up` from a preserved cut admits that cut's seat
checkpoints before it journals the resume attempt and before any process starts, so a refusal costs
nothing. Three gates run in order, each naming what it saw.

1. *Integrity.* Every file the record names must be present, a regular non-symlink file, the
   recorded byte size and the recorded sha256, re-stat'd after the read so a file that moved is a
   refusal. Failure here consults no other gate.
2. *Identity.* The recorded space must match, the recorded `lifecycleUid` must not belong to a live
   incarnation, and the profile revision must match this host's or be resumed under deliberately
   this host's. A differing revision is refused with both digests and the remedy, and there is no
   override: the checkpoint carries the recorded digest and not the config bytes, so nothing could
   run the seat under the recorded revision, and the manager re-digests the same file and refuses
   drift on its own. This gate has no blanket override, which is the only reason the next one may
   have one.
3. *Recency.* `capturedAt` is compared to this host's clock against the horizon the record carries.
   Inside it, the seat resumes. Outside it, `up` refuses and prints the capture instant, the clock
   reading and the horizon; `--accept-stale-checkpoint` admits it anyway and the exercised consent
   is printed with the actual age. An unreadable `capturedAt` is refused with no override, because a
   freshness gate that fails open is not a gate.

Custody transfers only after all three pass. The destination claims the recorded generation plus one
by exclusive create, before it launches anything. A lost create means another destination is already
claiming that seat, and it refuses with `seat-writer-generation-create-lost` rather than adopting
the winner and becoming a second writer. The recorded `lifecycleUid` is reused and never minted, so
the resumed seat binds the same lifecycle-keyed durables.

Admission is reconciled against the inventory the resume is about to hand the manager, and that
reconciliation finishes before the restore moves a single tree. A checkpoint whose recorded
`lifecycleUid` is not the one the retained inventory carries describes a different incarnation of
that seat, and it refuses with both uids while every live working tree is still untouched and no
generation is claimed. A retained
seat with no admitted checkpoint refuses the resume by name: an absent checkpoint directory and an
absent record are indistinguishable from a seat that was never checkpointed, and a seat that starts
without passing the gates has claimed no generation. `--accept-stale-checkpoint` is recorded in the
resume journal with the seat, the capture instant, the admitted age and the horizon, so the consent
survives the terminal it was typed into.

The whole admission is all or nothing. Coverage is settled first, then every gate runs over every
checkpoint, and only then is any generation claimed. A refusal at any point leaves every generation
unclaimed, including a lost exclusive create during the claim itself: the claims that attempt made
are removed before the refusal is raised, by the exact paths it wrote, so a generation another
destination holds is never touched. A claim is a create that can never be made again, so a refusal
that left one behind would consume the retry over the same checkpoint set.


## Seat checkpoint restoration

**Restoring a seat checkpoint.** Once every gate has passed over every checkpoint, and before a
single generation is claimed, `up` puts each admitted seat's captured bytes back. A refusal here
costs nothing for the same reason a gate failure does: no claim has been made and nothing has
started.

A restore never moves or replaces the destination's own control directory. A checkpoint excludes
`.cotal/` by design, so a seat whose `cwd` holds one, which is the layout an operator gets by
running `up` and `spawn` in a single directory, is refused before anything is staged: promoting a
tree that cannot contain `.cotal/` over that `cwd` would carry this host's live trust material and
maintenance state away with the superseded tree. The refusal names the control directory it found
and the remedy, which is to give the seat a working tree that is not a workspace root.

Each seat is staged beside its own `cwd`, in `<cwd>.incoming`:

1. every recorded digest is verified again over the files as they are now;
2. the bundle is cloned into `<cwd>.incoming`, which is refused when that path already exists;
3. the recorded base commit is verified in the clone and checked out detached, so a bundle that does
   not contain it stops the resume instead of continuing against a different history;
4. the index diff is applied with `--index` and the worktree diff without it, both `--binary
   --allow-empty`. That order is what puts staged content back in the index rather than only in the
   worktree, and `--allow-empty` is why a seat with a clean tree is still restorable;
5. the untracked archive is extracted.

Every seat stages before any seat is promoted. Promotion moves an existing `cwd` aside to
`<cwd>.superseded.<timestamp>` and renames the staging directory into place, then puts the session
pointer and store files where the destination's connector reads them, then re-reads
`git status --porcelain` in the promoted tree and compares it to the status the checkpoint recorded.
A restore that applied without error and produced a different index is a refusal, not a warning. The
two renames are the only steps that touch the path the seat will use, so a failure anywhere leaves
every seat's live `cwd` as it was.

The rename itself claims the superseded name, and a taken name gets a numeric suffix. The timestamp
has one-second resolution, so two promotions of the same seat within one second compute the same
path; a rename onto a name that already holds a tree fails on every platform, and that failure is
read as taken. Nothing creates the name ahead of the move, because Windows refuses to rename onto an
existing directory at all. A superseded tree is the thing that rename exists to keep.

`git` and `tar` run as child processes with argument arrays, never a shell string.

A leftover `<cwd>.incoming` refuses the resume by name. A staging directory from a failed run is the
only record of what failed, so nothing removes one automatically: inspect it, remove it by hand, and
resume. A pre-existing `cwd` is renamed rather than deleted, so a wrong checkpoint costs a rename
instead of a tree. When a promotion fails, the renames that attempt made are undone and the staging
tree is left where it is, as the evidence for what did not verify.

A session pointer whose recorded `sessionId` is not the one the retained inventory reopens is
refused before anything is cloned. A session file already present at its destination is judged by
content: bytes equal to the recorded digest are already restored, and different bytes under the path
the connector is about to read are refused with both digests rather than clobbered.

`up --restore <dir>` reaches the same admission and the same restore, after the store is restored
and validated and before commit intent is journaled. A registry-only restore resumes no seat, so it
admits and restores nothing.

The writer generation is claimed by exclusive create inside one workspace root. It fences competing resumes in that root. Separate roots on the same host, or on different hosts, do not share that fence: copying a checkpoint to two roots can let both claim the same successor. A cross-root fence needs a coordinate neither root owns.


## Restore commitment

Authenticated restores validate the complete
space trust bundle before staging, including nkeys, seed matches, JWTs, signers, and space binding;
full restores commit to the validated operator, system-account, data-account, and active-signer root
chain in addition to the static/user authority fingerprint. Because the system account is part of that
commitment, a [`cotal up --rotate-sys`](cli-startup.mdx#up) makes every full artifact taken before it unrestorable
against this root: take a fresh full backup after each rotation. [`cotal clean all`](cli-shutdown.mdx#clean) removes
the space trust itself, so it does the same. Such an artifact still restores its registry with
`--only registry`, and chat and DM history start empty. The composed commitment is revalidated
immediately before store mutation and never includes secret seeds. Restore never creates fresh auth.
Same-path restores atomically retain the old
source at the journaled fallback path; alternate targets retain it in place; a missing canonical
source needs explicit `--accept-missing-source`. Without it, the restore refuses `TARGET_NOT_FOUND`
(exit 2), names the missing path and changes nothing. With it, the store is rebuilt at its recorded
path, a custom `--store-dir` included, and later startups reopen it there. A `--store-dir` naming another
path is refused before staging. A default `.cotal/nats` that is a symbolic
link to the recorded source is that source, so the restore runs in place at the real path and the
link keeps naming it. Quarantine and target restores use current canonical
configs on isolated random-loopback brokers, never expose native snapshot consumers, and publish a
commit-intent immediately before the normal listener starts. Archive bytes never instantiate the real
target: after quarantine validation, every stream is re-snapshotted from the validated quarantine
state into attempt-owned sanitized files, and the target is restored solely from those. Before that boundary, failure rolls back
the attempt-owned target; after it, ambiguity preserves both stores and records forward-repair
recourse. The cooperative maintenance lock excludes Cotal commands, not arbitrary raw NATS processes.


## Bootstrap broker authority

Bootstrap brokers in every auth mode, including open, mount the store under a local account with
random operation-specific logins only, each carrying the exact per-phase subject permission matrix;
normal static credentials and user-auth sentinel/bearer connections are rejected, and no auth
service or callout starts. Open mode differs only in its account label, never in authority. Inventory, each stream snapshot,
restore initiation, exact upload id, validation, and each checkpoint recreation use separate exact
authorities. Every checkpoint carries the source stream's message/first/last sequence state and must
match its snapshot record before mutation; core then derives and validates the only allowed start
policy. TASK is not a CLI exception: the same core checkpoint API recreates its canonical `DeliverAll`
WorkQueue durable because acknowledged tasks are absent from retention and NATS forbids a
start-sequence policy there. Registry-only restore creates every omitted canonical stream and transient
bucket on the isolated target before the normal listener is exposed. It deliberately does not resume
retained agents or recreate their DM/DLV/TASK/ACL state; their identity material stays retained and
stopped rather than being reprovisioned into a partial restore.


## Manager finalization

After listener readiness, the manager starts attempt-bound, validates retained credentials/tokens
without granting or reprovisioning, and resumes the exact persisted principals under cleanup
suppression. Registry-only restore uses the same flow with an empty agent set. On a user-auth mesh
these manager calls run as the logged-in operator's `cli` actor, the caller the preserve cut used, so
that actor needs a current `admin` grant. `commitResume` is an
idempotent validation barrier only: success must be `awaitingFinalize` with an attempt-bound 64-hex
commit token and does not release suppression. Under the workspace lock, the CLI first fsyncs that
exact evidence as `manager-committed` (restore) or `resume-committed` (ordinary resume), then calls
token-bound `finalizeResume`; only an `active` response for the exact token releases suppression. The
CLI records the same token in finalization evidence before a restore becomes `active`, or before an
ordinary resume retires and consumes the marker. A new launch hands the token to the next manager as
a protected file: the CLI journals its path, writes it at mode 0600 in
`.cotal/maintenance/v1/handoff/`, then journals its inode and digest before the child starts. The
child reads it once with `--resume-commit-file` and `--resume-commit-sha256` and removes it. The
token never appears on a new launch's command line. Before retirement or activation the CLI settles
that file. A file it did not record, or a recorded path that now holds another file, holds the
attempt and is never deleted. `cotal supervise --resume-commit-token` stays accepted for older
callers; while such a process runs, its token is visible in its command line. Re-entry from either committed state skips the prior
idempotent activation/commit phases, retries finalization with the durable token, and finishes the
workspace transition. Failure before finalization preserves the committed state and cleanup
suppression; it is not rewritten through a degraded transition. A failed listener INFO read names
whether the attempt is a resume or restore and includes its attempt ID, so an ordinary resume does
not report a restore failure. Re-entry between any two earlier
boundaries reuses the same attempt and may retry the idempotent phases without deleting retained state. A missing or
changed per-agent dependency is a named fail-closed result; the journal becomes degraded and remains
available for forward repair. A retry from `resume-intent`,
`resume-active`, or `resume-degraded` reuses the same attempt and inventory after the prior listener is
proven stopped. A retained agent the lost manager already launched can still be running, for example
in a tmux window, while the journal reads `resume-intent`. On a static mesh the replacement manager
closes that seat through the reference the lost manager recorded on the agent's slot, waits for the
principal to leave presence, and launches it again. A live principal with no such record, or one that
stays live after the seat is closed, is refused. Every normal restore listener has an unguessable
attempt-bound NATS server name. The CLI fsyncs its exact name/nonce, canonical endpoint, process owner, and generation-bound target identity
immediately after spawn. Re-entry accepts a surviving listener only when its INFO server name, live PID
record, endpoint, and target identity all match that proof; degraded restore repair then moves through
the guarded workspace transition only after manager commit. If an uncommitted bound owner is provably
dead, recovery retires that exact proof under the maintenance lock and binds a fresh listener for the
same attempt, endpoint, and target with a new nonce and server name. A live foreign/mismatched listener
or ambiguous owner is preserved and refused, never adopted by reachability alone. Before the
daemons start, re-entry recreates the memory-only buckets on an adopted restore or resume listener,
because the interrupted `up` may have stopped before it made them. The mesh record it then writes
keeps the recorded attach host and session ceiling and the store cap the adopted broker started with.
On a legacy root, a restore uses the cap recorded in the preserved state unless `up --restore`
receives an explicit `--max-file-store <bytes>`. The restore journals the cap it uses so re-entry
keeps it. If SIGINT, SIGTERM or SIGHUP interrupts a restore after commit intent and before the listener
starts, the command names the attempt and tells you to run bare `cotal up` from that root. If SIGINT
or SIGTERM stops foreground `up --restore` before it records the manager commit, the command waits
for its stack to stop, gives the same recovery step, and exits 130 or 143, respectively. Bare
`cotal up` continues the same attempt. Once the manager commit is recorded, an interrupt lets the
restore finish and print its receipt before stopping the stack and exiting with the signal's status.
If no listener was bound to the attempt, it starts one only when no process of this account names
the attempt and the recorded port is free. A listener spawned and never bound may still be opening
the restored store, and NATS does not stop a second server from opening it too. While such a process
runs, `up` names its pid, refuses to start and preserves the attempt. On a host that cannot read
command lines, `up` can start a listener when the journal proves startup has not begun, or when
the published process identity proves the previous listener is gone. It refuses if the last spawn
may have started but did not publish its PID. A closed port does not prove that listener is gone.
A later ordinary startup may pass an `active` restore only when its details
prove manager commit and its exact recorded listener is dead.
