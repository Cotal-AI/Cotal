# Permanent agent ID across launches

This is a design, not an implementation. A fully stopped agent gets a new lifecycle when it starts again, but keeps its permanent ID and stable grants. Every kind of Cotal agent is in scope. The authority draws the ID at random and owns its record. An ID is a reference, not a credential, routing address or proof. Knowing only the ID grants nothing. There is no per-agent private key or agent-supplied signature.

A link uses the owner's saved sign-in, without asking for link approval again, or a standing permission the owner gave an independently registered launcher once and can revoke. Only one run can occupy an ID. **Sleep and wake ([#10943](https://github.com/Cotal-AI/Cotal/issues/10943)) are not links:** sleep keeps the exact run, and wake starts a process on that run. Retained resume and reconnect also keep an existing run. An ended run can never wake or return.

## A2.0 and A2.R: custody and launcher registration

**A2.0, protected saved sign-in.** Keep the opaque IdP session handle in an OS credential service with application access control and a trusted broker isolated from the agent process, or under a separate OS principal with an equivalent boundary. Agent shells cannot read the handle, extract the JWT, invoke the protected broker as the person or drive its user interface. Shared HOME and mode `0600` alone are insufficient. Stock CLI-only installations do not meet this condition today and stay off under this recommendation. Main caches the handle and exchanges it for an in-memory JWT; connector processes inherit HOME. `implementations/auth/src/login.ts:5-14,42-50,427-449,475-525,993-1005`, `implementations/auth/src/session-context.ts:19-27`, `extensions/connector-core/src/launch.ts:8-18` (**main**).

At admission the protected broker obtains a fresh JWT from the provider's `/token` using the saved session, bypassing the ordinary in-memory JWT cache for this operation. Check the token's issue time, never how old the sign-in session is or when the person last entered a password. The authority verifies the pinned signature, exact issuer and audience, nonempty subject, expiry and signed `iat` no more than **60 seconds** before its own clock, with no forward time allowance for this age check. Present the provider token only at the pinned authority. The token is not itself a signature over the launch; trusted admission binds the verified owner, account, space and exact request digest to one pending operation. Do not allow a user bearer, cache-only `sub` or `ownerForLogin` to link. Finish first release by the earlier of expiry and the same issue-time limit, or require a fresh online JWT for the exact same operation from the protected broker; never ask for new link consent. Revocation means **the IdP revoked the server-side session**. Local sign-out may leave it alive. A JWT issued just before revocation is usable only within its remaining validity and the age limit; do not claim instant JWT revocation. Loss of the IdP or protected store means refuse, not derive offline. A full copy of a local mesh disk can include the owner derivation and callout/signing material and can operate a separate copy of that mesh; IdP revocation cannot secure that copy. Main's ordinary verifier and offline owner derivation are separate: `implementations/auth/src/idp.ts:156-202`, `implementations/auth/src/provider.ts:530-540` (**main**).

**A2.R, registered launcher.** The principal is an account/space-scoped launcher registration, for exactly one Manager instance or hosted launcher service instance and one owner. Its credential is a separately generated, protected asymmetric key, a short-lived launcher-authenticated assertion of possession bound to the authority's audience, registration revision, one operation and request digest. Registration pins the public key, service/instance, owner, account, space and authority revision. The auth-host registry owns create, rotate and revoke; the owner gives explicit human confirmation for enrolling and rotating launcher keys; revoke uses the protected online owner token. Rotation and revocation invalidate pending requests at the same registry fence. Sign an assertion for each attempt, expire it at the same maximum issue-time age as an owner admission, and use its request ID as a one-use operation key. A launcher assertion is not an actor bearer, a Manager spawn grant, a copied IdP token, or an owner proof. Do not ship launcher admission until the Manager uses this distinct principal for linked enrollment and refresh of launcher authority. Legacy Manager operations keep their current path until migrated; the Manager today uses the owner's shared session handle and derives owner on the hosted token route. `implementations/auth/src/service-sessions.ts:5-7`, `implementations/auth/src/service-manager-routes.ts:392-398`, `implementations/auth/src/retained-manager-validation.ts:73-85` (**main**).

**Reported by the hosted side from source, not verified in this repository or run:** a hosted sign-in session has a seven-day inactivity limit and no absolute limit. The separate one-day freshness check measures time from session creation and is not used here. Whether fetching `/token` counts as use and extends that inactivity window is an open verification item. The hosted Manager token routes check issuer, audience, signature and expiry but do not check issue-time age. They must apply the same bound above, with no `auth_time` requirement.

### Decision 5: a headless Linux server

**Recommendation: require protected custody.** The stock PTY path passes a filtered environment but does not change the seat's Unix user. HOME and XDG paths reach the connector, and the ordinary IdP session is a file under the sign-in directory. On a server where the Manager and seats share a UID, the file's `0600` mode protects it from other users, not those seats. Splitting the Manager's and owner's trusted launcher processes from the seats into separate Unix users with private files and a restricted launch channel can meet A2.0 without a desktop. To retain one UID, use an OS-enforced sandbox or mandatory access-control policy that denies seats access to the store, process inspection/control and the privileged launch channel, or put the credential and trusted controls behind an independently protected service. A private directory or keyring available to every process of the UID is insufficient. Stock shared-UID PTY operation has none of those isolation guarantees, so it cannot qualify unchanged. `implementations/manager/src/runtime/pty.ts:29-57`, `extensions/connector-core/src/launch.ts:12-18`, `implementations/auth/src/login.ts:1011-1044` (**main**).

**A2.R is not a workaround for shared-user custody.** Main has no independent launcher key in this path. It can copy the same IdP session handle into Manager service stores (`implementations/auth/src/service-sessions.ts:5-10,55-71`, **main**). A future private key stored as a same-UID file would be exposed on the same terms. A non-exportable key is not enough if seats can call its signer or control the Manager process through the shared UID. A2.R is reachable on headless Linux only with isolation of both the key and its use, for example the separate-user or enforced sandbox arrangement above, or a protected external launcher with its own trusted authority boundary. This applies even when the owner is signed out. Do not advertise registered-launcher support only because the local Manager can load a key.

**Alternative: offer a shared-user mode.** Enable owner-authenticated linking on a compatible shared-user user-auth installation after a one-time notice at local Manager or foreground setup, before linked issuance: “Agents running as this Linux user are not isolated from each other or from your saved sign-in. Treat every agent on this account as trusted.” Show it again only if the owner changes that setup boundary. The notice records the operator's choice; it is not proof that later requests came from a person, and a same-UID shell is not prevented from changing local setup. Keep online provider verification, the token age limit, exact owner/account/space, one live run, terminal settlement and revocation fences. Do not put selectors on agent tools or accept agent credentials as owner proof. A2.R still needs protected custody; on an unchanged shared-UID machine this alternative supports starts authorized by saved sign-in, not signed-out launches using an exposed local key.

**What changes for an agent on that computer.** Today a same-UID shell with a still-valid owner session can already act as that owner within existing controls, including ordinary provisioning where supported; a mesh caller with only a seat credential is narrower. `implementations/auth/src/provider.ts:530-559`, `implementations/auth/src/ledger.ts:349-356` (**main**). With the alternative, the same-UID shell using the owner's sign-in gains the new owner link surface: it can start a new linked run or, after exact settlement, continue an owned permanent ID and exercise that ID's stable policy as the new run. It can also request exact owner retirement where that new surface is enabled, without needing Manager custody. This does not grant services beyond the verified current policy, admit a second live run, cross owners or confer authority from an ID alone. If the installation exposes owner confirmation controls to that same UID, treat them as shared too: destructive ID deletion and persistent launcher grants must stay disabled there until confirmation has a protected boundary. Moving the handle into A2.0 later tightens access, but does not invalidate copies already taken. Revoke the old IdP session and replace it with one stored only in the protected custody path before calling the installation protected.

**Rollout cost.** Under the recommendation, A2.0 gates A2b on that machine. Under the alternative, A2a readers still ship first and A2b may enable a separate shared-user owner-admission mode after notice and the local writer move in A4.1/A4.4. A2.0 remains a separate step and becomes the migration to protected custody, not a blocker for that mode. The alternative needs one local versioned setup record and discovery mode (listed below), positive and negative release cells for that mode, and preserves all A2.R, hosted-first, rollback and reader-before-writer gates. Neither choice unlocks local open/static modes automatically.

## A2: link on first credential, not at launch request

- **A2a, durable record and readers.** Keep the prototype's `ag_` plus 26 lowercase base32 characters, pure decision and closed server record. Mint only under the space authority, never from an alias, harness session or folder. An immutable create reservation covers even abandoned allocations; retention and restore preserve it. `current` is the last committed link. One occupied ID is serialized at its revision-pinned winner. For a new link, reserve exact lifecycle and operation before writing a bootstrap. A bootstrap is usable only at the same pending operation, not by the legacy exchange. At first root mint, pin authority/identity revisions, gate, head and root, write the immutable lifecycle binding, compare-and-set the ID, write audit and release through the final revision-pinned gate. Crash before commit reconciles the exact pending row or contains it; crash after commit finishes the audit or retires that run, never rewinds the sequence. A missing or inconsistent journal, revision or gate is a refusal. Restore does not reopen until reservations, grants and fences reconcile. Keep disabled until compatible readers, callout routing and writer fencing are deployed.
- **A2b, owner admission and exact retire.** Only the owner interactive row authenticated by A2.0 can authorize a request-supplied `select`, including across a Manager relay. If the shared-user alternative is chosen, its expressly enabled owner admission path can do the same. Shared-user proof authenticates the account, not a human rather than a same-UID process. After an occupied run is verified terminal and eviction verified, its successor has a new UID. A process dying, timing out, losing presence, losing its grant or using another alias proves nothing. Unknown settlement stays occupied. Add an owner-authenticated exact retirement operation, distinct from the current loopback capability route which requires the grant already revoked. Validate owner, actor and UID, fence mint first, revoke the exact actor grant and descendants, verify eviction before freeing the ID. This runs without a Manager or live app. Main's broker barrier and current routes are in `implementations/auth/src/credential-ledger.ts:533-580`, `implementations/auth/src/service-manager-routes.ts:130-161`, `implementations/auth/src/service-managed-retirement.ts:35-63` (**main**).
- **A2c, standing launcher permission.** `link-agent` is a host-private control permission, never a ledger scope, spawn ceiling entry, inherited right or delegated issuer claim. Default one owner, space, registration and existing ID; separate create-only permission for bounded new agents. Its ceiling is the intersection of allowed launch kinds, exact approved runtime/Manager registration and explicit scope, subscribe and publish limits with current policy and original-caller limits. A create-only grant does not implicitly gain `select`; a separately authorized owner can grant select before going away. A launcher can select without served evidence only when starting from its own authority-pinned, trusted stored launch reference or restart policy, never from a mesh caller's forwarded selection. The Manager rejects `select` from anyone other than the owner's interactive row. Where a caller originates the request, bind host-observed subject, serving registration and request digest to the exact admission, and verify original kind and live scope. Missing origin does not mean direct launch. A run driver or seat can request a new helper only, with its existing ceilings; it cannot borrow the launcher's select permission. Main's host evidence distinguishes missing `spawn`, observed served request and run driver; it does not itself verify a selection. `implementations/auth/src/managed-agent-enrollment.ts:67-101`, `implementations/auth/src/ledger.ts:360-410` (**main**).
- **A2c, revoke and unattended recovery.** The launcher permission fence and identity winner have a fixed acquisition order (registration, permission, identity). Revoke or narrow wins before release or follows it. If revoke wins, contain pending bootstrap and release nothing. Existing runs keep their own authority until retirement; the result lists their exact live lifecycles and offers a separate end action. Recommend a separately granted, non-delegable right to end only an exact predecessor this registration launched, after host-verified process death and custody, not to dismiss an active peer or an unknown run. A launcher without this grant waits for the owner to retire the run. Granting, widening, registering a launcher and irreversible deletion require an explicit human confirmation in the trusted owner controls, bound to one exact operation, with the same fresh online provider token as for link admission. Revoking and exact owner retirement require the fresh online owner token and exact target, without the extra confirmation step. For irreversible or permission-widening operations, create the one-use confirmation on the trusted owner surface, bind it to the verified owner and canonical operation digest, and consume it with the write. An API boolean saying the owner confirmed is not evidence. None of these operations requires `auth_time`, a password sign-in or a maximum session age.
- **A2d, lookup, audit and delete.** Owner-scoped read/list do not expose foreign IDs or live runs. Audit link, unlink, grant/revoke and delete with trusted principal, time, revisions and exact coordinates. Delete means permanent tombstone, never reallocation. Recommend refuse while live or settlement unknown. Under the identity fence, mark the ID non-active first and block further links and stable mint. Journal the pending cascade before releasing the identity fence. Revoke stable policy rows and select/retirement permissions for that ID, cut off indexed issued dependents, and wait for verified containment before reporting finished. Acquire applicable fences in the stated order during the cascade and on retries. No affected writer can re-enable a dependency once the identity is non-active. Append audit once and retain tombstones. A create-only permission not naming the ID is unaffected. Later tag rules must ignore the ID immediately and tombstone references when their writer exists. Leave messages, memberships and history under their original run and existing retention rules. A2d defines the lifecycle; enable delete with installed stable-policy and issued-source containment readers/writers before any stable policy is enabled. No caller receives a success before all present dependency families are reconciled.

After authentication, `conflict` names the current run or conversation to the authorized owner: “Agent ‘{agent}’ already has run ‘{run}’. End that run to continue this agent, or start a new agent. If its app is gone, end the run from the owner controls.” For sleep: “Agent ‘{agent}’ is asleep in run ‘{run}’. Wake that run to continue it, end it to replace it, or start a new agent.” A saved seat's Continue action offers wake directly for an asleep run, not new enrollment. If authority cannot confirm termination: “Cotal cannot verify that run ‘{run}’ ended. Retry ending it or start a new agent.” Do not disclose run coordinates before authorization.

### Decisions 3 and 4: one permission at launcher registration

**Recommendation:** retain the per-ID controls above. They limit what a compromised launcher can do but require the owner to grant continuation and dead-run recovery before going away. **Alternative:** the owner confirms the launcher once at registration. That confirmation grants one `link-agent` permission for the registered owner and space: start new agents, continue only those this registration launched, and clear only verified-dead predecessors of those agents that this registration launched. No mandatory second grant or per-agent approval. The owner may narrow the set or disable a right later. Both designs apply the launch-kind, instance, scope and channel ceilings.

| Situation | Recommended per-ID permissions | Alternative with one permission |
| --- | --- | --- |
| Launcher key stolen, without the owner's sign-in | A stolen key can authorize creation only with an explicit create grant, and continuation or recovery only for explicitly approved IDs. Those operations still require the authentic stored reference or restart policy and the authority's exact run evidence. | Creation is available within the registration ceiling. With matching references and verified settlement or death as appropriate, the damage can reach every eligible agent that registration launched, not just individually approved IDs. It can exercise an eligible agent's existing stable grants on the new run, but cannot continue another registration's agents, evict a live run or assign grants. |
| Launcher asked by a mesh caller | A seat or run driver can ask for a bounded new helper only if creation is granted. A caller-supplied ID or missing origin does not authorize a restart. An interactive owner selection uses the separate owner-proof path. | A bounded helper can be created without a second grant. The default does not let a seat or driver select or clear any predecessor, including its own. A launcher may not convert a caller request into a stored restart. |
| Launcher restarts after a crash | With its current registration and stored reference, it can continue only with the per-ID select grant. Clearing a predecessor also needs the separate recovery grant. Otherwise the owner must finish recovery. | The same registration can clear its verified-dead exact predecessor and continue its agent without the owner present. Unknown death, custody or provenance leaves the slot occupied. A sleeping run is not dead. |

**Unchanged safeguards.** Launcher select uses the launcher's own authority-pinned stored launch reference or restart policy, never a forwarded selector. The authority verifies and pins which registration first launched the agent and, separately, which launched the current lifecycle. Rotation keeps that registration; a replacement registration does not inherit it. A later owner launch through a different route cannot be cleared by the old launcher merely because it created that ID. Clear only after verified death and exact-run custody, then wait for terminal retirement and verified eviction before admitting a new run. Keep the registration, permission and identity fence order. If revoke wins before release, contain the pending bootstrap and release nothing. Revoking permission does not end an already released run.

### When mint-time rules can read the ID

A2a readers alone cannot supply an ID while linked writes are disabled. Once an A2 admission writer and a linked launch path are enabled, the credential authority can pass the committed `agentUid` of the exact active requesting lifecycle to a rule evaluator before releasing its credential. On first root mint, commit the binding and identity first under the issuance fence, then evaluate channel rules from that committed snapshot before compiling or releasing permissions. On later mints read the same verified lifecycle binding and recheck identity and issuance fences before release. Never take the ID from request input or silently mint without the intended rule check after a binding failure. An unlinked run has no ID to pass. Rule evaluation and enforcement need their own release, but neither a stable channel-grant family nor any A3 endpoint-grant step is required. If the enabled evaluator cannot complete, release nothing. Retry the same operation or contain the committed run under A2a without rewinding its link sequence.

## A3: stable endpoint grants, four pull requests

A stable grant names an owned `agentUid`, an exact endpoint instance and a capability ceiling. Issuance checks that the identity is **active** and its current binding matches the exact requesting lifecycle, account, space, owner and root credential. Recheck policy, assignment, approval, ancestry, scope and cutoffs under the issuance fence at final release; fail closed if a grant ID is ambiguous across stable and lifecycle policies. No stable capability follows a stale bearer or handle. A policy created before restart is unchanged when it works on the next run. No automatic conversion of existing lifecycle grants; they do not survive a new UID. Other grant families need an explicit stable variant, not inferred inheritance.

1. **A3a, policy and index readers.** Readers parse the closed stable grantee and policy, v2 list results and cursor and a separate stable caller index. Keep v1 index untouched so old `caller-policy-list` never sees stable IDs as lifecycle UIDs. Old v1 requests list only v1 data by contract, even when both surfaces are served; a stable list is an explicit versioned request and cannot silently receive a legacy-only page. Stable rows are direct service-owner grants for one exact instance. No delegated ancestry, journal or `any`/`ledger` target modes in this first cut. Verify the current assignment and service-owner authority before writing. Main's index and list enforcement is in `implementations/auth/src/service-host-caller.ts:264-277,489-513` (**main**).
2. **A3b, issued-source and cutoff readers.** Keep the closed `IssuedSourceRef { space, bucket, key }`, not a new union arm. The proposed source in the per-space private auth bucket is `stablegrant.<agentUid>.<grantId>`, scoped by account/space in the backing store. Index by stable grant identity, not policy revision. Pin the separate policy revision in mint gate evidence and fence release. A per-source cutoff reader denies admission at the marker and recognizes already-issued evidence, including after leader change. Old callout currently records only actor sources and will not add stable grants. The native source shape and index are in `packages/core/src/issued-authority.ts:233-237,274-312,575-596`, `implementations/auth/src/service-caller-policy.ts:211-225` (**main**).
3. **A3c, write and revoke.** After both readers have shipped, enable v2 service-host grant/read/list/revoke and index writes on a separate `stablecaller.enable` fence only when every issuer, verifier and admin reader is compatible. New wire requests retain the owner/service assignment and explicit capability validation. Serialize per-grant revocation with issuance, write durable cutoff first, retire all indexed issued dependents across revisions, verify eviction and retry idempotently before success. Delete uses the same operation. An old callout must not sit behind an enabled fence and quietly issue without the expected grant. Do not enable when the composition cannot prove its full reader quorum.
4. **A3d, mint integration and release cell.** After A3c and verifier release, enable stable mint on the exact live link with the current bounds. Exercise the end-to-end cell **“Restart while signed out, then use the same service”**: with a built CLI and real broker, grant a service call once, invoke it, end the agent, sign the owner out, start it via a permitted A4.1 or A4.2 launcher and invoke the same service without re-granting. Prove same ID, fresh UID, unchanged grant revision, denial of old connection/bearer/handle and denial of a run-only control grant on the new run. Race revocation with mint and check that no post-cutoff credential issues and already indexed dependents are cut off. A3 readers and writers may land disabled independently; this user acceptance gate cannot be claimed without a released launcher path.

Store only a server-acknowledged ID hint with the launch's existing authority pins. Never take a selection from a name or from a process holding an agent credential.

The hosted side reports its delegated sandbox mode is built and tested but not deployed: one stock Manager per space account runs outside the sandbox and reaches the hosted runtime over a socket; the backend creates the provider sandbox. Treat pooled delegated launch and its handoff as conditional gates for that rollout, never production prerequisites or evidence for any other step. Stage issue-time validation in both Manager routes. The Manager token proves the current transport caller, not owner intent or standing permission; replace shared owner-session use for linked launcher operations with A2.R. The hosted connection-approval page currently reuses an actor by name and offers no choice. That page gains the human-only picker in A5.

**Delegated user intent (§13.16).** The platform service can execute exactly one frozen owner-admitted launch, not supply an ID. Recommend create only at first, gated on the owner-authenticated intent and its original delegated ceiling. If a future owner decision permits continue, the hosted human-admission surface captures the selection and binds it to the exact account, owner, intent target, assigned instance, revision, expiry and consumed intent. Execution can only reproduce that selection, never add or substitute one. A `platform-control` holder is not a `link-agent` launcher by that role. A separate registration and grant are required for any independent launcher operation. Existing stock dispatch is unimplemented. `SPEC.md:6004-6033` (**main**).

**Linked Manager caller view (A4.V).** Land v2 `manager-caller` readers before writers. It preserves the exact Manager instance, linked current lifecycle and existing scope. It gains no stable endpoint grants, owner/operator elevation or `link-agent`. An old reader or unsupported host gets no unlinked substitute. Enable with A4.1, never separately. Main's scoped exchange lives in `implementations/auth/src/service-exchange-routes.ts:237-256,263-280` (**main**); the prototype's v2 explicitly rejects any view (see above).

**Shared retained seat record ([#10952](https://github.com/Cotal-AI/Cotal/issues/10952)).** Use one strict `cotal-seat-record/v2` with the previous fields, required `state: "live" | "asleep" | "ended"`, and optional server-acknowledged `agentUid` (absent for legacy). Read v1 as live and unlinked. Require `sleep: { at, sessionId, wakeBy? }` only when `state` is `asleep`; it is absent otherwise. `wakeBy` is the root credential's latest wake time on user-auth and is absent on static auth. `asleep` retains the exact resume entry and lifecycle, occupies its ID, holds its alias as a reservation and does not count against the seat ceiling. Wake starts the same run. The sleep writer writes only `live` and `asleep`, never `ended`. An `ended` record cannot be adopted or resumed, does not hold the alias and can be compacted only after its retained launch reference is safe. The seat file is keyed by space and name; keep the launch reference independently of terminal cleanup. Deploy the common reader one release before either writer. It leaves unknown versions or states alone: no adoption, cleanup or lifecycle retirement; malformed v1 keeps its current handling. On main, static custody can retire a lifecycle when its record does not parse (`implementations/manager/src/seat-custody.ts:189-198`, **main**).

This is one version bump for the shared seat shape, even if the two Manager command revisions land in either order.

## Needs owner decision

The recommendations below remain the baseline. The alternatives for decisions 3, 4 and 5 are proposals, not agreed changes. Please review every proposed public operation, wire field, refusal, version and persisted field in the inventory above together with this single decision list.

1. Require explicit human confirmation with a fresh provider token for granting or widening launcher permission, registering a launcher and deleting an agent, and require only the fresh provider token and exact target for revoking permission or ending a run.
2. Register each Manager or hosted launcher instance as its own protected key-backed principal rather than letting it reuse the owner's sign-in.
3. Keep a separate per-agent continuation grant to limit damage if the launcher key is stolen. Or let registration cover continuation of all its own agents for that owner and space, with optional narrowing and no second grant.
4. Keep a separate grant to clear a predecessor the launcher started. Or include that right in registration so the launcher can recover its own runs while the owner is away. Both choices require verified death and forbid stopping a live run.
5. Keep owner linking off where agents can reach the saved sign-in. Or enable it after one setup warning that shared-user agents are not isolated from each other or the sign-in. Until custody is protected, they can use that sign-in to continue a stopped agent and use its existing grants.
6. Apply the stated issue-time bound to owner links even when the mesh runs on the owner's computer, without applying it to session age.
7. Show which runs stay live after launcher permission is revoked and offer to end them separately rather than ending them automatically.
8. Let a delegated hosted launch create a new agent first, and allow continue later only if the owner selects it at intent admission and execution cannot substitute it.
9. Ask for the hand-started conversation's new-or-continue choice only on the connection-approval page, never from the conversation or its tool arguments.
10. Enable linking by default only on compatible authority and launcher paths once their release gates pass, and keep unadvertised or legacy modes unchanged.
11. Use “Start a new agent” and “Continue an existing agent” in the trusted terminal and connection-approval page, with no raw ID flag or model-facing selector.
12. Refuse a second live copy of a conversation, name the first run, and offer to end it or start a new agent instead of silently changing identity.
13. Make deletion permanent and refuse it while the current run is live or its settlement is unknown.
14. Begin persisted stable grants with exact-instance endpoint access and keep old lifecycle grants unchanged. Other persisted grant families need explicit review, but this does not hold back channel or tag rules evaluated at mint from the committed ID.
15. Expose owner-scoped lookup and link audit as inputs to hosted access policy and history without moving previous-run messages or merging history by name.
