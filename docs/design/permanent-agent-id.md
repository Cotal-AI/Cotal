# Permanent agent ID across launches

**Draft for decision.** This plan adds no product behavior. The foreground implementation on this branch is a prototype of how to fence issuance and retirement, not the sign-in model proposed here.

## Needs owner decision

Review the proposed names and fields in [the surface list](#surface-list), including private persisted fields. The list is a proposal, not an approval to ship. The remaining behavior decisions are:

- **Selection and forks.** Default to a new server ID on a new launch record, reuse the ID already in a trusted record, and offer an owned-agent picker only when a person chooses to continue an existing agent. Refuse the second copy of a live conversation. Do not silently create a different agent with different access. Offer an explicit new-agent choice instead.
- **Launcher limits and Manager access.** Default `link-agent` to one owner, one registered launcher and one ID. Allow an explicit create-only permission for a constrained launcher, including ordinary helper spawns. An agent can ask for a new helper under the existing spawn ceiling, not select an existing ID or use the launcher as a relay. Keep the existing scoped `manager-caller` view for linked seats only after it can verify the exact live link. A linked seat never falls back to an unlinked view. Revoking launcher permission stops future links and unreleased issuance, not an already issued run.
- **End versus delete.** End retires a run and keeps its ID. Deleting the agent permanently tombstones its ID. Prefer to refuse deletion while its run is live or settlement is unknown, rather than bundling eviction or allowing an undo.
- **Rollout and existing data.** Do not infer an ID from an alias or adopt an already issued run in place. Keep old grants bound to the old run. Opt in with an explicit stable grant and migrate a legacy agent on its next authorized fresh launch. Open and static spaces have no authenticated owner link path today. Prefer to add a protected space authority for those modes before claiming full coverage, not to treat a local file, static key or open broker as proof of human ownership.
- **History and hosted policy.** Expose an authenticated owned-ID lookup and link audit as inputs for later history, tags and hosted access-profile work. Do not merge history by name or change the meaning of a preexisting access profile here.

## What is settled

Every agent Cotal runs should have a permanent ID. The auth service draws it at random. The ID belongs to one owner in one space and does not confer access. One ID has at most one live run. A new run has a new lifecycle UID, even when it takes an existing ID or name. There is no per-agent private key or signed proof supplied by the agent.

An owner's launch uses their saved sign-in, not another approval. When the owner is absent, a launcher uses its own independently authenticated identity and a standing permission the owner granted once and can revoke. A saved sign-in that is no longer valid is a sign-in problem, not a reason to request approval for that agent again. Neither possession of an old run credential nor an ordinary right to spawn can authorize re-linking.

**Boundary with sleep and wake ([#10943](https://github.com/Cotal-AI/Cotal/issues/10943)).** Sleep stops the process but keeps the run. Wake uses that same lifecycle UID and its existing binding, so it neither links again nor asks for approval. Same-run reconnect, retained resume and managed handoff also do not link again. Part A covers a completely stopped and settled run followed by a new one, regardless of which launcher starts it. A missing process or a sleeping run is not proof that the preceding run has ended.

## A2: Issue the ID with the first credential

Keep the closed `agentid.<agentUid>` record and pure decision from `packages/core/src/agent-identity.ts:8-42,52-66,111-137`. Only the private account/space authority creates or changes the record. `current` means the last committed link, not a heartbeat. An immutable create reservation protects even an abandoned ID from reuse. Do not store a half-formed identity or transfer one across owners or spaces.

1. Auth derives the owner from a verified saved sign-in against the pinned IdP, or authenticates the registered launcher and reads its current owner-granted `link-agent` permission. For a relayed request, validate the host-observed original caller, target, selection and request ID against the serving registration. Reject unknown origin, an agent selecting an ID, and a launcher lending authority to a workflow driver or other agent. An authorized create-only helper launch uses the original caller's current scope ceiling too. Do not trust request-body caller names, environment markers or an actor secret as link authority. Today's ordinary token verification is in `implementations/auth/src/idp.ts:192-202`; Manager dispatch derives owner from the verified token in `implementations/auth/src/service-manager-routes.ts:418-429`. The foreground prototype instead verifies fresh purpose-bound approval in `implementations/auth/src/linked-agent-routes.ts:51-59,107-128`.
2. Before accepting a saved sign-in, require custody outside the launched agent's reach. Today's environment allowlist does not isolate the login stored under a shared home (`extensions/connector-core/src/launch.ts:8-18`, `implementations/auth/src/session-context.ts:19-27`). Use a protected desktop or launcher credential store and a trusted launch entry point that does not relay seat-originated requests. A deployment that cannot isolate the sign-in cannot enable that path yet. A launcher must not copy a person's saved sign-in into a seat or use it as its operating credential.
3. Journal the attempt, reserve the candidate ID if new, serialize the winner per ID, and reserve the lifecycle UID before writing a bootstrap grant. Pin expected identity, authority and registration revisions, target and scope. The bootstrap joins only its exact operation. At first root mint, stage the root and immutable binding, recheck the same authority, compare-and-set the identity, write the link audit and mark the journal ready. Release only through a final revision-pinned issuance gate. Connect and later mints verify the signed claim against the current binding, ledger, root/gate and head; they never resolve a stale bearer to a successor. This follows the prototype's durable admission and release seams (`implementations/auth/src/linked-agent-authority.ts:141-187,221-247`), replacing approval consumption with authority evidence described below.
4. Revocation and release must serialize on the relevant authority fence. For a launcher grant, acquire the same permission fence for revoke and final mint and recheck the expected revision while it is held; an identity fence separately serializes retire, link and delete for that ID. Order the fences consistently, and do not rely on a last read alone. If revoke wins, contain any pending bootstrap and do not release a credential. If release wins, normal exact-run retirement is how to end that run. A crash before commit resumes the exact attempt or closes its UID without releasing authority. A crash after commit completes the audit or retires the exact run; it never rewinds the link sequence. Keep admission off during restore until reservations, pending grants and fences reconcile. An exact authorized retry is idempotent.
5. A linked run occupies its ID until the exact lifecycle is durably terminal and usable authority is contained, including broker eviction. Presence, PID, expiry, an absent grant and a reused name cannot settle the predecessor. Use `conflict` for an occupied ID and `unavailable` if evidence or eviction is uncertain. An owner's saved sign-in can drive the existing exact-lifecycle retire action without the Manager. Cleanup uses the exact grant/UID, never a same-name successor. Audit link, unlink and revoke with trusted actor and time, and retain tombstones. `implementations/auth/src/linked-agent-authority.ts:131-138,281-304`, `implementations/auth/src/credential-ledger.ts:533-580` describe the prototype and retirement seams.

Deploy readers and issuance fences on all participating auth and callout instances before enabling linked writes. Readers that cannot understand version 2 refuse it. Keep legacy unlinked launches and existing lifecycle operations unchanged on old paths. If a requested link cannot be checked or verified, refuse before launch and never retry unlinked. Turning off new admissions must leave validation, recovery and retirement for already linked runs available.

## A3: Store policy on the agent, issue authority to the run

Start with exact endpoint caller grants. Add a stable grantee variant alongside the existing lifecycle grantee. A stable grant names an owned ID plus the existing endpoint, instance, approval and capability ceiling. Store it once under `servicepolicy.<agentUid>` and change it only on a grant or revoke operation, not at restart. The prototype's reader already restricts stable rows to direct service-owner grants on an exact instance (`implementations/auth/src/service-caller-stable-policy.ts:12-36`). Keep that first-cut boundary and the current command's authority and containment checks (`implementations/auth/src/service-host-contract.ts:172-176`). This is not blanket inheritance for every access system: grant families that still target a lifecycle keep that meaning until they gain their own explicit stable variant.

At mint, the signed claim selects a candidate stable policy, not a grant of access. Resolve that policy's `agentUid` through the authoritative current link and require it to name the exact requesting lifecycle and credential. Apply the stable policy only within existing root, endpoint-assignment, service approval, parent and scope ceilings. The former run cannot use the ID as a route to the successor's authority. Persist the stable policy/grant revision as a source of the issued authority along with exact lifecycle lineage, so revocation cuts off issued dependents as well as future mints. Recheck policy and link at release under the revocation fence. The actual credential, capability handle and broker subject remain lifecycle-bound. Going offline does not stop a stable policy from applying, and showing a claim is not sufficient to mint. Existing lifecycle policies stay on their old key with no automatic rewrite, migration or fallback by actor name. A later stable replacement for a legacy grant must be explicit and separately authorized. If both variants name one grant ID, fail closed rather than silently widening access. Index by the stable grant identity across all revisions so revoking it contains every still-valid issued dependent, not just those issued at the latest revision. Use the issued source index for containment (`packages/core/src/issued-authority.ts:579-595`).

Where no current record survives retirement, add a small retained launch reference rather than saving old run material. Do not reuse a reference chosen by alias, persona or working directory alone. Launchers pass references internally; people choose an agent, not an opaque ID.

## Ship and prove each step on its own

A2 is the foundation. A3, A4 and A5 depend on the A2 release, not on each other. Use A2's saved-sign-in and standing-launcher admission directly in A3's test rather than waiting for a production launcher. Test through real auth and broker boundaries with private test state. Run each linked client only against a host that advertises support; an upgraded client refuses a requested link on an old host without emitting an ordinary launch. An old client without a selector continues its legacy behavior. Do not claim all-path coverage until each enabled mode passes its own cell.
