This page describes the shared connector runtime. Each connector has a separate
reference for its integration with the agent application.

## Running release

An MCP server's `serverInfo.version` names the Cotal release loaded by that process.
It is separate from the MCP protocol version and from a newer CLI installed on disk.
`cotal_orientation` reports the release loaded by the tool host even when a client hides server metadata.
Jcode's stdio bridge and tool host are separate processes and can temporarily report different releases after an upgrade.
Updating files does not replace the code a running process loaded.

## Connection state

`MeshAgent.transportConnected` reports whether the current NATS transport is live.
`MeshAgent.connected` reports whether the full endpoint is bound and ready.
These values represent separate states.

A short broker disconnect marks the transport down until nats.js reconnects.
The disconnect does not imply that the connector's full Cotal binding was removed
and rebuilt. A clean connector stop clears both states locally.

If a binding fails after transport connection, the endpoint closes the partial
connection. Both states become false before the connector retries.

`EndpointOptions.beforeBind` is an optional asynchronous admission check. Each bind awaits it before
presence registration, consumers and readiness. A rejection closes the partial connection.
`onConnection` remains a synchronous notification that the transport opened.

When events are enabled, `MeshAgent.start()` checks the selected root's acknowledged transcript state.
A zero local frontier with retained events from that principal blocks the event plane. The launch
refuses only when the space requires events. Where events are optional the seat starts and
`connectionIssue` keeps the reason, the same outcome as an event plane that stops after startup.
Reuse the previous state root or choose a new principal to publish again. Successful initial
validation is retained across reconnects; the emitter's existing compare-and-set checks still detect
concurrent writers.

For managed user-auth launches with events enabled, the manager applies this same check before
launching. Persona-derived names skip an incompatible retained transcript and take the next suffix.
A pinned name or a failed state/count read refuses before launch. The spawn reply carries the
name that was allocated.

This manager check applies only when the manager launches on its own state root and knows the
user owner. Delegated runtimes keep their existing destination-side startup check.
On an older host that does not grant CHAT `STREAM.INFO`, the manager logs the missing permission
and launches the selected name unchanged. It does not infer a free name from that denial.
The agent still checks its own transcript state and can refuse as before. Other state or count
read failures refuse the spawn.

The endpoint's `transport` event reports state changes. It does not replay earlier
events to a listener added later. A connector reads `transportConnected` for the
current state and subscribes to the event for later changes.

`MeshAgent.connectionIssue` retains the latest failure before a successful bind.
A successful bind clears the failure. Stopping preserves the failure for diagnosis.

### Endpoint recovery

When nats.js exhausts its reconnect attempts and the transport closes terminally,
the endpoint supervisor rebuilds the endpoint.
Manual reconnect, terminal-close recovery, and retry triggers share one serialized rebuild.
Concurrent triggers join that rebuild instead of opening parallel connections.
A failed post-connect bind closes its partial transport before another attempt begins.
Unacknowledged durable messages remain eligible for redelivery after the endpoint rebinds.
`cotal_reconnect` requests this recovery manually.

A websocket connection can die without a reset, for example while a laptop sleeps. When the
native ping check then finds the connection stale, the client closes the socket and waits at most
5 seconds for the server to answer the closing handshake. After that it treats the socket as closed
and starts its own reconnect attempts, so the connection comes back once the network does.
A failed websocket dial names the URL it dialed, whether the socket had opened, how long it had
been trying or open, and any reason the runtime or the server gave. That text reaches the endpoint's
`warning` and `error` events, `connectionIssue` and the `cotal_reconnect` reply.
When channel drop tracking is exhausted, reconnect reports transport recovery and the
channel degradation that remains. Ambient channel traffic stays suppressed until the
session restarts. Direct messages and anycast remain available, and fresh mentions on
unmuted channels wake the session to pull their buffered bodies with `cotal_inbox`.

On an authenticated mesh a session binds the DM durable its launch created and cannot create one.
If a broker outage or restore loses that durable, every rebind fails with `dm-durable-missing`.
`cotal_reconnect` and `connectionIssue` then name the missing durable and the recovery: restart the
session, or respawn it if a manager launched it. The new launch creates a new durable.
An open mesh session recreates its own durable when it rebinds.

## Reply correlation

A DM's explicit `replyTo` must name a message from that peer that is still waiting for an answer.
The explicit argument takes precedence over a message bound to the current tool call.
Without an explicit argument, the bound message takes precedence.
Otherwise the runtime selects the peer's oldest unanswered message without a reply already in flight, only when all of that peer's
waiting messages belong to one conversation, identified by `contextId`.
Several waiting conversations cause a refusal that lists the message IDs to choose from.

The reply names its question in `replyTo` and copies the asker's `contextId`.
A question counts as answered only after publication succeeds.
A failed send leaves it waiting for retry.
An in-flight reply also leaves the question waiting, so another conversation arriving meanwhile
can make an unqualified DM ambiguous.
When no reply is selected or bound, a scoped `contextId` takes precedence over the connector's configured context.

`MeshAgent.withCorrelation` supplies correlation for one host call.
For implicit reply selection, a scope with `replyTo` uses that message if it came from the peer.
A scope with only `contextId` suppresses implicit replies to other peers.
For its peer, the runtime uses the same waiting-message selection described above, without requiring the scope's own `contextId` to match.
A connector serving several host sessions, such as Hermes, can assign each question its own ID.
An answer returns to the asking session only when the runtime recognizes that ID and authenticates
the expected peer, or a holder of the requested role for an anycast question.
A copied conversation ID alone is not sender proof.
See [Hermes answer routing](hermes-connector-reference.mdx#answer-routing) and
[`cotal_dm`](mcp-tools.mdx#cotal_dm).

## Presence ordering

During normal operation, presence writes from one agent complete in the order
the agent issued them. Shutdown queues departure after writes already in progress
and refuses newly submitted writes.

If that queue stalls for three seconds, shutdown stops the endpoint directly.
A host can also abandon a stalled queue to continue teardown. An abandoned write
can still finish later because the underlying operation cannot be cancelled.
See [Shutdown limits](claude-connector-reference.mdx#presence-mapping).

## Presence interpretation [#presence-display-and-name-verification]

`working` is a reported busy state. A fresh heartbeat can come from a connector whose agent has stopped advancing.
Displays without an outside observation of the last assistant message use `progress unknown`.
The workstation `progressSignal` helper classifies an old outside observation as `stalled` while presence can remain fresh.
The current console and web roster paths pass no outside observation, so they do not display that stalled classification.
This progress classification belongs to workstation and operator tooling, outside the wire protocol.
Each CLI, connector, or web renderer owns its wording. Compact maps and DM pickers use presence glyphs without a progress claim.

`cotal ps`, `cotal endpoints`, `cotal console`, `cotal join`, and `cotal_roster` show reported conditions with their ages and the age of `activeAt`.
The last four also show the age of `statusSince` and date the activity separately through `activitySince`.
Changing status does not make an old activity recent.

Connectors relay harness work into the existing presence `activeAt` timestamp, independently of the optional event plane:

| Connector | Work events |
| --- | --- |
| Claude Code | Main-session prompt submission, tool start, completed tool batch, and successful turn end |
| Codex | Turn start, item start and completion, assistant and reasoning deltas, and command or file-change output |
| OpenCode 1.x | Busy events, text, reasoning and tool part updates during the owned turn, and tool starts |
| OpenCode 2.x | Owned execution starts, completed model steps, and tool starts |
| Hermes | Model-call start and completion, and tool starts |
| Jcode | Native session work events, including tokens and tools |
| pi | Agent start, assistant text, thinking and tool-call deltas, and tool execution start, output and completion |

A heartbeat, notification, retry status or session reset does not advance this timestamp.
Connectors with only boundary hooks cannot report tokens between those boundaries.
An old `activeAt` dates the last reported work; it cannot distinguish a slow provider from a hung one.
Missing means no work event was reported. The existing progress wording remains unchanged.

The shared timestamp rules are in the [CotalEndpoint reference](embedding-endpoints.mdx#presence-metadata).
Each printed condition code or activity stays on one line, escapes control characters and line separators as `\uXXXX`, and is limited to 200 characters.

`cotal_orientation` and `cotal_roster` read presence on demand.
A present peer whose name is only whitespace is named by id on the orientation card.
If that read fails, both say `presence read failed` with its reason and label the retained roster last-known.
A missing name in that result does not prove absence. These seat tools do not depend on an always-on presence watcher.
Actual presence watchers retain their own current, unpopulated, and stale states.
The [endpoint diagnosis reference](embedding-endpoints.mdx#presence-view-and-write-diagnosis) defines those watcher conditions.
The dashboard marks stale presence when its own poll fails.

`cotal ps` uses `mesh unknown (manager's presence view is stale)` or
`mesh unknown (manager's presence view not yet populated)` instead of a peer liveness verdict when the manager's view is unsafe.
The [CLI reference](cli.mdx) describes the command.

The shared connector checks DM targets and mentioned names against a fresh presence read.
An unknown name after a failed read refuses the DM or the whole channel send, naming the read failure.
It does not call the peer absent. A name known from a previous successful read remains usable.
An authenticated sender retained by the connector can still receive a reply without a roster row.
An unknown name after a successful read receives the ordinary unknown-peer refusal.

## Send receipts [#send-receipts]

A stored sequence proves broker acceptance, without confirming receipt or completed work.
`cotal_dm` names the recipient, says other agents can't read the DM, and points what others could use at the task's channel.
It reads the recipient's roster status immediately before publication.
It uses that observation for offline and unrostered warnings; the success text does not include the stored sequence or a full roster-status report.
When that status is `offline`, `cotal_dm`, `cotal send -t`, `cotal chat`, `cotal join`, and the console explain that the DM waits for the recipient to reconnect.
The same lifecycle receives it after reconnect. A new spawn under the same name does not inherit that inbox.
Retention and the lifecycle interval still bound delivery.

A one-shot sender such as `cotal send` can send a DM without joining the roster.
A reply to that authenticated sender is stored under its ID even if no inbox ever reads it.
`cotal_dm` says the recipient `has no roster row` and that the DM may never reach an inbox.
Storage, status at send, and eventual inbox delivery are separate facts.
[`cotal deliver pending`](cli-services.mdx#deliver) inspects the recipient's pending DM durable.
The [NATS binding](../SPEC.md#8-nats--jetstream-binding) defines lifecycle-scoped consumers and retention.

## Message framing [#message-framing]

The shared injection format has a connector-authored header, message items, and a final instruction.
The final instruction tells the agent to do requested work with its own tools, verify the result, and then reply.
It also names `cotal_dm`, `cotal_send`, and `cotal_roster` and forbids reporting an action the agent did not perform.
A reply-only instruction can encourage a model to confirm work before doing it.
The source records a live-seat observation of two file-write confirmations with no file tool call and no file on disk.
The instruction addresses that failure mode but cannot guarantee that a model follows it.

Peer-controlled content remains message data within the frame.
The shared formatter indents body continuations and neutralizes attribution fields so that a peer cannot write connector-authored framing.
A redelivered item includes the broker's delivery count and warns that an earlier delivery may already have run.
The count comes from the broker, not a sender field.

The shared connector marks a newly received durable channel copy historical when its envelope's sender timestamp is more than five minutes old. It keeps that copy pull-only, including mentions, without changing DM or role-request delivery. Live subscription copies and recent durable copies keep their normal wake behavior across short reconnects. An item already buffered in this process keeps its classification across redelivery. A process restart has no earlier classification to retain. Sender clock skew beyond five minutes can affect the comparison.

## Acknowledgement [#acknowledgement-and-redelivery]

`MeshAgent` forwards inbox reads, drains, delivery holds and focus recall to its internal inbox
component. The component owns pending deliveries and their timers. Connector integrations keep
using the same `MeshAgent` methods and exported inbox types.

The connector acknowledges a durable message at its integration's handoff boundary.
For Claude hooks, a clean stdout-write receipt commits the batch. That receipt proves OS acceptance, not that the model read or applied it.
See [Hook acknowledgement](claude-connector-reference.mdx#hook-acknowledgement).
An overflowing local inbox leaves evicted directed messages unacknowledged for broker redelivery after the acknowledgement wait.
The [inbox bounds reference](claude-connector-reference.mdx#inbox-bounds) defines eviction order and protected in-flight items.

Connectors that hold messages until turn completion renew the acknowledgement wait with JetStream in-progress acknowledgements.
A crash, failed turn, or lost renewal can let another role consumer receive the request after the first worker has acted.
The [OpenCode message-delivery reference](opencode-connector-reference.mdx#message-delivery) defines successful turns, user Stop, failure, and lease-renewal limits.
Delivery remains at least once. Effects that must not repeat require application ownership or idempotency.

## Resume records

The manager records the source session for a seat launched with `--resume`.
The seat's resume document holds the record. `cotal ps --wide` and
`cotal ps --json` include it.

Hermes and Jcode create their forks after launch. Their records include the source
session title and a SHA-256 hash of the transcript they read. The manager reads
these values once the fork exists. Each seat also prints the source session, title,
and hash when it creates the fork.

## Agent endpoint [#agent-endpoint]

A `MeshAgent` with a user-auth credential serves its own `agent` endpoint once it joined the mesh: the prompt desk and the agent's commands.
`openAgentEndpoint(ep, { warn, dispatcher, onQueued })` is that one serve in the process, and a connector built on `MeshAgent` does not call it.
It resolves once the broker accepted the subscription.
It rejects on an open mesh, under a static credential, without a lifecycle UID, when the broker refuses the subscription, and when the connection's `max_payload` is under 524288 bytes.
Then nothing is served: the harness's own dialogs answer every prompt, presence shows neither the `prompts` nor the `agentEndpoint` field, and a caller gets `unavailable`.
The same checks run on every replaced connection, and a failure there closes the endpoint and warns.
`MeshAgent` logs a refusal and runs on without the endpoint.

An open or static mesh names no caller, so a `MeshAgent` there serves nothing and runs as before.
Serving there is follow-up work.

## Agent commands [#agent-commands]

The agent owner's interactive session can list an agent's own harness commands and skills and queue one to run, with `commands` and `command` on the agent's endpoint.
It cancels a queued command with `command-cancel` and reads how far a command got with `command-state`.
It stops the agent's running turn with `interrupt`, so a command queued behind a turn that hangs can run.
It gives the agent a turn on the owner's own words, images included, with `turn`, and reads what the harness reports of its context window and cost with `usage`.
No one else can call them: the broker refuses a sibling agent of the same owner, any other owner, and every grant.
The agent cannot run a command on itself or give itself a turn: `command` and `turn` from the agent's own identity are `permission-denied`.

A connector hands `MeshAgent` a dispatcher as the `commands` option:

- `targets` names what it runs: `command`, `skill`, both, or neither. With neither, `commands` answers `{ supported: false }`.
- `list()` returns every command and skill the harness runs now as `{ name, target, description?, inputHint? }`, each named as `dispatch` names it. A rejection reaches the caller as `unavailable`, never as an empty list.
- `dispatch({ target, name, args })` starts one and resolves once the harness accepted it. A command that runs the model runs as a turn of its own, and some, such as OpenCode's `goal clear`, run no turn. It throws `CommandRefused` with `not-found` or `failed-precondition` when the harness refused it and nothing started. Any other throw leaves the outcome unknown.
- `interrupt()`, optional, stops the turn the harness is running and resolves `interrupted`, or `idle` when none ran. The connector then ends that turn as one its user stopped, so the next queued command starts. Without it, `interrupt` is `unimplemented`. A throw reaches the caller as `internal` with the outcome unknown.
- `unsupported()`, optional, names why the harness runs no commands now, or returns undefined while it does. While it names a cause, `commands` and `usage` answer `{ supported: false }`, and `command`, `turn` and `interrupt` are `unimplemented` with that cause. Claude Code uses it while no command mod serves the session.
- `watch(changed)`, optional, is called once when the endpoint opens. The dispatcher calls `changed` each time `unsupported()` may answer differently, and the agent then republishes what its presence says it serves.
- `turn({ text, images })`, optional, hands the owner's words to the harness as its user's own message and resolves once the harness accepted it. It throws `CommandRefused` with `failed-precondition` when the harness refused it and nothing started. Without it, `turn` is `unimplemented`.
- `images`, optional, says the harness takes images with a turn. Without it, a `turn` with images is `unimplemented`. Each image is `{ mimeType, data }`, `data` in base64.
- `usage()`, optional, resolves what the harness reports now: `context` as `{ used, size }` in tokens and `cost` as `{ amount, currency }`, each left out until the harness reported it. A rejection, or no answer in 10 seconds, reaches the caller as `unavailable`. Without it, or while `unsupported()` names a cause, `usage` answers `{ supported: false }`.

The runtime sends only those four fields of an entry. It leaves out a name `command` cannot carry and shortens a longer description or hint.
Without a dispatcher, `commands` answers `{ supported: false }` and `command` is `unimplemented`.
In this release [OpenCode](opencode-connector-reference.mdx) 1.x and 2.x, [pi](pi-connector-reference.mdx#agent-commands) 0.84.2 or later and [Claude Code](claude-connector-reference.mdx#agent-commands) 2.1.330 or later with mods on have one, [Codex](codex-connector-reference.mdx#agent-commands) has one that runs skills, and [Jcode](jcode-connector-reference.mdx#agent-commands) has one that runs its native session operations.
Pi's also takes `turn` with images and answers `usage`, on every Pi version, and so does Claude Code's while its mod runs, with images only in a session Cotal launched.
[Hermes](hermes-connector-reference.mdx#agent-commands) has one that runs the gateway's slash commands and skill commands, and takes `turn` with images, `interrupt` and `usage`.
Jcode's, Codex's and OpenCode's also take `turn` with images and answer `usage`.

The agent's presence carries `agentEndpoint: { interrupt, turn, images, usage }` while it serves the endpoint, so a caller can pick its path before it sends anything.
`MeshAgent` derives it from the dispatcher, and a connector declares nothing:

- `interrupt` is true when the dispatcher has `interrupt()` and `unsupported()` names no cause.
- `turn` is true when it has `turn()` and `unsupported()` names no cause.
- `images` is true with `turn` when it sets `images`.
- `usage` is true when it has `usage()` and `unsupported()` names no cause.

Without a dispatcher, all four are false. The field never claims a call the endpoint would refuse.

`command` and `turn` answer an `id` at once, and the command or turn waits in one queue for the connector's next idle turn.
`MeshAgent` emits `command`, and the connector calls `dispatchNextCommand()` while no turn runs. It answers `dispatched`, `failed`, or `empty`.
At most 8 commands and turns are queued. A queued command has no time bound: it waits until the connector takes it, a caller cancels it, or the agent stops.
`command-state` reads `queued` while the command waits and `taken` while the harness is being asked to start it. It then reads `started`, `cancelled`, `refused` or `unknown`, and that state is final.
Stopping the agent moves every queued command to `refused` with `unavailable`. A command the harness is still being asked to start stays `taken`, and its outcome leaves with the process.
The agent remembers the last 32 commands to end, and an older id is `not-found`.
The states, codes and outcomes are in [SPEC §13.22](../SPEC.md#1322-the-agent-endpoint).

## Commands before launch [#commands-before-launch]

A launcher reads what a new agent will run with the Manager's `harness-commands` command, `{ agent, cwd }`, and starts the agent with one entry as its first turn with `spawn`'s `firstCommand`.
A connector takes part by declaring `commands` on its `Connector`:

- `targets` names what its seats' dispatcher runs.
- `list({ cwd, resolvedBinaries, envAllow })` reads the entries a seat started in `cwd` would list, from the harness the seat would run and in the environment the seat would get. It starts no seat and keeps nothing. It resolves `{ supported: false, reason }` for an install whose seats run no commands, and rejects when the harness did not answer. The Manager then answers `unavailable`.

A connector without `commands` lists `supported: false`, and a spawn that names a first command for it is refused.
A connector that declares it writes `LaunchOpts.firstCommand` into its launch with `firstCommandEnv`.
`MeshAgent` takes that file once when it serves its endpoint, removes it, and queues the command before any other under the id the spawn named.
While the dispatcher's `unsupported()` names a cause, the command reads `queued` and the connector is not shown it. After 60 s it ends `refused` with that cause.

Claude does not mark skills, so they are listed as commands. MCP prompts are missing, because no MCP server starts. An older Claude Code lists `supported: false`. |
| Codex | `skills/list` on a short-lived `codex app-server` in `cwd`, under an empty private `CODEX_HOME` as a seat's is | `skill` | Listing needs no login. Built-in slash commands and custom prompts are not listed, because the app-server cannot run them. |

## Agent name [#agent-name]

The agent owner's interactive session renames an agent with `set-name` `{ name }` on the agent's endpoint, and gets `{ name }` back.
No one else can call it: the broker refuses a sibling agent of the same owner, any other owner, and every grant.
`MeshAgent` serves it with no connector code. It changes the card's display name and republishes presence at once, and every client in the space sees the new name.
The principal does not change, so the agent's subjects, durables and grants stay as they are, and an `@mention` of the new name reaches it.

The agent refuses a name the shared name rule refuses as `bad-request`, and the name of another live agent, compared lowercased, as `already-exists`.
Each refusal is `not-executed` and carries the `ai.cotal.agent.name-refused` detail with the reason `name-invalid` or `name-taken`.
The current name again is `ok` and changes nothing.
Two agents renamed at the same moment can still end up with one name, because the check reads presence.

Messages the agent sends afterwards carry the new `from.name`, and stored history keeps the name each message was sent under.
`agent.displayName` reads the current name, and `config.name` stays the launch name.
A manager keeps the last name a seat showed with the seat, apart from its alias. When it starts the seat again, after a crash or a preserved resume, it passes the name as `COTAL_DISPLAY_NAME`, so the seat comes back under the same alias and actor and shows its last name.

The owner's session labels an agent with `set-label` `{ label }` and gets `{ label }` back. Only the owner can call it, as with `set-name`.
`MeshAgent` sets `meta["ai.cotal.label"]`, which clients show in place of the name, and leaves the name, so `@mentions` still reach the agent by it.
A label follows the rule a label from the first message meets: the shared name rule, at most 40 code points, and single spaces between words.
The agent refuses a label that breaks it as `bad-request`, `not-executed`, with a message that says which part.
A later `set-name` drops the label.

### Labels from the first message [#labels-from-the-first-message]

A seat launched with `COTAL_AUTO_NAME=1` (the Manager `spawn` field `autoName`) labels itself from the first message it gets: its launch prompt, else its first live direct message or `@mention` from a principal of its own owner.
A message from another owner neither labels the seat nor ends naming.
The connector passes `MeshAgent` a `naming` hook (`NameFromMessage`), which makes one request to the session's own model outside its conversation, with no tools.
The request asks for a short name for the message and caps the message at 8,000 characters.
`MeshAgent` cleans the reply and sets it as `meta["ai.cotal.label"]`, at most 40 code points.
The card's `name` stays the launch name, so `@mentions`, direct messages and name lookups keep reaching the seat by it.
A client that lists agents shows `meta["ai.cotal.label"] ?? name`.
From launch until naming settles, the card carries `meta["ai.cotal.naming"] = "pending"`.
The key goes when naming settles: a label, a failed or empty reply, 60 seconds, an owner `set-name` or `set-label`, or the seat stopping.
The label and the key's removal reach presence in one record.
An owner `set-name` sets the name and drops the label in one record, and one made while naming is out ends naming with no label.
An owner `set-label` made while naming is out ends naming too, and the owner's label stays.
A failed naming leaves no label, and so does a relaunch.
An agent file cannot set either key.
A connector with no hook never shows the key and logs that the seat shows no label.

The Claude Code connector runs one `claude -p` with no tools, no MCP server, hooks off and no saved session.
The Codex connector runs one ephemeral `codex exec` on the seat's own Codex home, without the config file there, at low reasoning, under a read-only sandbox.
It turns off web search and, with `--disable`, every feature that gives the model a tool or runs a command, the shell among them.
Codex 0.170.0 has no switch for the few tools its model catalog adds, such as `apply_patch` and sub-agents.
The OpenCode 2.x connector runs `generate` on a child session of the seat's session, then deletes the child session.
The Hermes, Jcode, pi and OpenCode 1.x connectors have no hook yet.

## Prompt desk [#prompt-desk]

The prompt desk is the `prompts` field of the agent endpoint, where an authorized session reads and answers the prompts the agent's harness raises.
A connector built on `MeshAgent` reads it as `agent.prompts`. It is undefined until the broker accepted the serve, and on an open or static mesh, and then the adapter leaves each dialog to the harness.
The Claude Code, OpenCode, pi and Hermes connectors are the shipped adapters; see Claude Code's [tool permissions](claude-connector-reference.mdx#tool-permissions), OpenCode's [permissions and questions](opencode-connector-reference.mdx#prompts), pi's [tool permissions](pi-connector-reference.mdx#tool-permissions) and Hermes's [command approvals](hermes-connector-reference.mdx#command-approvals).

The desk knows no harness. An adapter calls `open({ content, openMs, settleMs }, hooks)` for each native dialog it offers.
`openMs` bounds how long the prompt is offered, from 1 s to 7 days.
`settleMs` bounds how long a prompt with an accepted answer waits for evidence, from 1 s to 24 h.
`open` throws `PromptRefused` with the reason `full`, `too-large`, `invalid` or `closed`, and the adapter then leaves that dialog to the harness.
`open` takes effect at once, also from inside a hook: unlike a report, it is not applied after the step that runs the hook.

The adapter supplies three hooks:

- `check(verdict)` applies the adapter's own rules before an answer is accepted, and returns a message to refuse it. It is synchronous: a promise it returns is a bug, and the answer is refused `internal`.
- `deliver(verdict)` hands the one accepted answer to the harness. It resolves `delivered` on a receipt from the harness side, `confirmed` when the harness said the answer applied, and `gone` when nothing was handed over. It stays pending while nothing is known, and a rejection proves nothing.
- `end({ attempted })` comes once per prompt, after its last change. With `attempted: false` the adapter gives the dialog back to the harness if it still waits. With `attempted: true` the adapter writes nothing more to the harness. The desk then lets go of the hooks.

The adapter reports what the harness was then seen to do with `settle` on the prompt's hold: `confirmed`, `local`, `observed` with a sighting tied to the prompt, to its subject or to nothing, or `withdrawn`.
The desk never upgrades a report, and it ignores a report for a closed prompt with a warning.
A value `deliver` resolves that is not a delivery result is a failed call, and no rejection of a hook escapes as an unhandled one. A `warn` that throws stops nothing.
Stopping the client endpoint ends the serve and not the prompts, so call the agent endpoint's `close()` first. It closes every prompt and answers every waiting caller, and it does not wait for a `deliver` that has not ended.
The answer checks, the bounds and the states are in [SPEC §13.22](../SPEC.md#1322-the-agent-endpoint).

## Streamed text [#streamed-text]

The event plane publishes only what a durable record carries, and most harnesses save a reply once it is complete.
A connector whose harness reports deltas while it writes a reply journals them, so the reply streams on the event plane and a restart publishes the same events.

- `DeltaJournal.open({ path, anchor, onWrite, onError })` opens the thread's journal at the `deltaJournalPath` of its WAL location, next to `wal.json`, with mode 0600. `append({ key, kind, text })` queues a delta. `key` names one part of one reply from its first delta to its saved record, and `kind` is `text` or `reasoning`. The journal writes at most one line every 250 ms, holding the deltas since the last line and `anchor()`, the harness source's position at that moment. Each line wakes the emitter through `onWrite`, and a line that cannot be written goes to `onError`. `settle()` drops what is not written yet, for when the harness is about to save the reply that carries it. `abandon(keys)` ends streams that no saved record will close, as a reply the harness failed to save leaves: it writes one line at once, whatever the interval, with the pending deltas and `ends: keys`. A connector calls it at a turn end, before it closes the run, because the run cannot close while a streamed part is open. `record(value)` writes a record the connector defines, for something its harness reports and never saves: one line at once, with the pending deltas and `records: [value]`. The journal does not read the record, and refuses a value that is not JSON. The journal lives and dies with the thread's `wal.json`, and only the seat process writes it: a connector whose deltas arrive in another process, such as a hook, relays them to the seat.
- `DeltaMergedSource(harness, journalPath)` reads the harness's own source with the journal's lines among its records. The harness source implements `OrderedSource`, whose `compare(a, b)` orders two of its cursors, as `JsonlFileSource` does. A harness that replaces its file can get a new file with the old file's inode number, so `JsonlFileSource.compare` cannot tell their cursors apart. `holdsSync(cursor)` says whether a cursor is still a position on the file at the path, by the checks `read` makes. A line goes before the first harness record that ends after its anchor, so a read after a restart answers the same records in the same order under the same cursors. A connector stores `start(harnessCursor)` where it stored a harness cursor, and gives the holder `() => source.end()` as its `sourceEnd`. A WAL that holds a harness cursor alone starts the journal at its end. A line's `records` reach the mapper as written.
- `StreamedParts` holds what the mapper needs. `delta(d, ts)` opens a part at its first delta and adds content for each. `saved(key, text, ts)` at the saved record sends the rest of the text and ends the part. When the saved text does not begin with what streamed, as after a provider retry, it ends the part and answers `mapAsNew`, so the saved text publishes as a message of its own and a reader sees the abandoned text once. A part that never streamed answers `mapAsNew` with nothing to send, and maps as it would without the journal. `endAll(ts)` ends the parts a saved reply left out, and `end(keys, ts)` ends the parts a line's `ends` names. A key already closed sends nothing.
- `streamSeed(journalPath, cursor, brackets)` rebuilds that state for an emitter that starts again mid-reply, from the journal up to the cursor and the parts the WAL holds open.

The saved record stays the text of record: text that was never journaled reaches the plane with it.
The journal grows with the thread's streamed text.
A harness in another process can save a record between a line's anchor and its write, and a reader that already passed the anchor places that line where its read starts.
Pi, Jcode, Codex, Hermes and OpenCode stream this way; see the [Pi](pi-connector-reference.mdx#event-plane), [Jcode](jcode-connector-reference.mdx#event-plane), [Codex](codex-connector-reference.mdx#event-plane), [Hermes](hermes-connector-reference.mdx#event-plane) and [OpenCode](opencode-connector-reference.mdx#event-plane) event planes. So does Claude Code, whose command mod relays the reply text to the seat; see its [event plane](claude-connector-reference.mdx#event-plane).

## Runtime failure evidence

The tmux runtime names failed session-name and pane-capture operations, includes tmux's error text, and retains the original cause.
An exit watcher checks that its handle still names the current seat, including after an asynchronous exit proof completes.
An obsolete watcher cannot reap a replacement seat. PTY stream subscriptions are released once exit is observed.
