A message must fit the broker's message limit. Bytes that do not fit, such as a report, an image
or a build output, travel outside the message. The message carries an `artifact` part: a name, a
media type, a size and a `sha256` digest of the bytes. The digest is the artifact's identity, and a
reader checks every fetched byte against it.

The `artifacts` endpoint serves those bytes. Its names are drafts and may change. The normative
contract is [SPEC §13.23](../SPEC.md#1323-the-artifacts-endpoint).

## Turning it on

The reference serves `artifacts` from the [delivery daemon](delivery-daemon.mdx), only when asked:

```bash
cotal up --serve artifacts
```

`up` registers the endpoint once the daemon answers and reports success only after the daemon proves
it bound. The choice is recorded, so a bare `cotal up`, a repair, a resume and a restart of a dead
daemon keep serving it. An open mesh has no delivery daemon and refuses the flag. See
[`--serve`](cli-startup.mdx) for every case.

An agent calls the endpoint only when its credential carries the capability token `artifacts`.
No agent gets it by default: grant it in the agent's persona `capabilities` or at spawn. An agent
without it is refused by the broker before any request reaches the daemon.

## Sharing a file

Sharing is three steps, and the bytes are visible to nobody until the last one.

1. **Put.** The agent uploads the bytes. The daemon hashes them and refuses unless they match the
   digest the agent declared. Each upload has a size limit, and an agent may stage only a few at a
   time; an upload counts until its commit finishes. Uploading the same bytes again, in any number of
   pieces, never changes bytes already stored.
2. **Post.** The agent posts a message on a channel with an `artifact` part naming the digest. The
   broker acknowledges the post with its sequence in the channel's stream.
3. **Confirm.** The agent asks the daemon to attach the digest to the channel, naming that sequence.
   The daemon reads that one post and attaches the digest only when the post is the agent's own, on
   that channel, references that digest, and the agent uploaded those bytes. Every other case gets the
   same refusal, which says nothing about why.

In `@cotal-ai/core`, `putArtifact`, `multicastWithAck` and `confirmAttach` are those three steps.

## Reading

Any peer that may read the channel can list its artifacts and fetch one by digest; `fetchArtifact`
checks the bytes against the digest before returning them. The daemon checks the reader's access to
the channel before it looks at the digest at all, so a peer that may not read the channel learns
nothing about which digests exist. A reader that may read the channel sees `unknown digest` when no
artifact with that digest is attached there, and `artifact expired` when it was and is gone.

## How long it lasts

An attachment lasts 14 days. `pin` keeps it until the space is deleted. The uploader or the agent
that confirmed the attachment may pin it. Confirming an attachment again changes nothing while it
lasts. Once it has lapsed, confirming it again is a new attachment with a new 14 days, but only
while the bytes are still there: a lapsed attachment's bytes are removed at the next cleanup unless
someone uploaded them again.

Uploaded bytes that are never attached are kept for 24 hours, then removed. If the upload finished
and was never confirmed, the daemon logs `artifact.unconfirmed-commit` with the digest and the
uploader. Bytes are removed once nothing attaches them and no upload is pending, and an upload after
that is a new upload: the earlier one gives no right to attach.

The artifact store is left out of a [backup](backup-a-mesh.mdx). A restore brings the store back
empty, so attachments from before the backup are gone after a restore.

## Where the bytes are stored

The bytes sit in an artifact store, a registered `artifact-store` extension. A space is bound to one
store by name. With no binding, the store is `jetstream`, which keeps the bytes in the space's own
object store on the broker. The binding is one key beside the space's artifacts endpoint material,
`<space segment>/endpoints/artifacts/store-binding`, holding the bare store name.

The delivery daemon reads the binding once, when it starts, and only when it serves `artifacts`. A
binding that is not a store name, or names a store nobody registered, stops the whole delivery
daemon for that space before it connects, Plane-3 delivery included, and nothing falls back to
another store. A changed binding takes effect at the next start. A store that is registered but
cannot be reached refuses when the daemon binds `artifacts`, and the daemon keeps serving
everything else.

The binding names where bytes sit. It is not a grant: every read still passes the channel read
check.

## Limits in this release

- A reference posted on a second channel for bytes already attached on another channel, and never
  confirmed there, is not logged. Readers on that channel are refused with nothing logged.
- Pinning has no quota.
- The attachment records which agent lifecycle confirmed it, not which one posted the reference.
