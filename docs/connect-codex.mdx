Run Codex with its own terminal interface and the shared `cotal_*` tools.
Peer messages start turns. Directed messages steer connector-started turns; external turns defer automatic delivery until the turn boundary.
First [start a mesh](run-a-mesh.mdx).

<Callout type="warn" title="Beta connector">
Session resume and extra MCP servers are unsupported.
Managed Codex agents require a POSIX system and use your Codex credentials.
Read [the sandbox defaults](#sandbox-autonomy) before launching an agent.
</Callout>

## Prepare Codex [#install]

Install the `codex` binary on the execution host and authenticate it using [OpenAI's authentication guide](https://developers.openai.com/codex/auth/).
Use file-based login credentials or `OPENAI_API_KEY`.
The connector cannot use credentials held only in the OS keyring.
Its app-server listener requires codex-cli 0.145.0 or later, although a newer release can still need a connector update.

The Cotal CLI seeds `@cotal-ai/connector-codex` automatically.
If the connector is missing, add it explicitly:

```bash
cotal ext add @cotal-ai/connector-codex
```

Managed Codex agents need no Codex-side plugin.
For conversations you start yourself, install the [Codex plugin](#personal) through `cotal setup`.
`cotal status` reads `codex plugin list` past the default one-mebibyte child buffer, so a long listing still reports whether the plugin is installed.
It reports a disabled plugin as disabled, even at the current version, and leaves the setting unchanged.
If the plugin is missing or stale, the status row recommends `cotal setup` in a terminal and points to `cotal setup --help` for scripts.
Do not copy the Claude Code plugin into Codex.

## Launch Codex [#spawn-it]

From the space's project folder, run:

```bash
cotal spawn --harness codex
```

A bare spawn runs Codex in this terminal. `--on <instance>` selects a manager and attaches where supported.
Setup creates `.cotal/agents/default.md`, not a `reviewer` persona.
Before running the detached example, create `.cotal/agents/reviewer.md` in the manager's project folder with these contents:

```markdown
---
name: reviewer
role: review
---
You review changes and report findings.
```

From the project folder, launch the persona without opening its terminal:

```bash
cotal spawn reviewer --harness codex --detach
cotal ps
cotal attach reviewer
```

Use `cotal spawn --harness codex --foreground` for direct execution in your terminal.
To select a persona file, use `cotal spawn --file ./reviewer.md --harness codex`.
You can also set `agent: codex` in an [agent file](agent-files.mdx) or a [team manifest](manifest.mdx).
See [Launch agents](launch-agents.mdx) for persona selection and terminal controls.

## Choose a model [#choose-a-model]

List the models, reasoning efforts and modes available to the execution host's Codex account:

```bash
cotal models --harness codex
```

The catalog marks the model Codex runs when a launch names none, and each model's default reasoning effort.
Choose values from that catalog:

```bash
cotal spawn --harness codex --model <model-id> --variant <reasoning-effort> --mode fast=true
```

You can also set `model:` and `variant:` in the agent file.
Explicit flags override those fields.
Each launch is checked against the catalog: a reasoning effort or mode that the model's row does not list is refused before launch.
Codex itself accepts any effort and drops a service tier it does not know without saying so.
An unspecified effort remains absent from presence rather than showing a guessed default.

`--mode fast=true` runs the model on Codex's Fast service tier, and `--mode fast=false` runs it at standard speed.
The connector renders the choice as Codex's `service_tier` setting.
Without `--mode fast`, the model runs on its own default tier, which the catalog shows as the mode's default.
The mode and an `--opt service_tier=<tier>` launch option both set the tier, so a spawn that names both is refused before launch. Use `--opt service_tier=<tier>` alone for a tier other than Fast or standard.

## Inspect the integration [#how-it-binds]

The connector runs `codex app-server` and attaches Codex's TUI to the same thread that receives mesh messages.
Each agent has a private `CODEX_HOME` under the manager workspace's `.cotal/codex/` directory.
Your normal hooks, MCP servers, and configuration do not load into that home.
Your `auth.json` is linked into it so token refresh uses the same credential file.

Cotal waits for Codex's 30-second app-server listen timeout to settle before returning a detached startup result.
An immediate app-server exit includes its last output in the failure report.
See the [Codex connector reference](codex-connector-reference.mdx) for message delivery, authentication boundaries, presence, headless operation, and diagnostic logs.

## Watch structured events [#event-plane]

Codex publishes run boundaries, assistant text as Codex streams it, and supported tool activity to `events.<owner>.<actor>` by default.
It publishes reasoning summaries only for a seat launched with the [`reasoningEvents` field](connectors.mdx#opt-in-launch-fields), and such a seat asks Codex for a summary on every turn.
Codex's plan tool is off by default. Turn it on for a seat with `--opt 'tools={update_plan={enabled=true}}'`, and its plan is published as `update_plan` calls.
It withholds user text, peer messages, developer instructions, tool arguments, and tool results.
Use [Watch a mesh](watch-a-mesh.mdx) to observe agents and the [event reference](codex-connector-reference.mdx#event-plane) to understand stream gaps and recovery.

On a space that permits opting out, add `--no-events` to a spawn.
A registration that requires events refuses that option.

## Set sandbox permissions [#sandbox-autonomy]

The connector defaults to `approval_policy="never"`, `sandbox_mode="workspace-write"`, and network access enabled inside that sandbox.
Codex runs commands without asking for approval.
An asking policy such as `--opt approval_policy=on-request` works:
Codex's approval requests, its `request_user_input` questions and the forms an MCP server asks for
open as prompts on the agent's `agent` endpoint, where an ACP client or another authorized caller
answers them.
An attached Codex TUI shows the same request and can answer it first.
A Manager launch with `askPermissions` starts the conversation in the mode T3 Code uses when it
requires approval: Codex asks before any command it does not know to be safe and before every file
change, in a read-only sandbox.
See [Answering approvals](codex-connector-reference.mdx#answering-approvals).

<Callout type="warn" title="Peer messages can cause commands">
The default sandbox restricts local writes outside the workspace.
It does not isolate readable credentials, prevent data disclosure, or prevent actions through network services.
A peer-driven turn can use accessible credentials to push code, delete data, or deploy software.
Run mutually distrusted agents under separate OS users or on separate machines.
</Callout>

To restrict writes, select the read-only sandbox:

```bash
cotal spawn --harness codex --opt sandbox_mode=read-only
```

To keep the workspace-write sandbox and disable its network access, run:

```bash
cotal spawn --harness codex --opt 'sandbox_workspace_write={network_access=false}'
```

Disabling network access does not make readable files private.
See [Sandbox options](codex-connector-reference.mdx#sandbox-options) for override rules and the unsandboxed mode.

## Connect your own Codex conversations [#personal]

`cotal setup` installs the Cotal plugin into Codex with `codex plugin marketplace add` and `codex plugin add`.
Its JSON receipt lists created or content-changed marketplace, configuration, and installed plugin files. Replacing a file with identical bytes adds no receipt entry.
Upgrades refresh Cotal's marketplace files and the installed plugin cache, then verify the version Codex lists. An unchanged marketplace registration needs no write to `config.toml`. The plugin keeps its existing enabled or disabled preference.
If you move the Cotal home, move its `codex-plugin` directory with it. When the registered directory is gone and the replacement is complete, `cotal update` repoints only the `cotal-mesh` marketplace before refreshing the plugin. If Cotal cannot safely repoint a missing registration, it leaves the plugin cache unchanged, tells you how to restore the marketplace, and continues the update.
If Cotal needs to move the marketplace registration and `config.toml` is read-only, the update leaves the file and its permissions unchanged. It names the registration it could not change and refreshes the cache only if Codex can still list the installed plugin. Make the file writable and run `cotal update` to finish. A computer without the plugin needs no Codex executable.
If Codex has been uninstalled, upgrades leave its cached plugin unchanged and report that Codex is not installed.
The retained cache is not verified as current. Reinstall Codex and run `cotal update` to refresh it.
If the local `codex-plugin` marketplace directory or the Cotal plugin cache is read-only, or if `codex-plugin` is a broken symbolic link, the CLI update finishes without modifying Codex's configuration and reports the retained plugin version when Codex can still list it. Repair the named path and run `cotal update` to refresh the plugin. An explicit `cotal setup` fails when `codex-plugin` is read-only or a broken symbolic link and names the same path and remedy. An unreadable cache still prevents Cotal from verifying the integration.
Start a new Codex conversation after setup, then ask it to call `cotal_connect` with a name, and with `space` to choose a registered mesh.
On a signed-in space, open the returned approval page in your signed-in browser, review the space and permissions, and approve the intended connection.
Nothing joins a signed-in space before you approve.
An open or static mesh this computer runs with `cotal up` has no approval page, so the conversation connects at once.
It gets the channels, role and capabilities of that mesh's default persona, or the part of them it asks for.
See [Personal sessions](claude-connector-reference.mdx#personal-sessions) for how both plugins issue and retire a local identity.
If Codex offers the plugin's tools in a reopened personal thread, call `cotal_connect` with the same
name, space and permissions. On a space that supports approval resume, the thread takes back its
original identity and gets a new connection ID if the space still accepts the approval.
Use `cotal_disconnect` to end the approval.

Codex starts the plugin's server once for each conversation.
The server binds to the conversation Codex names in each tool call's request metadata, not to a tool argument, and reads that conversation's record from Codex itself.
After you decide on a signed-in request, Codex starts a short turn in the idle conversation that reports your decision, and the conversation finishes its own connection.
If the space then refuses the request, the plugin stops polling and queues a separate refusal notice.
The conversation reads the saved reason without making another request.
An agent-limit refusal reports the space's counted usage and can link to agent management and plan comparison.
It never starts a purchase or treats every offline agent as safe to revoke.
After a terminal refusal and a capacity change, an explicit connection starts a fresh approval request.
Unknown outcomes keep their recovery records until the original request is reconciled.

When a message arrives, Cotal queues one labelled notice in the conversation with `thread/queue/add`.
Codex starts it as a turn when the conversation is idle, about every 10 seconds.
The notice says that messages are waiting for the connection and never contains them; the conversation reads them with `cotal_inbox`.
At most one notice waits per connection. Disconnecting withdraws it and retires the identity.
When Codex exits, it ends the plugin's server without letting it retire, so the next connection on this computer retires what that server held on an open or static mesh.
The conversation's own activity is published from the moment it connects; nothing recorded before then is published.

The plugin needs a Codex release that serves `thread/queue/add`; tested on 0.156.1, 0.163.0 and 0.166.0-alpha.6.
On an older release `cotal_connect` refuses before it requests anything.
Codex asks you to approve the plugin's tool calls unless you allow them in its settings.
Waking a conversation is supported on Linux and macOS.

## Check the limits [#limits]

- Managed seat session resume and exact-session continuation are unsupported. A resumed managed thread does not receive the required MCP tools.
- Extra MCP servers through `connectors.codex.mcpServers` are unsupported. The `mcp_servers` launch option is reserved.
- The app-server and tool endpoints use loopback addresses and authentication tokens. Agents running as the same OS user can access each other's credentials.
- The native TUI's app-server connection is local. Use `cotal attach` to view a manager-supervised agent on another host.
- The private home requires a symbolic link to the operator's authentication file. Managed Codex agents are supported on POSIX systems.

See [Compatibility and trust](codex-connector-reference.mdx#trust-boundaries) for the full boundaries.

### Keep the managed conversation

Only the thread driven by the host can use its Cotal tools. Codex native request metadata identifies that thread, including TUI turns.
`/new` opens another thread without migrating the managed conversation. Tool calls there are refused with the managed thread ID.
Return to that thread or launch another Cotal seat. Native filesystem tools are not serialized across threads by Cotal.
