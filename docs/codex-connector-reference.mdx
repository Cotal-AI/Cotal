The `codex` connector runs a host process that owns one mesh endpoint and drives a Codex app-server thread over JSON-RPC.
[Connect Codex](connect-codex.mdx) covers installation and launch procedures.

## Tool connection

Codex's MCP client cannot wake an idle session, so the managed
connector runs Codex's own client/server split: a small **host process** embeds the mesh
endpoint and drives a `codex app-server` thread over JSON-RPC (the same protocol the Codex TUI
runs on). The app-server runs as an authenticated loopback **listener** rather than a private
pipe, which is what lets Codex's own TUI attach to the very thread the mesh is driving.

- **Wake and steer.** An inbound batch starts a real turn (`turn/start`). A DIRECTED message
  (DM, anycast, @mention) arriving during a connector-started turn is injected into that turn
  (`turn/steer`). During an externally started turn, the connector buffers the message and starts
  a delivery turn after the external turn ends. The external turn's completion cannot acknowledge
  a connector batch it did not carry. In focus mode, an @mention's pull hint can still steer an
  external turn; the message body stays on the inbox recall path. Ambient channel chatter waits
  for the turn boundary so it can't derail work in flight.
- **Native tools, one endpoint.** The host serves the shared `cotal_*` tools itself, on a
  bearer-authenticated loopback MCP endpoint (the token is passed by env name, so it never appears
  in the process table; see [Limits](#trust-boundaries) for what that token does and does not protect). The model calls them like any tool and they
  execute against the host's single mesh endpoint: no sidecar process, no second identity. The
  app-server is the MCP client, so the tools work the same on a turn a peer message started and
  on one **you** typed into the TUI.
- **One managed conversation.** Only the thread the host drives can use its Cotal tools. Codex's
  native MCP request metadata identifies that thread, including turns typed in the attached TUI.
  Cotal tool calls from a second root thread are refused, rather than speaking with the managed
  conversation's identity. Native filesystem tools are not serialized across threads by Cotal.
  An app-server restart binds the replacement thread without creating a second mesh lifecycle.
- **Ready means on the mesh.** The host announces `ready` and hands the terminal to Codex only
  after the app-server, MCP surface, and mesh endpoint are all live (including the initial
  presence publish). If the broker cannot be reached, startup fails within 15 seconds with the
  broker address and latest connection error; it never opens an offline-looking TUI.
- **At-least-once delivery.** A turn's surfaced messages are acked (by exact id) when the turn
  completes, and also when the operator interrupts it (Escape in the attached TUI): that dismisses
  the batch rather than redelivering it. A failed turn retries with backoff for three turns total,
  counting the first attempt and two retries for each buffered message. Broker redelivery of the
  same nonempty message id does not reset that budget. At the limit, the host log and seat status
  name the paused message ids and `cotal_inbox` as the way to read them. The messages stay
  unacknowledged, not discarded or reported as handled, and new messages can still start turns.
  The pause lasts while those messages remain in this host's bounded inbox, across app-server
  restarts but not a host-process restart. An empty message id has no cross-delivery identity and
  cannot share a retry budget across broker copies. An unknown terminal
  outcome (a missing or unrecognized status) leaves the batch un-acked with no retry of its own. If
  the Codex app-server itself dies, the host restarts it in place (same mesh identity, credential,
  and durable) and re-drives the un-acked batch into the new thread; a crash *loop* (more than 3 in
  2 minutes) is fatal rather than an endless respawn. A retirement (the host shutting itself down)
  interrupts any live turn too, but that batch stays un-acked and redelivery to it is not promised:
  a later same-name spawn is a successor with its own delivery frontier. (The shared bounded-inbox
  overflow rule applies: under extreme bursts an evicted in-flight id cannot redeliver.)
- **Isolated, never written.** Each agent gets a private `CODEX_HOME` (one hashed directory
  per space+name under `.cotal/codex/`, rooted at the manager's workspace): your `~/.codex`
  config.toml, hooks, and MCP servers never load into a managed agent, and Codex's per-project
  trust records never touch your real config. Your `auth.json` is symlinked in (re-linked each
  launch), so ChatGPT-plan token refreshes never fork. Without an `auth.json` (or an
  `OPENAI_API_KEY`) the launch fails loud at thread start. Keyring-stored credentials are not
  wired through the isolated home; use the file store or the env key for managed agents. That
  symlink is why managed Codex agents are **POSIX-only** today: on Windows without Developer
  Mode the link fails, and the launch fails loud rather than copying `auth.json` (a copy would
  fork the token and break plan refreshes).
  The app-server and TUI inherit non-secret seat attribution for `cotal stop --self`:
  `COTAL_SPACE`, `COTAL_MANAGER_INSTANCE`, `COTAL_NAME`, `COTAL_ID`, `COTAL_LIFECYCLE_UID`,
  `COTAL_ACCEPTED_TOKEN` and `COTAL_HOME`. Broker credentials and the launch-material pointer
  remain private to the connector host.
- **Autonomy defaults.** Spawned agents run `approval_policy=never` unless asked otherwise,
  `sandbox_mode=workspace-write`, and `sandbox_workspace_write={network_access=true}`.
  See [Sandbox autonomy](#sandbox-options) for what each one means and how to
  change it.
- **It really is Codex.** `cotal spawn --agent codex` drops you into the actual Codex TUI,
  attached to the thread the mesh drives (`codex resume --remote`). Mesh turns render as they
  happen, and anything you type is a real user turn on that same thread with the `cotal_*` tools
  still available. In the foreground that is your terminal; detached it is the manager's pty,
  which is what `cotal attach` streams and drives. With no terminal at all (piped output,
  CI, a smoke) the host stays headless and prints an activity feed instead: the same peer either
  way, only the UI differs.
  **Which mode you get** is decided by whether *stdout* is a terminal, and `COTAL_CODEX_TUI=1|0`
  overrides that check when it would guess wrong (a wrapper that redirects output, a CI run that
  wants deterministic text). The host refuses any value outside the on/off spellings in
  [Configuration](config.mdx#environment-variables) when it starts. It is read from the environment
  of **whichever process builds the launch**, so set it in the right place:
  - foreground `cotal spawn`: your own shell, per spawn;
  - detached (`-d`): the **manager's** environment, because the manager builds the launch. Set it
    when you start the stack (`COTAL_CODEX_TUI=0 cotal up --detach`). It applies to new Codex seats
    that manager launches. Changing the value requires restarting the manager. Setting it in the
    shell that runs `cotal spawn -d` does not affect the launch.

  A detached agent gets the manager's pty, which *is* a terminal, so the default there is the TUI,
  which is what `cotal attach` streams.
  Once the TUI paints, the terminal belongs to Codex, so the host's own diagnostics move to
  `host.log` inside the agent's private home
  (`<workspace>/.cotal/codex/<space>-<name>-<hash>/host.log`; the handoff line prints the exact
  path, and `ls -t .cotal/codex/*/host.log` finds it after the fact). Attached, a failure is also
  reported on the terminal; detached, that report goes to the pty, so the file is the durable copy.
- **Presence from events.** working/idle/waiting are derived from the app-server event stream;
  a user-input request's temporary waiting presence does not end the host turn. A completed
  native turn still yields `done` for its surfaced workflow turn after the host answers a
  user-input request, even if no later command or MCP item runs. Explicit `blocked` and
  `handoff` yields remain unchanged.
  Approval requests relay an `approval` condition. A failed turn maps its native
  `codexErrorInfo` into the closed condition vocabulary and preserves that value in
  `condition.source`. Presence writes leave the host in the order the events arrived, so a
  turn that fails or asks for approval in the tick it started keeps its condition until the
  next turn starts. The model id is reported from the started thread.

  `contextWindowExceeded` maps to `context`; `sessionBudgetExceeded` to `budget`;
  `usageLimitExceeded` to `billing`; `rateLimitExceeded` to `rate_limit`;
  `serverOverloaded` to `overloaded`; `internalServerError` and `httpConnectionFailed` to
  `server`; `unauthorized` to `auth`; `badRequest`, `cyberPolicy`, and
  `misalignmentPolicyViolation` to `request`; and rollback, sandbox, `other`, or an unrecognized
  value to `failed`. An error marked `willRetry` maps to `retrying` while keeping its native source.

`--opt k=v` launch options render as codex `-c k=v` config overrides on the app-server child
(top-level keys, scalar values; write TOML inline-table text yourself for nested values). The
connector's own defaults and selectors ride the same rail and yield to yours, except
`mcp_servers`, which is how the agent reaches the mesh: the whole namespace is refused loud (at
spawn, not at launch) rather than silently overridden.

## Agent commands

On a per-user mesh the host runs Codex's skills as [agent commands](connector-runtime-reference.mdx#agent-commands).
It lists the enabled skills that Codex's `skills/list` finds for the agent's working directory,
read again from disk on every list, by each skill's name and description. Codex lists a repo skill
before a user or system skill of the same name, and the host lists and runs only that first one.
A skill runs as a turn of its own, only while no other turn runs: `turn/start` carries
`{ type: "skill", name, path }` with the listed path, and the args, when given, as the turn's text.
Codex loads the skill's `SKILL.md` into that turn as the skill's instructions. Codex runs a turn even
for a skill path it cannot read, so the host refuses an unknown or disabled name as `not-found`
before it asks Codex. Right after a skill's turn, waiting messages go before the next queued skill.
`interrupt` sends `turn/interrupt` for the running turn, the host's or one typed into the attached
TUI, and answers `interrupted`. It answers `idle` when no turn runs, and when Codex refuses because
the turn already ended. A stopped turn ends `interrupted`, which the host handles as an Escape in
the TUI: the messages it carried count as delivered, and the next queued skill runs.

`turn` runs the owner's words as a turn of its own on the same thread, again only while no other
turn runs. `turn/start` carries the text, and each image as `{ type: "image", url }` with a `data:`
URL, as T3 Code sends them. A turn of images alone sends no text. When Codex refuses the start, the
turn ends `refused` with `failed-precondition`. `usage` answers the thread's context use from
Codex's last `thread/tokenUsage/updated`: `used` is the last model call's total tokens, which is what
Codex's own context meter counts, and `size` is the model's context window. It has no context until
Codex reported both, and none again after an app-server restart starts a new thread. Codex reports
no cost.

Codex's app-server has no method that lists or runs its built-in slash commands or custom prompts,
so the agent offers no `command` target, and a `command` for one is `unimplemented`.

## Model reporting

```bash
cotal models --harness codex             # ids, reasoning efforts and modes, via app-server model/list
cotal spawn --agent codex --model gpt-5.6-sol --variant high --mode fast=false
```

The **variant** is Codex's reasoning effort, from the efforts `model/list` names for each model.
The `fast` mode is Codex's Fast service tier, listed on each model that offers it. The catalog row
carries Codex's description, the default model, the default effort, and the tier Codex runs by
default. A launch is refused an effort or mode the row does not list.

The catalog comes from a short-lived `codex app-server`, the binary a launch runs:
`COTAL_CODEX_BIN` when you set it, otherwise the absolute path the manager resolved when Codex became available.
If it exits, closes its input, or does
not answer `model/list` within 10 seconds, `cotal models` reports that as the Codex error and the
manager keeps serving the other connectors.

Model and variant are published on presence, which is where the web dashboard's `model · variant`
badge reads them from. The variant appears only when you asked for one (via
`--variant` or `variant:` in the agent file): there is no way to read the effort back off a running
thread, so an unset variant is shown as absent rather than guessed at. After a switch, presence
shows the model and effort the switch answered.

### Switching the model

On a per-user mesh the owner switches the agent's model with the `agent` endpoint's `set-model`
command. Codex accepts a model name it does not know and finds out only when a turn runs, so the
host first reads `model/list` from the agent's own app-server, hidden models included. A model it
does not list is refused as `not-found`. A variant the model's reasoning efforts do not list is
refused as `failed-precondition`. The host then sends `thread/settings/update` with the model and
the effort. Without a variant it sends the model's default effort from `model/list`, because an
update with no effort keeps the previous one. Without a model it keeps the model the thread runs
and changes only the effort. When Codex refuses the update, the switch is refused as
`failed-precondition` and nothing changes. The answer names the model and effort Codex runs from
then on.

The switch applies from the next turn, and a turn already running keeps its model. Codex tells
every client attached to the thread, so turns typed into the attached TUI follow it. After an
app-server restart the host sends the same update to the new thread before that thread runs a
turn, and a new thread that refuses it stops the agent. The host does not see a model picked with
`/model` in the attached TUI, so a `set-model` without a model keeps the model the host launched
with or last switched to. `thread/settings/update` belongs to Codex's experimental app-server API,
which the host already turns on.

## Sandbox options

A spawned Codex agent is woken by peer messages, which arrive when nobody is watching the
terminal. The defaults follow from that, and all three are overridable per spawn with `--opt`.

| Default | What it means |
| --- | --- |
| `approval_policy="never"` | Never **ask** before running a command. Not "refuse": the agent runs its commands, it just does not stop to prompt. An asking policy is answered through the prompt desk (see [Answering approvals](#answering-approvals)). |
| `sandbox_mode="workspace-write"` | Commands may read anywhere but write only inside the agent's workspace. This, not the prompt, is the part that is actually enforced; see below for the (real) exposure it leaves. |
| `sandbox_workspace_write={network_access=true}` | Network **on** inside that sandbox. Codex's own default is off, which breaks installing a dependency, pushing a branch, or calling an API, with an error that reads like the task is impossible rather than the sandbox saying no. Applied only when the sandbox is actually `workspace-write`: tighten the mode and no network grant is emitted at all. |

### Answering approvals

With an asking `approval_policy`, the seat serves Codex's requests
on its `agent` endpoint (SPEC 13.22) and declares `prompts`.

The connector declares `supportsAskPermissions`. A Manager launch with `askPermissions` starts the
thread with `approvalPolicy: "untrusted"`, a `read-only` sandbox and the user as the approvals
reviewer, as T3 Code's approval-required mode does. These go on `thread/start`, because codex 0.162
refuses `approval_policy = "untrusted"` in config, and they replace the autonomy defaults above. Such
a launch is refused when its launch options set `approval_policy`, `sandbox_mode` or
`approvals_reviewer`.

The prompts:

- A command approval opens a `permission` prompt for `exec_command` (or `write_stdin` for input to
  a running command) with the command, its working directory and Codex's reason.
- A file change approval opens a `permission` prompt for `apply_patch` whose input is the change
  list Codex proposed on the item, `{ changes: [{ path, kind, diff }] }`.
- Both offer Codex's decisions: allow, allow for this session, deny, and deny and stop the turn.
  A server that lists its decisions gets only those.
- When the prompt would pass the desk's size limit, as a patch that deletes a large file does, its
  input is left out and only deny and deny and stop the turn are offered. Nobody can read that
  input remotely, so it cannot be approved there; the attached TUI can still approve it.
- A permissions request opens a `permission` prompt for `request_permissions`. Codex sends one when
  the model calls its `request_permissions` tool, which a launch turns on with
  `features.request_permissions_tool`, to ask for network access or file system access the sandbox
  does not give. The input is what it asks for, `{ permissions: { network?, fileSystem? } }`, and the
  body gives the model's reason and names the access. Allow for this turn or for this session
  grants what it asked for, and deny grants nothing.
- An MCP tool-call approval opens a `permission` prompt. Codex sends one, as an MCP elicitation,
  before it runs a tool of an MCP server other than cotal, such as a server that a trusted project's
  `.codex/config.toml` defines. Its subject is the running call, with the tool's arguments and the
  server. It offers allow, the persistence Codex lists, deny and cancel. Allow for this session
  lasts until Codex's session ends, and always allow is saved in the config that defines the
  server. Deny and cancel both stop that call, and the turn goes on.
- A form that an MCP server asks for opens a `form` prompt with the server's fields, and its body
  names the server. Submit sends the values, and decline and cancel send none. A url elicitation,
  an OpenAI form, or a form outside the desk's form profile is not put on the desk.
- A `request_user_input` call opens a `question` prompt with a form, one field per question. A
  question with choices and no free answer is a single choice. A question marked secret is not put
  on the desk, because a form never asks for a secret.

The answer goes back as the request's result. The attached TUI shows the same request, and
whichever answer reaches Codex first applies. Codex reports only that the request was resolved,
not who answered, so a prompt the TUI answered first closes `withdrawn`, and one answered remotely
closes unconfirmed. A request nobody answers stays open for seven days and is then declined, or
cancelled when it is an MCP elicitation. A seat whose `agent` endpoint the broker refused, which its
log reports when it joins, holds no prompt desk. A permissions request that no prompt desk holds
grants nothing, an MCP elicitation that no prompt desk holds is cancelled, and any other request is
declined.

What the sandbox guarantees, stated literally: it **blocks out-of-workspace local filesystem
writes**. It does **not** block reads, exfiltration, or networked side effects.

All three of those are live with the defaults above, because a peer's message is a **remote input**
that can cause this agent to run commands. A confused or hostile peer can in principle get it to
read a file elsewhere on your machine and send it; reach loopback or link-local services; or act
through any credential it can read, which includes irreversible actions: a force-push, an API
delete, a deploy. Containing filesystem writes is therefore not the same as containing damage, and
it should not be read that way. It is still worth keeping, because it is the one class this sandbox
can actually enforce.

If that exposure is wrong for a given agent, turn the network back off (below), tighten the mode,
or run it under a separate OS user; the same point is repeated under [Limits](#trust-boundaries) so it
survives a skim. The spawn capability is the trust boundary for *who* may create an agent; the
sandbox bounds one class of what it can then be talked into doing, not all of it.

Tune it per spawn:

```bash
cotal spawn --agent codex --opt sandbox_mode=read-only                        # tightest: no writes
cotal spawn --agent codex --opt 'sandbox_workspace_write={network_access=false}'  # contained, offline
cotal spawn --agent codex --opt sandbox_mode=danger-full-access               # no sandbox at all
```

`danger-full-access` is Codex's own name for it and means what it says: the agent may write
anywhere your user account can. Codex documents that mode as intended only for environments that
are already externally sandboxed (a container, a VM), not a workstation. On a laptop, prefer
tightening the workspace over removing the sandbox.

## Event plane

The shared launch and emitter carry payload-withholding safety controls. This release does not
qualify Codex payload mapping or native payload acceptance. See the
[payload rules](claude-connector-reference.mdx#event-plane) for the separate rail and current scope.

A spawned seat publishes a structured account of what it did: run
boundaries per turn, assistant text, reasoning when the launch asks for it, and the tool calls the model makes through Codex's
function-call and custom-tool interfaces, each with its start and its end. Tool arguments and
tool results are not republished onto this channel. That covers the tools you watch a seat use,
`shell` and `apply_patch` among them. The channel is
`events.<owner>.<actor>`, named after the seat's principal, and the rules for it are the same on
every connector: see [connect-claude.md](connect-claude.mdx#event-plane) for the channel, the grant,
and how to read it. The launcher sets `COTAL_EVENTS` by default; pass `--no-events` to opt out on an
unrestricted space. A registration that requires events refuses `--no-events`, and its launch
always carries the flag and the workspace root the event log lives under. A hand-driven user-mode
launch with `COTAL_EVENTS_REQUIRED=1` arms the plane without that flag.
Your own `codex` publishes nothing unless its environment arms the plane or the Cotal plugin connects
it. A plugin connection publishes its own activity from the moment you approve it; see
[your own Codex conversations](connect-codex.mdx#personal).

```bash
cotal spawn watcher --agent codex -d   # event plane armed; read it with `cotal console`
```

Twelve things are specific to Codex and worth knowing before you read a stream:

- **The thread's rollout file is the durable record.** The seat's
  rollout lives inside its own isolated `CODEX_HOME`, under
  `<workspace>/.cotal/codex/<space>-<name>-<hash>/sessions/<yyyy>/<mm>/<dd>/rollout-<stamp>-<thread>.jsonl`.
  Reading the file rather than the stream is what lets the seat resume a thread's stream where it
  stopped after its own process restarts, rather than reopening it from the top.
- **A restarted app-server is a NEW thread, and its stream is a new one.** When the child dies and
  the seat brings up a replacement, Codex starts a fresh thread with a fresh rollout. The seat
  finishes the old one first, publishing what it had and closing any run left open, then begins
  publishing the new thread under its own write-ahead log. A reader sees one stream end and another
  begin, never one stream silently continuing under a different thread. If the new thread's file is
  slow to appear the order is the other way round: the seat spends its whole bounded look for the new
  file first, and the old stream ends when that look gives up, not at the moment of the restart. From
  the give-up on it publishes nothing until the new thread binds at a later turn boundary; it does not
  keep reporting the dead thread's activity in the meantime.
- **The stream starts where the seat binds to the file.** `thread/start` writes nothing to disk; the
  file appears when the thread is primed. The seat binds to it then, and publishes from that point
  forward. If the file is slow to appear the seat says so in its log and looks again at each turn
  boundary, and whatever the thread wrote before the bind is not republished. A seat stopped before
  it binds leaves without binding.
- **Codex's built-in tools remain private to the host.** Web search, tool search and image generation
  record an end with no start, and nothing joins the two halves: the start-shaped record carries no
  call id and the end carries one. Rather than guess a pairing, the seat drops them, so those tool
  uses are absent from the stream while everything on the function-call path is present.
- **Failed turns publish run errors.** Codex records a failure on
  the turn's own completion record, so a turn that hit a usage limit or an upstream error ends its
  run with `RUN_ERROR` carrying the fixed message `run failed` and no code. Neither Codex's error
  text nor its `codex_error_info` is published there: both are upstream values that can echo your
  prompt or tool output, and the events channel has a different read ACL. Both reach presence as the
  agent's condition, and an [ACP thread](acp-clients.mdx#threads) shows them when the turn fails.
- **No user-authored text is published, ever.** Your prompts, the peer messages injected into the
  thread, and the developer instructions the persona supplies are all withheld. The events channel
  carries a different read ACL from the channel you typed into, so republishing your own words there
  would widen who can read them. Assistant text, reasoning and tool activity are unaffected.
- **A broker outage can stop the plane.** Initial mesh absence still
  fails the host's readiness gate within 15 seconds, so it never opens an offline-looking TUI. Once
  ready, the plane publishes through the seat's reconnecting mesh endpoint, and an outage can stop
  its emitter. The seat keeps running on every space, its log records `AG-UI emitter stopped` with
  the delay before the plane is re-established, and the thread publishes again from its stored
  cursor once that succeeds.
  Tool arguments and tool results are not published. The stream also does not carry the
  session's own record of the user's words and the developer instructions. A bind announces
  where the stream starts and the emitter's setup then runs before its first read; what the
  thread appends inside that window is published rather than left behind the cursor, and a whole
  turn can sit in there. Nothing is sent twice. The boundary itself is written to the log as soon
  as the bind succeeds, so a host that dies before its first read still resumes from that boundary
  rather than from wherever the file ends by the time it comes back.

  The grant still does not decide who may READ a plane. A spawn through the manager gives a seat
  publish rights on its own event channel and nothing else, and a spawn whose grant names a
  different agent's event channel is refused at the door. That fence is the manager's, it reads
  the concrete form and leaves a pattern such as `events.<owner>.>` to ordinary ACL authority,
  and a foreground `cotal spawn` on your own machine grants whatever you name because it mints
  from your own signing material. [connect-claude.md](connect-claude.mdx#event-plane) spells all
  three out. Who may READ a plane is minted separately and out of band either way, with
  `cotal actor grant` on a user-auth mesh and `cotal auth mint --profile agent --allow-subscribe` on a
  static one. Who may read the plane is still that mint, not the spawn grant.
- **Assistant text and reasoning summaries stream while Codex writes them.** The seat journals the
  deltas of each agent message and each reasoning summary next to the thread's write-ahead log, at
  most one line every 250 ms, and publishes them under the message id `stream:<item id>` before
  Codex saves the record. The saved record then sends the rest of its text and ends the message, so
  a reader gets the saved text once. When the saved text does not continue what streamed, the
  streamed message ends and the saved text is published as a message of its own, so a reader sees
  the abandoned text once. A message that began before the seat opened its journal, as the first
  reply of a seat still connecting to the mesh can, is published whole when Codex saves it. A turn
  that ends, or a seat that stops, while a message streams ends that message before the run. A
  reasoning summary streams only when the model provider sends one.
- **Reasoning is off by default, and published as its summary only.** A seat launched with the
  [`reasoningEvents` field](connectors.mdx#opt-in-launch-fields) publishes it, and sends a reasoning
  summary setting on every `turn/start`: the `model_reasoning_summary` set with `--opt`, else
  `auto`. Codex's model catalog can default the summary to none, and T3 Code's own Codex provider
  sends the same setting on each turn. A seat without the field publishes no reasoning, journals
  none, and leaves Codex's own default in place. Codex also stores an encrypted reasoning blob on
  every reasoning record; it is opaque, no reader can display it, and it is never put on the wire.
- **Each tool result carries the `cotal.toolResult` marker.** A Codex tool output has no error flag,
  so `isError` comes from the call's end record: a command's exit code, whether a patch applied, or
  an MCP tool's error. When the seat has seen no end record for the call, as for `write_stdin`,
  `update_plan` or a command still running when its output is written, the marker leaves `isError`
  out.
- **In code mode, the calls a script makes are the tool calls.** With code mode, which Codex 0.162
  runs for its catalog models, the model makes every tool call from one `exec` script. app-server
  reports no item for the script, so T3 Code's own Codex provider shows only the calls it makes.
  The seat does the same: the script and its output are not published. Each command, file change
  and MCP call the script makes is published as its own tool call, `exec_command`, `apply_patch`
  with Codex's change list, or the MCP tool's name. The rollout records such a call only once it
  has ended, but app-server reports it when it starts, and the seat journals that. So the call is
  published while it runs, and its result when it ends. A call that started before the seat opened
  its journal is published whole at its end.
- **The plan tool is off unless a launch turns it on.** Codex 0.162 offers `update_plan` only when
  its config enables the tool, as T3 Code's own Codex provider does for every thread. A seat gets
  it with `--opt 'tools={update_plan={enabled=true}}'`, since a launch-option key names one config
  field. A direct `update_plan` call is published from the rollout. A plan a code-mode script sets
  reaches app-server clients only as `turn/plan/updated`, so the seat journals it and publishes it
  as the `update_plan` call the script made, with the plan in `update_plan`'s own arguments. A plan
  Codex reports before the seat opens its journal is not published.

## Trust boundaries

- **The sandbox blocks out-of-workspace filesystem writes, and only that.** It does not block
  reads, exfiltration, or networked side effects. With the default `workspace-write` + network on,
  a peer-driven turn can read anything your user account can (`~/.ssh`, `~/.aws`, `.env` files, the
  agent's own `auth.json`) and send it; reach loopback and link-local services; and act through any
  credential it can read, including irreversibly (a force-push, an API delete, a deploy). Only
  local writes outside the workspace are stopped, so this is not "everything risky is reversible"
  and not "the only exposure is disclosure". If that is wrong for a given agent, spawn it with
  `--opt 'sandbox_workspace_write={network_access=false}'` or `--opt sandbox_mode=read-only`, or
  run it as a separate OS user. See [Sandbox autonomy](#sandbox-options).
- **Not a boundary between agents on one machine.** The app-server listener and the tool
  endpoint are both loopback-bound and token-authenticated, which keeps out other OS users and
  anything off-box. It is not isolation between *managed agents*, which run as the same user and
  can therefore reach each other's tokens; a hostile agent on your workstation could drive
  another's Codex or speak as it on the mesh. Run mutually distrusted agents under separate OS
  users or separate machines.
- **The TUI is local-only.** The app-server listener binds loopback and nothing else, so
  attaching Codex's UI to an agent on another machine needs your own SSH port-forward; there is
  no built-in remote attach. `cotal attach` (which streams the manager's pty) is the supported
  way to reach a detached agent.
- **`/new` does not replace the managed conversation.** The attached TUI can open a different
  thread, but the host keeps driving its original thread. Cotal tool calls from the other thread
  fail with an explanation naming the managed thread. Return to that thread in Codex, or spawn
  a separate Cotal seat for another conversation. There is no thread migration or hook recovery.
- **No session resume.** `cotal spawn --resume <id>` throws: a resumed codex thread comes up
  without its configured MCP servers, so the agent would be mute on the mesh.
- **No tool-sharing.** `connectors.codex.mcpServers` is not implemented and throws if set.
- **Experimental upstream surface.** `codex app-server` is labeled experimental by OpenAI (it
  is also what the Codex TUI itself runs on). The connector pins every protocol shape in one
  driver file and re-proves the contract with a gated live smoke (`COTAL_E2E_CODEX=1`).
