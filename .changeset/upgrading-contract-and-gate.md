An operator upgrading a deployment that already exists now has a page to read before starting. `docs/UPGRADING.md` states the pre-1.0 upgrade contract in operator terms and carries the first release section, 0.48.2 to 0.49.0.

The section answers what a running fleet actually needs to know. Existing agent credentials keep authenticating, the channel registry survives, standalone `cotal deliver` is still supported, and `cotal join --lifecycle-uid` is not new in this release. What does not migrate is renewal: a credential minted before 0.49.0 carries no issuance, so the manager refuses to renew it and names the agent.

Respawning the managed agents is a required step of this upgrade rather than a tidy last pass, and the reason is the upgrade itself rather than the credential. Stopping a 0.48.2 manager ends its agent processes whichever CLI does the stopping: sparing them is a capability a 0.49.0 manager publishes and a 0.48.2 one never did, so the newer CLI either refuses the stop or falls back to signalling the older manager anyway. The respawn is how the fleet comes back, and it is also what mints each credential as an issuance so renewal works from then on.

It also gives the order for a split broker and manager topology, what the outage window looks like and what survives it, what to snapshot first, and the commands end to end. Where an answer was reasoned from the code rather than measured on a fleet, the page says which.

A repository check keeps it true. `scripts/upgrade-section-gate.mjs` refuses a range that carries a breaking change and adds no new release section to the page in that same range. It grades itself in one invocation over three legs: breaking with no new section reds and names what it caught, breaking with a new section stays green, and non-breaking with no section stays green, so a gate that detects breaking changes is distinguishable from one that reds on everything. Replayed against the v0.48.2 to v0.49.0 range it refuses, naming both breaking commits.

Coverage is the sections a range **added**, base compared against head, and not whether the range touched the page. The first version of this check asked only the weaker question, and it accepted on the total number of sections the page carried at head, so a breaking change shipped beside a one-line typo fix passed on eight sections written for earlier releases. That predicate accrues coverage it never earned and grows weaker every time someone does the right thing, because each new section becomes permanent pre-coverage for every future break. Stated plainly: it greened on a breaking release that did no upgrade work, which is the reported failure reintroduced one level up inside the thing built to prevent it. An edit that adds no section now reads the same as no edit, and rewording an existing release's section is not coverage for a new one.

A section must also name the release it covers, and only a top-level heading counts. Coverage is claimed by a heading, so a heading that names no release claims everything and distinguishes nothing: without the rule the cheapest way to satisfy the check becomes a section called Notes with one sentence under it, or an unrelated heading that happened to land in the same range. Subsections belong to their release rather than counting as further coverage, which is also why this page reports one new section for 0.49.0 instead of the eight its subsections used to inflate it to.

Misuse and refusal are distinct exits. A mistyped ref used to let the underlying git read throw out of the top level, printing a stack trace and exiting 1, the refusal code, so a job with a bad base ref reported a missing upgrade section for a verdict that was never computed. Misuse now exits 2 with one sentence, and every git read reports in the tool's own words rather than leaking a raw fatal line under an otherwise legitimate refusal.

The page's own facts were re-measured against the source rather than against an earlier draft, and every command in it was run against real CLIs built at both releases. That found eight corrections, most of which change what an operator does. Managed credentials are re-signed once a credential passes 75 percent of its life, not at half life: half-TTL is named in the manager as the old schedule and as the cause of #457, so the page had been repeating a schedule the project already fixed and would have had an operator expecting renewal at 12 hours when it happens at 18. Bare `cotal backup` and bare `cotal channels` are usage errors at both releases, which reading the page twice had missed and running it found immediately. The durable backup path turns out not to be available on a split topology at all, because `cotal backup` needs a cut that only `cotal down --preserve-state` publishes, and that in turn needs a manager alive on the same host to attest its children stopped. The page now says so plainly and points at the volume snapshot instead of inventing a sequence that merely parses. The recipe also stops the manager that `cotal up --detach` starts on the broker host, since there is no broker-only mode and the procedure as written finished a split-topology upgrade with a second manager nobody intended. An external peer's `cotal mint` credential is issued with no expiry and no manager renews it, so the advice to re-mint those has gone. The `--lifecycle-uid` pairing rule predates the release the page named. And the contract now states that a change to a credential's shape, or to who may renew one, is breaking whatever the commit marker says, since a fleet that still authenticates looks compatible and is not.

The page also says what the check does not prove. It proves a section was written for the release. It cannot prove the section is correct. That limit is stated where a reader will meet it rather than left for someone to discover by trusting it too far.
