`cotal_inbox` now delivers a message larger than one response in parts. Once no smaller mail is waiting, each call carries the next part, a peek shows the current part without moving on, and the message is cleared only after its last part goes out. This holds for focus recall too: an oversized channel message recalled in focus is read in parts, and recall does not move past it before its last part. A recalled message with an empty id is keyed by its stream sequence, so it keeps one receive key across calls, even when an older identical message ages out, and is read through to its last part and not served again afterwards. Within one read every message is tracked by its receive key, so a held message with an empty id is named in the reply, and a recalled message with an empty id stamped ahead of the local clock no longer moves recall past an oversized message that has not been read. Focus recall also no longer skips every message with an empty id once one quiet or muted message with an empty id was excluded from it: recall pairs the stored copies of an id-less message with its deliveries in focus, newest first, and hides only a copy whose delivery was excluded. A later publication of the same content that the same path delivered is still recalled, also after the excluded copy ages out, and excluding a later copy no longer lets it back into recall in place of an earlier one. A delivery excluded while recall is reading history is honored for a copy the read returned, and an identical publication the read did not see yet no longer hides an earlier message or lets recall move past the rest of it. When two delivery paths disagree about one stored copy, recall hides it and reports the channel as incomplete instead of guessing from which path delivered first, since nothing orders the paths. A recalled message that already went out in part is read to its last part, even if an exclusion lands after its first part. The read position survives a reconnect; a process restart starts the message again from its first part. `recallChannel` in core now also returns each message's stream sequence for this. Before this, such a message was named but could never be read.
