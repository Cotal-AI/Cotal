`service start --new-instance` of a service whose HTTP readiness address its first instance answered reported the new instance running and reachable, though the new process had already failed to bind that port. A start now sends one readiness request before it launches, and when something already answers there it refuses `CONFLICT`, exit 2, naming the address and the instance that answers, and launches nothing. A service that keeps answering its readiness check with another status, such as 503, now fails with `OPERATION_FAILED`, exit 5, naming that status, instead of sharing the unknown outcome of a check that got no answer. That unknown outcome's Next now also names `cotal service show <name>`, which shows the readiness deadline. A process service with process readiness whose child exits at once, such as on a bad configuration, was reported running by `service start` and `service restart`, and its exit code was never recorded. Process readiness now waits up to one second for such an exit, and the start fails with `OPERATION_FAILED`, exit 5, recording the exit code; a restart is partial, exit 4, and names the replacement's exit code and its log.
