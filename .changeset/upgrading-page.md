An operator upgrading a deployment that already exists now has a page to read before starting. `docs/UPGRADING.md` states the pre-1.0 upgrade contract in operator terms and carries the first release section, 0.48.2 to 0.49.0.

The section answers what a running fleet actually needs to know. Existing agent credentials keep authenticating, the channel registry survives, standalone `cotal deliver` is still supported, and `cotal join --lifecycle-uid` is not new in this release. What does not migrate is renewal: a credential minted before 0.49.0 carries no issuance, so the manager refuses to renew it and names the agent. The fleet therefore comes up fine and then stops one agent at a time about a day later, which is the failure the reporting deployment was heading for.

Respawning the managed agents is a required step of this upgrade rather than a tidy last pass, and the reason is the upgrade itself rather than the credential. Stopping a 0.48.2 manager ends its agent processes whichever CLI does the stopping: sparing them is a capability a 0.49.0 manager publishes and a 0.48.2 one never did, so the newer CLI either refuses the stop or falls back to signalling the older manager anyway. The respawn is how the fleet comes back, and it is also what mints each credential as an issuance so renewal works from then on.

It also gives the order for a split broker and manager topology, what the outage window looks like and what survives it, what to snapshot first, and the commands end to end. Where an answer was reasoned from the code rather than measured on a fleet, the page says which.

The page's own facts were re-measured against the source rather than against an earlier draft. Which commands were executed and which were reasoned from source is stated in the page rather than implied: the `cotal backup create` refusal, the bare `cotal backup` and bare `cotal channels` usage errors, the `--with-agents` flag rule, the `cotal stop` grammar and the `cotal spawn` grammar were each run against real CLIs at the release named beside them, the 0.48.2 and 0.49.0 `down` summary lines were read from the command table at each tag, and the boot and renewal log lines were verified against the format strings that emit them. The two-host split itself was not performed, because it needs two hosts, so the ordering recommendation is labelled reasoned rather than measured in the page itself.

That found more than a dozen corrections, most of which change what an operator does. Managed credentials are re-signed once a credential passes 75 percent of its life, not at half life: half-TTL is named in the manager as the old schedule and as the cause of #457, so the page had been repeating a schedule the project already fixed and would have had an operator expecting renewal at 12 hours when it happens at 18. Bare `cotal backup` and bare `cotal channels` are usage errors at both releases, which reading the page twice had missed and running it found immediately. The durable backup path turns out not to be available on a split topology at all, because `cotal backup` needs a cut that only `cotal down --preserve-state` publishes, and that in turn needs a manager alive on the same host to attest its children stopped. The page now says so plainly and points at the volume snapshot instead of inventing a sequence that merely parses. An external peer's `cotal mint` credential is issued with no expiry and no manager renews it, so the advice to re-mint those has gone. The `--lifecycle-uid` pairing rule predates the release the page named.

The end-to-end recipe was then read as a sequence rather than as a set of individually correct lines, which is where the rest of the corrections came from. It stops the manager with the 0.48.2 CLI before the install that overwrites it, rather than after. It stops the manager that `cotal up --detach` starts on the broker host, since there is no broker-only mode and the procedure as written finished a split-topology upgrade with a second manager nobody intended. It notes that `cotal supervise` runs in the foreground and has no detach flag, so an operator following the block top to bottom is not trapped at that line. And the boot wait is bound to the launch it is waiting for: the manager log is opened append-only, so on any host that has run a manager before, grepping the whole file matches a previous boot's line and returns immediately. The size is recorded before the start and only the appended bytes are read, mirroring what the product already does for its own broker wait.

The contract now also states that a change to a credential's shape, or to who may renew one, is breaking whatever the commit marker says, since a fleet that still authenticates looks compatible and is not.
